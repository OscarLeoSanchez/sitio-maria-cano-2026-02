Cambiar y borrar con seguridad

¿Cómo cambio o borro una fila sin tocar las demás?

Primera red

sql_safe_updates frena los descuidos

LIMIT 1 limita la sentencia a una fila como máximo. Con LIMIT la sentencia pasa aunque el WHERE no use una clave, como UPDATE ... WHERE nombre = 'Mouse' LIMIT 1;

@@nombre lee una variable de sesión. En la consola vale 0 y Workbench la activa. En un archivo, el cliente añade at line N tras el número de error.

UPDATE cambia valores de filas y DELETE las borra; ambos son sentencias DML y el WHERE elige las filas. Con la variable en 1, MySQL rechaza la sentencia si el WHERE no usa una columna clave.

Una red de seguridad

Una transacción es una línea de tiempo

  • Una transacción es un grupo de sentencias que se confirman juntas o se deshacen juntas.
  • START TRANSACTION la abre. Hasta cerrarla, tus cambios son provisionales.
  • COMMIT los confirma y ROLLBACK los deshace.

ON DELETE con datos

ON DELETE: qué pasa con los hijos

Una clave foránea es una columna que apunta a la clave de otra tabla. La tabla con la clave foránea es la hija (producto) y la referenciada es la padre (categoria). ON DELETE decide qué pasa con las hijas cuando se borra el padre.

TRUNCATE y el ROLLBACK

La tabla tiene 3 filas. ¿Cuántas filas hay tras TRUNCATE TABLE y ROLLBACK?

Tras DELETE y ROLLBACK, la tabla conserva sus 3 filas. Tras TRUNCATE y ROLLBACK queda vacía: TRUNCATE es DDL, una sentencia que define estructura, y hace un commit implícito, así que el ROLLBACK no tiene nada que deshacer.

Ejercicios

Ejercicio 3. Predecir tres DELETE

Sobre la base recién cargada, decide qué hace cada DELETE: si funciona, qué borra además de la fila indicada, y si falla, con qué error y por qué.
Solución
  • A funciona: borra el pedido 114 y, por CASCADE, su única línea.
  • B falla con 1451: el pedido 114 todavía apunta al empleado 2 (fk_pedido_empleado).
  • C falla con 1451: el producto 8 aparece en líneas de pedido (fk_detalle_producto).

Cada sentencia se evalúa sobre la base recién cargada. Si A se ejecuta antes que B, el pedido 114 ya no existe y B también funciona.

Reto

Ejercicio 4. Borrar un historial completo

Con la base recién cargada, Carlos (cliente 2) pide que borren todo su historial: el cliente, sus pedidos y las líneas de esos pedidos. Trabaja dentro de una transacción, comprueba los conteos y deja la base como estaba.
El orden importa: primero las filas hijas y al final la fila padre.
Solución
  1. Carlos tiene 4 pedidos.
  2. El primer DELETE falla por RESTRICT: error 1451.
  3. Borrar sus pedidos cambia 4 filas y, por CASCADE, sus líneas: quedan 48.
  4. Ahora el cliente se borra y quedan 9.

Resumen

Lo que quedó de modificar y borrar

  • UPDATE y DELETESiempre con WHERE, y con un SELECT previo.
  • sql_safe_updatesError 1175 si el WHERE no usa una clave ni un LIMIT.
  • TransacciónSTART TRANSACTION, ROLLBACK para ensayar y COMMIT para confirmar.
  • ROW_COUNT()Dice cuántas filas tocó la sentencia.
  • AutocommitSin transacción abierta, cada sentencia es definitiva.
  • RESTRICT, CASCADE, SET NULLEl cliente con pedidos no se borra; el pedido arrastra sus líneas; el jefe deja a su equipo en NULL.
  • TRUNCATEReinicia ids, no se deshace y falla con claves foráneas.
