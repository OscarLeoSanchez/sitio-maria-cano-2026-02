Unidad Unidad 4. Métodos de ordenamiento, búsqueda y eficiencia
Tema Tema 4. Algoritmos de búsqueda

El Tema 3 cerró con Dijkstra, Prim y Kruskal, tres algoritmos que resuelven un problema sobre un grafo entero. Este tema vuelve a una pregunta mucho más pequeña y mucho más frecuente en cualquier programa real, dado un dato concreto, está en esta colección y en qué posición. La Unidad 1 ya adelantó una comparación informal entre revisar una colección de principio a fin y aprovechar que está ordenada para descartar la mitad en cada paso, y el Tema 2 de esta unidad resolvió con la recurrencia T(n) = T(n/2) + O(1) por qué esa segunda estrategia crece en O(log n) en vez de en O(n). Este tema retoma las dos, les suma una tercera que usan a diario las bases de datos y los sistemas de archivos, la búsqueda secuencial indexada, y las implementa completas con programación orientada a objetos, el resultado de aprendizaje que la carta descriptiva reserva para el cierre de la asignatura.

1 La clase Buscador

Las tres estrategias de este tema trabajan sobre la misma clase, Buscador, que envuelve un arreglo y ofrece un método por cada forma de buscar en él. Separar el algoritmo del dato que recorre es la misma decisión de diseño que ya tomaron ArbolBinarioBusqueda en la Unidad 3 y GrafoPonderado en el Tema 3, el objeto expone el comportamiento y esconde cómo lo logra por dentro.

public class Buscador {
    private int[] datos;

    public Buscador(int[] datos) {
        this.datos = datos;
    }
}
class Buscador:
    def __init__(self, datos):
        self.datos = datos

2 Búsqueda secuencial: revisar uno por uno

La búsqueda secuencial, también llamada lineal, es el algoritmo más simple de los tres y el único que no exige ninguna condición sobre el arreglo, recorre las posiciones en orden, desde la primera, y compara cada valor contra el objetivo hasta encontrarlo o hasta agotar la colección completa. No necesita que los datos estén ordenados porque no usa el orden para nada, cada comparación descarta exactamente una posición, la que acaba de revisar, así que en el peor caso, el valor buscado no está o está en la última posición, hace tantas comparaciones como elementos tiene el arreglo, O(n).

public int buscarSecuencial(int objetivo) {
    for (int i = 0; i < datos.length; i++) {
        if (datos[i] == objetivo) {
            return i;
        }
    }
    return -1; // recorrio todo el arreglo sin encontrarlo
}
def buscar_secuencial(self, objetivo):
    for i, valor in enumerate(self.datos):
        if valor == objetivo:
            return i
    return -1  # recorrio todo el arreglo sin encontrarlo

Sobre el inventario [82, 14, 55, 3, 91, 22, 63, 8], sin ningún orden particular, buscarSecuencial encuentra el 63 en la séptima comparación, la posición 6, y se detiene ahí sin tocar la posición 7. Esta es exactamente la situación en la que la búsqueda secuencial es la única opción viable, datos que llegan en el orden en que ocurren, un registro de ventas del día, una lista de eventos, un inventario que se actualiza constante, donde ordenarlos solo para buscar una vez costaría más que la propia búsqueda.

TipReto 1. Cuántas comparaciones hace la peor búsqueda

Sobre el mismo inventario, [82, 14, 55, 3, 91, 22, 63, 8], ocho elementos, vas a llamar buscarSecuencial(40), y 40 no aparece en ningún lugar del arreglo. Antes de seguir, decide cuántas comparaciones hace el método antes de devolver -1.

NotaSolución del Reto 1

La tercera es correcta. buscarSecuencial no tiene forma de saber que el valor no está sin revisar cada posición, el bucle recorre los ocho índices, compara cada valor contra 40 y nunca encuentra una coincidencia, así que hace las ocho comparaciones, sale del bucle sin haber retornado nada dentro de él, y devuelve -1. Este es el peor caso de la búsqueda secuencial, el valor no está o está en la última posición, y en los dos casos el costo es O(n), el tamaño completo del arreglo.

3 Búsqueda binaria: descartar la mitad en cada paso

La búsqueda binaria exige una condición que la secuencial no pedía, que el arreglo esté ordenado. A cambio de esa condición, cada comparación no descarta una sola posición, descarta la mitad completa de lo que quedaba por revisar, porque comparar el objetivo contra el valor del medio del rango actual dice de una vez si el objetivo, de existir, está en la mitad izquierda o en la mitad derecha, sin necesidad de revisar ningún elemento intermedio.

public int buscarBinariaIterativa(int objetivo) {
    int ini = 0, fin = datos.length - 1;
    while (ini <= fin) {
        int medio = (ini + fin) / 2;
        if (datos[medio] == objetivo) {
            return medio;
        } else if (datos[medio] < objetivo) {
            ini = medio + 1; // descarta la mitad izquierda, incluido el medio
        } else {
            fin = medio - 1; // descarta la mitad derecha, incluido el medio
        }
    }
    return -1;
}
def buscar_binaria_iterativa(self, objetivo):
    ini, fin = 0, len(self.datos) - 1
    while ini <= fin:
        medio = (ini + fin) // 2
        if self.datos[medio] == objetivo:
            return medio
        elif self.datos[medio] < objetivo:
            ini = medio + 1  # descarta la mitad izquierda, incluido el medio
        else:
            fin = medio - 1  # descarta la mitad derecha, incluido el medio
    return -1

Sobre el arreglo ordenado [3, 8, 14, 22, 29, 35, 41, 48, 55, 63, 70, 77, 84, 91, 98], quince elementos, buscarBinariaIterativa(55) lo encuentra en cuatro comparaciones, no en las nueve que habría necesitado la búsqueda secuencial si 55 fuera el último valor revisado. Cada paso corta el rango a la mitad, así que el número de veces que se puede dividir quince entre dos antes de llegar a un solo elemento es exactamente lo que determina cuántas comparaciones hacen falta, la misma cuenta que ya resolvió el Reto 4 del Tema 2 con la recurrencia T(n) = T(n/2) + O(1).

La misma idea que el árbol binario de búsqueda

El Tema 3 de la Unidad 3 mostró que buscar en un árbol binario de búsqueda también descarta una mitad del espacio de búsqueda en cada comparación, izquierda si el dato buscado es menor, derecha si es mayor. La búsqueda binaria de hoy hace exactamente ese mismo razonamiento sobre una estructura distinta, un arreglo contiguo en memoria en vez de nodos conectados por punteros, así que en vez de bajar por una referencia izquierdo o derecho, calcula un índice medio con aritmética sobre ini y fin.

Sobre el árbol de siete nodos del Tema 3, raíz 50 con hijos 30 y 70, y hojas 20, 40, 60 y 80, buscar 60 comparó 50, después 70, después 60, tres comparaciones. Sobre el arreglo ordenado equivalente con esos mismos siete valores, [20, 30, 40, 50, 60, 70, 80], buscarBinariaIterativa compara el índice 3, valor 50, después el índice 5, valor 70, después el índice 4, valor 60, los mismos tres valores, en el mismo orden, tres comparaciones. No es casualidad, ese árbol quedó perfectamente balanceado porque sus siete valores se insertaron en el orden que produce ese equilibrio, así que su forma coincide exactamente con cómo la búsqueda binaria divide el arreglo. La diferencia real entre las dos estructuras no aparece en cuántas comparaciones hacen sobre datos ya acomodados, aparece en qué le cuesta mantener esa forma cuando los datos cambian, un problema que retoma la tabla de cierre al final de este tema.

TipReto 2. Traza la búsqueda binaria de otro valor

Sobre el mismo arreglo de quince elementos, [3, 8, 14, 22, 29, 35, 41, 48, 55, 63, 70, 77, 84, 91, 98], vas a llamar buscarBinariaIterativa(29). Antes de seguir, calcula a mano el valor de medio en cada paso y decide cuántas comparaciones hacen falta.

NotaSolución del Reto 2

La segunda es correcta. El primer paso es igual para cualquier búsqueda sobre este arreglo, ini=0, fin=14, medio=7, valor 48, mayor que 29, así que fin pasa a 6. El segundo paso calcula medio=(0+6)/2=3, valor 22, menor que 29, así que ini pasa a 4. El tercer paso calcula medio=(4+6)/2=5… espera, hay que revisar: con ini=4 y fin=6, medio=(4+6)/2=5, valor 35, mayor que 29, así que fin pasa a 4. El cuarto paso calcula medio=(4+4)/2=4, valor 29, igual al objetivo, encontrado. La traza correcta hace cuatro comparaciones, no tres, el error más fácil de cometer al trazar a mano es olvidar que la división entera de (4+6)/2 da 5, no redondea hacia donde uno esperaría intuitivamente. Vale la pena repetir esta traza con papel y lápiz antes de seguir, siguiendo exactamente el código, para no arrastrar ese error a la versión recursiva.

La versión recursiva

buscarBinariaIterativa mantiene ini y fin como variables que cambian dentro de un bucle. buscarBinariaRecursiva expresa la misma idea sin ningún bucle, cada llamada recibe un rango [ini, fin] más pequeño que el de la llamada que la originó, hasta llegar a uno de los dos casos base, el rango queda vacío y el valor no está, o el elemento del medio es justo el objetivo.

public int buscarBinariaRecursiva(int objetivo) {
    return buscarBinariaRecursiva(objetivo, 0, datos.length - 1);
}

private int buscarBinariaRecursiva(int objetivo, int ini, int fin) {
    if (ini > fin) {
        return -1; // caso base: el rango quedo vacio, no esta
    }
    int medio = (ini + fin) / 2;
    if (datos[medio] == objetivo) {
        return medio; // caso base: lo encontro
    } else if (datos[medio] < objetivo) {
        return buscarBinariaRecursiva(objetivo, medio + 1, fin);
    } else {
        return buscarBinariaRecursiva(objetivo, ini, medio - 1);
    }
}
def buscar_binaria_recursiva(self, objetivo):
    return self._buscar_binaria_recursiva(objetivo, 0, len(self.datos) - 1)

def _buscar_binaria_recursiva(self, objetivo, ini, fin):
    if ini > fin:
        return -1  # caso base: el rango quedo vacio, no esta
    medio = (ini + fin) // 2
    if self.datos[medio] == objetivo:
        return medio  # caso base: lo encontro
    elif self.datos[medio] < objetivo:
        return self._buscar_binaria_recursiva(objetivo, medio + 1, fin)
    else:
        return self._buscar_binaria_recursiva(objetivo, ini, medio - 1)

El Tema 3 de la Unidad 1 explicó qué guarda cada marco de la pila de llamadas, parámetros, variables locales y dirección de retorno, con factorial y fibonacci como ejemplo. La diferencia que vale la pena notar aquí es que buscarBinariaRecursiva hace como máximo una llamada recursiva por nivel, nunca dos como fibonacci, así que el valor que produce el caso base sube por la pila sin combinarse con nada, cada marco simplemente devuelve lo que le devolvió el marco de abajo. Esa forma de recursión, donde no queda ningún trabajo pendiente después de la llamada recursiva, se conoce como recursión de cola, y es la razón por la que la versión iterativa y la recursiva hacen exactamente el mismo número de comparaciones, cuatro para este ejemplo, la única diferencia real es si ese conteo lo lleva una variable de un bucle o la profundidad de la pila de llamadas.

TipReto 3. Qué guarda cada marco

Sobre la traza de buscarBinariaRecursiva(55, 0, 14) del diagrama de arriba, cuatro marcos hasta el caso base. Antes de seguir, decide qué le pasaría a la profundidad máxima de la pila si el arreglo tuviera un millón de elementos en vez de quince.

NotaSolución del Reto 3

La segunda es correcta. Cada llamada recursiva reduce el rango a la mitad, así que la cantidad de marcos que se apilan antes de llegar al caso base es la cantidad de veces que se puede dividir el tamaño del arreglo entre dos, log2(n). Con n = 1 000 000, log2(1 000 000) es aproximadamente 19,93, así que hacen falta 20 marcos como máximo, no un millón ni una fracción proporcional al tamaño. Esa es la razón práctica por la que la versión recursiva de la búsqueda binaria es segura incluso sobre arreglos enormes, a diferencia del árbol binario de búsqueda degenerado que el Tema 3 de la Unidad 3 mostró estrellándose con RecursionError sobre solo tres mil nodos, aquí la profundidad de la pila crece de forma logarítmica, no lineal, sin importar qué tan grande sea el arreglo.

4 Cuando la intuición falla: búsqueda binaria sobre datos sin ordenar

La búsqueda binaria no verifica en ningún momento que el arreglo esté ordenado, simplemente asume que lo está y calcula medio con esa confianza. Si la asunción es falsa, el algoritmo no lanza ningún error, sigue calculando índices, comparando valores y descartando mitades como si nada estuviera mal, y puede terminar devolviendo que un valor no está, aunque sí esté, en silencio, sin ninguna señal de que algo salió mal.

desordenado = [23, 4, 67, 12, 89, 3, 45, 56, 78, 9]
buscador = Buscador(desordenado)
print(buscador.buscar_binaria_iterativa(12))    # -1, incorrecto: 12 esta en el indice 3
print(buscador.buscar_secuencial(12))           # 3, correcto
>>> desordenado = [23, 4, 67, 12, 89, 3, 45, 56, 78, 9]
>>> buscador = Buscador(desordenado)
>>> buscador.buscar_binaria_iterativa(12)
-1
>>> buscador.buscar_secuencial(12)
3

Sobre [23, 4, 67, 12, 89, 3, 45, 56, 78, 9], el valor 12 está guardado en el índice 3, y buscarSecuencial(12) lo confirma sin ningún problema. Pero buscarBinariaIterativa(12), sobre ese mismo arreglo, calcula primero el medio en el índice 4, valor 89, mayor que 12, así que descarta correctamente la mitad derecha. El segundo paso calcula el medio en el índice 1, valor 4, menor que 12, así que mueve ini a 2, decisión que en un arreglo ordenado sería correcta, pero aquí deja fuera al índice 3, que todavía no se había revisado y que sí contiene el 12. El tercer paso calcula el medio en el índice 2, valor 67, mayor que 12, fin pasa a 1, y con ini en 2 el rango queda vacío, el bucle termina y el método devuelve -1. El resultado es incorrecto, pero llega sin ningún mensaje de error, sin ninguna excepción, exactamente como si el valor de verdad no estuviera. La confianza ciega en el orden es el precio de la velocidad de la búsqueda binaria, y ese precio se cobra en silencio si la condición que la hace correcta, el arreglo ordenado, deja de cumplirse.

TipReto 4. Predice antes de correr el código

Sobre el arreglo sin ordenar [50, 10, 90, 30, 70, 20, 80, 40, 60], vas a llamar buscarBinariaIterativa(20), y 20 sí está en el arreglo, en el índice 5. Antes de seguir, decide si el resultado va a ser correcto.

NotaSolución del Reto 4

La segunda es correcta, y es la más incómoda de las tres, porque no da una regla fija. Sobre un arreglo sin ordenar, la búsqueda binaria puede acertar o fallar según cómo quedaron acomodados los valores respecto a los puntos medios que el algoritmo termina calculando, no hay forma de saberlo sin trazar el caso concreto o sin correr el código. Sobre este arreglo, medio=4 da valor 70, mayor que 20, descarta la derecha, fin pasa a 3. medio=1 da valor 10, menor que 20, ini pasa a 2. medio=2 da valor 90, mayor que 20, fin pasa a 1, y con ini=2 el rango queda vacío, resultado -1, incorrecto otra vez, aunque 20 sí está en el índice 5. La tercera opción tampoco es correcta, el bucle siempre termina porque ini y fin se acercan en cada paso sin importar si los datos están ordenados, lo único que cambia es si la respuesta final es confiable. La lección real de este reto no es memorizar cuándo falla, es entender que sobre datos sin ordenar la búsqueda binaria no es ni siquiera confiablemente incorrecta, a veces acierta por casualidad, y esa inconsistencia es peor que un error consistente porque nadie la detecta a tiempo.

5 Medir la diferencia: secuencial contra binaria en arreglos grandes

La Unidad 1 ya mostró una comparación de tiempo entre las dos estrategias sobre un arreglo grande. Esta medición va un paso más allá y cuenta comparaciones reales, no solo tiempo de reloj, para los mismos tres tamaños de arreglo que usó el Tema 1 de esta unidad para comparar los algoritmos de ordenamiento, sobre dos mil búsquedas aleatorias en cada caso.

n (tamaño del arreglo) Comparaciones promedio, secuencial Comparaciones promedio, binaria log2(n) de referencia
1 000 500,5 8,99 9,97
100 000 48 811,6 15,68 16,61
1 000 000 496 272,6 18,97 19,93

El promedio de comparaciones de la búsqueda secuencial ronda la mitad del tamaño del arreglo en los tres casos, porque en promedio, sobre un objetivo elegido al azar, la mitad de las veces está cerca del principio y la otra mitad cerca del final. El promedio de la búsqueda binaria queda siempre justo por debajo de log2(n), porque no todos los objetivos necesitan el peor caso completo, y crece tan despacio que pasar de mil elementos a un millón, mil veces más datos, solo le suma unas diez comparaciones más. La diferencia de tiempo real medida en el mismo equipo confirma esa distancia, con un millón de elementos la búsqueda secuencial tardó unos 4 828 veces más que la binaria en resolver las mismas dos mil búsquedas. El resultado exacto varía según el equipo donde se ejecute, lo que importa es la dirección y la magnitud, no la cifra al milisegundo.

6 Búsqueda secuencial con índices

La búsqueda binaria paga su velocidad con una condición estricta, el arreglo completo tiene que estar ordenado de principio a fin, y mantener esa condición cuando los datos cambian tiene un costo real, insertar un valor nuevo en la posición que le corresponde obliga a desplazar todos los que quedan después, O(n) por cada inserción. La búsqueda secuencial indexada ofrece un punto intermedio, no exige el orden total de todo el arreglo, solo que los datos estén repartidos en bloques y que exista una tabla auxiliar mucho más pequeña, el índice, con una entrada por bloque que indica el valor más alto que ese bloque contiene.

public void construirIndice(int tamanoBloque) {
    this.tamanoBloque = tamanoBloque;
    this.indice = new ArrayList<>(); // cada entrada: [valorMaximoDelBloque, indiceDeInicio]
    for (int inicio = 0; inicio < datos.length; inicio += tamanoBloque) {
        int fin = Math.min(inicio + tamanoBloque, datos.length) - 1;
        indice.add(new int[]{datos[fin], inicio});
    }
}

public int buscarIndexada(int objetivo) {
    int inicioBloque = -1;
    for (int[] entrada : indice) {
        if (objetivo <= entrada[0]) {
            inicioBloque = entrada[1];
            break;
        }
    }
    if (inicioBloque == -1) {
        return -1; // objetivo mayor que el maximo del ultimo bloque
    }
    int finBloque = Math.min(inicioBloque + tamanoBloque, datos.length);
    for (int i = inicioBloque; i < finBloque; i++) {
        if (datos[i] == objetivo) {
            return i;
        }
    }
    return -1;
}
def construir_indice(self, tamano_bloque):
    self.tamano_bloque = tamano_bloque
    self.indice = []  # cada entrada: (valor_maximo_del_bloque, indice_de_inicio)
    for inicio in range(0, len(self.datos), tamano_bloque):
        fin = min(inicio + tamano_bloque, len(self.datos)) - 1
        self.indice.append((self.datos[fin], inicio))

def buscar_indexada(self, objetivo):
    inicio_bloque = None
    for valor_maximo, inicio in self.indice:
        if objetivo <= valor_maximo:
            inicio_bloque = inicio
            break
    if inicio_bloque is None:
        return -1  # objetivo mayor que el maximo del ultimo bloque
    fin_bloque = min(inicio_bloque + self.tamano_bloque, len(self.datos))
    for i in range(inicio_bloque, fin_bloque):
        if self.datos[i] == objetivo:
            return i
    return -1

Sobre el arreglo de veinte elementos [2, 5, 9, 13, 18, 21, 24, 28, 33, 37, 40, 44, 49, 53, 58, 61, 65, 70, 74, 79], dividido en cuatro bloques de cinco, construirIndice(5) arma la tabla [(18, 0), (37, 5), (58, 10), (79, 15)]. Buscar 53 recorre el índice, tres comparaciones hasta encontrar que 53 es menor o igual a 58, y después recorre solo el bloque que empieza en la posición 10, otras cuatro comparaciones hasta encontrarlo en la posición 13, siete en total. La búsqueda secuencial pura sobre el mismo arreglo habría necesitado catorce comparaciones para llegar a esa misma posición. La ganancia crece con el tamaño de los datos, para un arreglo de un millón de elementos con un tamaño de bloque cercano a mil, la raíz cuadrada de un millón, el peor caso de la búsqueda indexada ronda las dos mil comparaciones, mil para recorrer el índice completo más mil para recorrer un bloque completo, frente al millón de comparaciones del peor caso secuencial y las apenas veinte de la búsqueda binaria.

Esa cota intermedia, más lenta que la binaria pero muchísimo más rápida que la secuencial, es justo lo que hace atractiva a esta estrategia cuando los datos viven en disco en vez de en memoria, el caso real de una base de datos o de un sistema de archivos. Leer un bloque del disco cuesta mucho más que comparar dos números en memoria, así que minimizar cuántos bloques hay que tocar importa más que minimizar cuántas comparaciones exactas se hacen, y mantener pequeños bloques ordenados por dentro, con solo el índice apuntando a sus límites, cuesta mucho menos que reordenar un archivo entero cada vez que llega un dato nuevo, insertar solo desplaza dentro del bloque que le corresponde, o como mucho reparte ese bloque en dos cuando se llena, nunca todo el archivo completo.

TipReto 5. Cuenta las comparaciones de otra búsqueda

Sobre el mismo arreglo indexado, [2, 5, 9, 13, 18, 21, 24, 28, 33, 37, 40, 44, 49, 53, 58, 61, 65, 70, 74, 79] con bloques de cinco y el índice [(18, 0), (37, 5), (58, 10), (79, 15)], vas a llamar buscarIndexada(6), y 6 no está en el arreglo. Antes de seguir, decide cuántas comparaciones totales hace, sumando las del índice y las del bloque.

NotaSolución del Reto 5

La segunda es correcta. El recorrido del índice compara 6 contra la primera entrada, 18, y como 6 es menor o igual a 18, se detiene ahí mismo, una sola comparación, y elige el bloque que empieza en la posición 0. Ese bloque tiene los valores [2, 5, 9, 13, 18], y como 6 no está entre ellos, la búsqueda secuencial dentro del bloque recorre las cinco posiciones completas sin encontrarlo. El total es una comparación del índice más cinco del bloque, seis en total, muy por debajo de las veinte que habría costado revisar el arreglo completo con búsqueda secuencial pura, aunque el valor buscado no exista en ninguna parte.

7 Los tres algoritmos, uno al lado del otro

Algoritmo Requiere orden Complejidad Costo de mantener el orden al insertar
Búsqueda secuencial No O(n) Ninguno, se agrega al final
Búsqueda binaria Si, total, sobre todo el arreglo O(log n) O(n), desplaza para mantener el orden completo
Búsqueda secuencial indexada Solo dentro de cada bloque O(n/b + b), optima cerca de O(raiz de n) O(b), desplaza solo dentro de un bloque

Los tres algoritmos resuelven exactamente el mismo problema, encontrar la posición de un valor dentro de una colección, con un compromiso distinto entre qué tanto exigen sobre cómo están acomodados los datos y qué tan rápido responden. La secuencial no exige nada y por eso es la más lenta. La binaria exige el máximo, orden total, y a cambio da la respuesta más rápida de las tres. La indexada negocia un punto intermedio, exige orden solo dentro de bloques pequeños, mucho más barato de mantener que un arreglo completo, y a cambio entrega un tiempo de búsqueda que queda entre las otras dos.

TipReto 6. Elige la estrategia según el escenario

Tienes tres escenarios. El primero es un registro de asistencia que se actualiza en el orden en que llegan los estudiantes y se consulta solo una vez al final del día. El segundo es un diccionario de sinónimos que casi nunca cambia y se consulta miles de veces al día. El tercero es un archivo de un banco con millones de registros de clientes, guardado en disco, con nuevas cuentas abriéndose todo el tiempo. Antes de seguir, decide qué estrategia conviene para cada uno.

NotaSolución del Reto 6

La primera es correcta. El registro de asistencia se consulta una sola vez y cambia todo el día, ordenarlo para una única búsqueda no compensa el costo de mantenerlo ordenado, así que la secuencial es la opción razonable. El diccionario de sinónimos casi no cambia y se consulta muchas veces, exactamente el escenario donde vale la pena pagar una vez el costo de ordenarlo y aprovechar O(log n) en cada una de las miles de consultas, así que la binaria es la mejor opción. El archivo del banco combina un volumen enorme, que descarta la secuencial pura, con actualizaciones frecuentes, que descartan mantener un arreglo completo perfectamente ordenado en disco por el costo de desplazar millones de registros en cada apertura de cuenta, así que la indexada, con bloques pequeños que se reordenan localmente, es la que de verdad se usa en un sistema así.

8 De arreglo a árbol balanceado: el mapa completo de búsqueda de la asignatura

Este tema cierra la comparación con las dos estructuras dinámicas de la Unidad 3 que también resuelven el problema de buscar un dato, el árbol binario de búsqueda y el árbol AVL. Las cuatro filas de esta tabla son las cuatro formas de buscar que viste en el curso completo.

Estructura Complejidad de búsqueda Se mantiene ordenada sola Cuándo conviene
Arreglo con búsqueda secuencial O(n) No aplica Datos pequeños, sin orden, pocas búsquedas
Arreglo ordenado con búsqueda binaria O(log n) No, hay que reordenar a mano Datos que casi no cambian, muchas búsquedas, todo cabe en memoria
Arreglo con búsqueda secuencial indexada Entre O(log n) y O(n), cercana a O(raiz de n) con bloque optimo Solo dentro de cada bloque Volúmenes grandes en disco, con inserciones frecuentes, bases de datos y sistemas de archivos
Árbol binario de búsqueda (Unidad 3, Tema 3) O(log n) en promedio, O(n) en el peor caso Si, automaticamente, pero sin garantia de forma Datos dinámicos donde el orden de llegada es razonablemente variado
Árbol AVL (Unidad 3, Tema 4) O(log n) garantizado siempre Si, con rotaciones que fuerzan el equilibrio Datos dinámicos donde no se puede confiar en el orden de llegada y se necesita la garantía

El arreglo ordenado y el árbol AVL llegan al mismo O(log n), pero por caminos distintos, el arreglo lo logra porque su memoria es contigua y calcular el medio es aritmética directa, el AVL lo logra porque se reorganiza solo con cada inserción para que su altura nunca se aleje de log2(n), el mismo invariante que el Tema 3 de la Unidad 3 mostró que un árbol binario de búsqueda ordinario no garantiza. Elegir entre las cinco filas de esta tabla no depende de cuál es “la mejor” en abstracto, depende de tres preguntas concretas sobre los datos reales del problema, si cambian con frecuencia, si el volumen obliga a pensar en disco en vez de en memoria, y si se puede pagar el costo de mantenerlos ordenados a cambio de buscar más rápido después.
