Unidad Unidad 3. Estructuras dinámicas
Tema Tema 4. Árboles 2-3 y árboles AVL

El Tema 3 cerró con una medición que no deja lugar a dudas, el mismo árbol binario de búsqueda que ordena mientras almacena se degrada a una cadena de 7999 enlaces con solo insertar ocho mil valores ya ordenados, mientras que esos mismos ocho mil valores insertados en un orden distinto dejan la altura en 35. El contenido final del árbol es idéntico en los dos casos, lo que cambia por completo es la forma, y esa forma la decide el orden de llegada de los datos, algo que ningún programa controla. Este tema resuelve ese problema desde dos ángulos distintos. El árbol AVL sigue siendo un árbol binario, con un nodo y dos hijos como el del Tema 3, pero después de cada inserción revisa si algún nodo quedó demasiado inclinado hacia un lado y lo corrige con una rotación local. El árbol 2-3 cambia la pieza misma, un nodo ya no guarda un solo valor sino uno o dos, y esa holgura extra le permite absorber una inserción sin necesitar bajar un nivel más, así que nunca llega a desbalancearse porque su forma no lo permite desde el diseño.

1 Árboles AVL: rebalancear después de cada inserción

Un árbol AVL, llamado así por los apellidos de sus inventores, Georgy Adelson-Velsky y Evgenii Landis, es un árbol binario de búsqueda con una regla adicional que se cumple en cada nodo, no solo en la raíz, la altura de su subárbol derecho y la de su subárbol izquierdo nunca difieren en más de uno. Esa diferencia tiene nombre propio, el factor de balanceo de un nodo, que se calcula como la altura del subárbol derecho menos la altura del subárbol izquierdo. Un factor de balanceo fuera del conjunto {-1, 0, 1} rompe el invariante AVL, y es exactamente lo que dispara una rotación.

Esta guía usa la misma convención que las implementaciones de referencia, la altura de un subárbol vacío es -1 y la de una hoja es 0, así que el factor de balanceo de una hoja siempre es 0, sin importar en qué árbol esté.

El árbol de siete nodos que construiste en el Tema 3 ya cumple el invariante AVL sin que hiciera falta ninguna rotación, el factor de cada nodo es 0 porque las dos mitades quedaron perfectamente parejas. Eso no es el resultado garantizado de cualquier inserción, es la excepción que confirma que un ABB puede quedar balanceado por casualidad. Lo que el AVL agrega no es esa casualidad, es la garantía de que se mantenga así pase lo que pase.

La clase NodoAVL

Guardar el factor de balanceo en cada consulta recorriendo el árbol completo sería demasiado costoso, así que NodoAVL agrega un campo más frente al NodoArbol del Tema 3, altura, que cada nodo mantiene actualizado sobre la marcha después de cada inserción. Con la altura de los dos hijos a la mano, calcular el factor de balanceo de un nodo es una sola resta.

public class NodoAVL {
    int dato;
    NodoAVL izquierdo;
    NodoAVL derecho;
    int altura;

    public NodoAVL(int dato) {
        this.dato = dato;
        this.izquierdo = null;
        this.derecho = null;
        this.altura = 0;
    }
}

public class ArbolAVL {
    private NodoAVL raiz;

    private int altura(NodoAVL nodo) {
        return nodo == null ? -1 : nodo.altura;
    }

    private int factor(NodoAVL nodo) {
        return altura(nodo.derecho) - altura(nodo.izquierdo);
    }

    private void actualizarAltura(NodoAVL nodo) {
        nodo.altura = 1 + Math.max(altura(nodo.izquierdo), altura(nodo.derecho));
    }
}
class NodoAVL:
    def __init__(self, dato):
        self.dato = dato
        self.izquierdo = None
        self.derecho = None
        self.altura = 0


class ArbolAVL:
    def __init__(self):
        self.raiz = None

    def _altura(self, nodo):
        return nodo.altura if nodo is not None else -1

    def _factor(self, nodo):
        return self._altura(nodo.derecho) - self._altura(nodo.izquierdo)

    def _actualizar_altura(self, nodo):
        nodo.altura = 1 + max(self._altura(nodo.izquierdo), self._altura(nodo.derecho))

Las cuatro rotaciones

Una rotación reorganiza tres nodos y sus subárboles sin tocar el invariante de orden del ABB, ningún valor cambia de lugar respecto a sus vecinos en el recorrido inorden, lo único que cambia es cuál de los tres queda arriba. Hay cuatro formas en que un nodo puede quedar desbalanceado según de qué lado venga el exceso de altura, y cada una tiene su propia rotación para corregirla.

Caso izquierda-izquierda (LL)

El exceso de altura viene del hijo izquierdo del hijo izquierdo. La corrección es una sola rotación a la derecha sobre el nodo desbalanceado, que promueve a su hijo izquierdo al lugar que él ocupaba.

private NodoAVL rotarDerecha(NodoAVL nodo) {
    NodoAVL nuevaRaiz = nodo.izquierdo;
    nodo.izquierdo = nuevaRaiz.derecho;
    nuevaRaiz.derecho = nodo;
    actualizarAltura(nodo);
    actualizarAltura(nuevaRaiz);
    return nuevaRaiz;
}
def _rotar_derecha(self, nodo):
    nueva_raiz = nodo.izquierdo
    nodo.izquierdo = nueva_raiz.derecho
    nueva_raiz.derecho = nodo
    self._actualizar_altura(nodo)
    self._actualizar_altura(nueva_raiz)
    return nueva_raiz

nodo.izquierdo sube a ocupar el lugar de nodo, nodo pasa a ser el hijo derecho de quien antes era su propio hijo izquierdo, y el subárbol derecho de la nueva raíz, que antes colgaba de ella, se reubica como hijo izquierdo del nodo que bajó. Ningún valor cambió de posición relativa en el recorrido inorden, solo cambió qué nodo queda arriba.

Caso derecha-derecha (RR)

El caso simétrico, el exceso de altura viene del hijo derecho del hijo derecho, y la corrección es una rotación a la izquierda.

private NodoAVL rotarIzquierda(NodoAVL nodo) {
    NodoAVL nuevaRaiz = nodo.derecho;
    nodo.derecho = nuevaRaiz.izquierdo;
    nuevaRaiz.izquierdo = nodo;
    actualizarAltura(nodo);
    actualizarAltura(nuevaRaiz);
    return nuevaRaiz;
}
def _rotar_izquierda(self, nodo):
    nueva_raiz = nodo.derecho
    nodo.derecho = nueva_raiz.izquierdo
    nueva_raiz.izquierdo = nodo
    self._actualizar_altura(nodo)
    self._actualizar_altura(nueva_raiz)
    return nueva_raiz

Caso izquierda-derecha (LR)

Aquí el exceso de altura no viene en línea recta, viene del hijo derecho del hijo izquierdo, un zigzag. Una sola rotación a la derecha sobre el nodo desbalanceado no lo arregla, más adelante esta guía muestra exactamente por qué. La corrección necesita dos rotaciones, primero una rotación a la izquierda sobre el hijo izquierdo, que convierte el zigzag en una línea recta LL, y después la rotación a la derecha ya conocida sobre el nodo original.

Caso derecha-izquierda (RL)

El caso simétrico del anterior, el exceso de altura viene del hijo izquierdo del hijo derecho. La corrección es la misma idea reflejada, primero una rotación a la derecha sobre el hijo derecho, y después una rotación a la izquierda sobre el nodo original.

Las cuatro rotaciones, junto con la decisión de cuál aplicar, se resumen en un solo método que revisa el factor de balanceo del nodo y el de su hijo pesado para distinguir el caso simple del caso zigzag.

private NodoAVL balancear(NodoAVL nodo) {
    actualizarAltura(nodo);
    int factor = factor(nodo);
    if (factor < -1) {
        if (factor(nodo.izquierdo) > 0) {
            nodo.izquierdo = rotarIzquierda(nodo.izquierdo); // LR: primero deshace el zigzag
        }
        return rotarDerecha(nodo);
    }
    if (factor > 1) {
        if (factor(nodo.derecho) < 0) {
            nodo.derecho = rotarDerecha(nodo.derecho); // RL: primero deshace el zigzag
        }
        return rotarIzquierda(nodo);
    }
    return nodo; // ya esta dentro de {-1, 0, 1}, nada que hacer
}
def _balancear(self, nodo):
    self._actualizar_altura(nodo)
    factor = self._factor(nodo)
    if factor < -1:
        if self._factor(nodo.izquierdo) > 0:
            nodo.izquierdo = self._rotar_izquierda(nodo.izquierdo)  # LR: deshace el zigzag primero
        return self._rotar_derecha(nodo)
    if factor > 1:
        if self._factor(nodo.derecho) < 0:
            nodo.derecho = self._rotar_derecha(nodo.derecho)  # RL: deshace el zigzag primero
        return self._rotar_izquierda(nodo)
    return nodo  # ya esta dentro de {-1, 0, 1}, nada que hacer

La condición factor(nodo.izquierdo) > 0 es la que distingue LL de LR, si el hijo izquierdo está a su vez inclinado hacia la derecha es un zigzag y hace falta la rotación extra antes de la principal. La condición simétrica factor(nodo.derecho) < 0 distingue RR de RL de la misma forma.

Cuando se aplica la rotación equivocada

Diagnosticar mal cuál de los cuatro casos aplica es el error más común al implementar un AVL, así que vale la pena ver qué pasa cuando se aplica la rotación simple donde hacía falta la doble. Retoma el caso izquierda-derecha de arriba, 30 con hijo izquierdo 10 y el hijo derecho de 10 es 20, factor de 30 igual a -2. Si en vez de reconocer el zigzag se aplica directamente rotarDerecha(30), tratándolo como si fuera un caso LL simple, el resultado no arregla el árbol.

rotarDerecha(30) promueve a 10 al lugar de 30, y el hijo derecho de 10, que era 20, se reubica como hijo izquierdo de 30, exactamente lo que el código de la rotación simple hace siempre, sin mirar si el caso era zigzag. El resultado deja a 10 como raíz del subárbol, con 30 como su único hijo, a la derecha, y 20 colgando del propio 30. La altura de 30 es 1 y la de su hijo izquierdo, que no existe, es -1, así que el factor de 10 termina en 2, todavía fuera del rango permitido. La rotación simple no arregló el árbol, lo dejó desbalanceado hacia el otro lado. La razón de fondo es que una sola rotación solo puede enderezar una línea recta, y un caso zigzag necesita primero convertirse en línea recta con la rotación del hijo antes de que la rotación del nodo principal tenga algo que enderezar.

TipReto 1. El caso derecha-derecha, en el árbol de ejemplo

Sobre el árbol de siete nodos de esta guía, raíz 50, con 30 y 70 como hijos, y 20, 40, 60 y 80 como hojas, vas a insertar 85 y después 90. Antes de seguir, decide en qué nodo se dispara una rotación y cuál de los cuatro casos es.

NotaSolución del Reto 1

La segunda es correcta. Insertar 85 baja por 50, 70 y 80, y cuelga como hijo derecho de 80, una hoja sin hijos hasta ese momento, así que no rompe nada todavía, el factor de 80 queda en 1. Insertar 90 baja por el mismo camino, 50, 70, 80, y ahora sigue hacia 85, donde cuelga como su hijo derecho. Con ese segundo nodo nuevo, 80 pasa a tener altura -1 a la izquierda, porque no tiene hijo izquierdo, y altura 1 a la derecha, por la cadena 85 a 90, así que su factor queda en 2, fuera de rango. El exceso de altura viene del hijo derecho del hijo derecho, exactamente el caso derecha-derecha, y se corrige con rotarIzquierda(80), que deja a 85 como nueva raíz de ese subárbol, con 80 a la izquierda y 90 a la derecha. El resto del árbol, 50, 30, 70 y las hojas 20, 40 y 60, no cambia nada.

Insertar con rebalanceo

Insertar en un AVL empieza exactamente igual que insertar en el ABB del Tema 3, bajar comparando hasta encontrar el hueco vacío y colgar ahí el nodo nuevo. La diferencia está en el camino de vuelta, cada llamada recursiva, al regresar, pasa por balancear antes de devolver el resultado, así que el árbol se corrige de abajo hacia arriba, empezando por el nodo más cercano al que se insertó y subiendo hasta la raíz si hace falta.

public void insertar(int dato) {
    raiz = insertar(raiz, dato);
}

private NodoAVL insertar(NodoAVL nodo, int dato) {
    if (nodo == null) {
        return new NodoAVL(dato); // caso base: aqui va el nodo nuevo
    }
    if (dato < nodo.dato) {
        nodo.izquierdo = insertar(nodo.izquierdo, dato);
    } else if (dato > nodo.dato) {
        nodo.derecho = insertar(nodo.derecho, dato);
    } else {
        return nodo; // valor repetido, no se hace nada
    }
    return balancear(nodo); // en la vuelta de cada nivel, corrige si hace falta
}

public boolean buscar(int dato) {
    return buscar(raiz, dato);
}

private boolean buscar(NodoAVL nodo, int dato) {
    if (nodo == null) {
        return false;
    }
    if (dato == nodo.dato) {
        return true;
    }
    return dato < nodo.dato ? buscar(nodo.izquierdo, dato) : buscar(nodo.derecho, dato);
}

public int altura() {
    return altura(raiz);
}
def insertar(self, dato):
    self.raiz = self._insertar(self.raiz, dato)

def _insertar(self, nodo, dato):
    if nodo is None:
        return NodoAVL(dato)  # caso base: aqui va el nodo nuevo
    if dato < nodo.dato:
        nodo.izquierdo = self._insertar(nodo.izquierdo, dato)
    elif dato > nodo.dato:
        nodo.derecho = self._insertar(nodo.derecho, dato)
    else:
        return nodo  # valor repetido, no se hace nada
    return self._balancear(nodo)  # en la vuelta de cada nivel, corrige si hace falta

def buscar(self, dato):
    return self._buscar(self.raiz, dato)

def _buscar(self, nodo, dato):
    if nodo is None:
        return False
    if dato == nodo.dato:
        return True
    return self._buscar(nodo.izquierdo, dato) if dato < nodo.dato else self._buscar(nodo.derecho, dato)

def altura(self):
    return self._altura(self.raiz)

Fíjate que insertar tiene exactamente la misma forma que en el Tema 3, un caso base para el hueco vacío y un caso recursivo que reasigna nodo.izquierdo o nodo.derecho. Lo único que cambia es una línea, return balancear(nodo) en vez de return nodo, porque cada nivel que la recursión atraviesa de vuelta hacia la raíz es una oportunidad para que ese nivel específico haya quedado desbalanceado por la inserción, y balancear revisa y corrige antes de seguir subiendo. eliminar en un AVL sigue la misma idea aplicada al camino de eliminación del Tema 3, cada nivel llama a balancear en la vuelta, esta guía no repite esa implementación completa porque la lógica de rebalanceo ya quedó cubierta aquí.

Por qué la altura queda garantizada en O(log n)

La demostración formal de por qué un AVL nunca supera una altura de aproximadamente 1.44 * log2(n) sale de acotar cuántos nodos hace falta como mínimo para construir un AVL de una altura dada, un argumento que Adelson-Velsky y Landis publicaron junto con la estructura y que Weiss desarrolla en el capítulo de árboles balanceados. Esta guía no repite esa demostración completa, en cambio la comprueba igual que el Tema 3 comprobó el caso degenerado, insertando en un AVL el mismo conjunto de datos que degeneró al ABB simple.

import random
import time
import math

N = 8000
datos_ordenados = list(range(N))

arbol_avl = ArbolAVL()
for x in datos_ordenados:
    arbol_avl.insertar(x)

print(f"N = {N} valores insertados, ya ordenados")
print(f"altura del AVL: {arbol_avl.altura()}")
print(f"log2(N) de referencia: {math.log2(N):.1f}")
print(f"altura del ABB degenerado con el mismo N (Tema 3): {N - 1}")

random.seed(42)
busquedas = random.sample(range(N), 3000)

inicio = time.perf_counter()
for x in busquedas:
    arbol_avl.buscar(x)
tiempo_avl = time.perf_counter() - inicio

print(f"tiempo de busqueda en AVL (3000 busquedas): {tiempo_avl:.4f} s")

Esta es la salida real de correr ese script:

N = 8000 valores insertados, ya ordenados
altura del AVL: 12
log2(N) de referencia: 13.0
altura del ABB degenerado con el mismo N (Tema 3): 7999
tiempo de busqueda en AVL (3000 busquedas): 0.0030 s

El resultado exacto varía según el equipo donde se ejecute, lo que importa es la magnitud. Los mismos ocho mil valores que en el Tema 3 produjeron un ABB de altura 7999 producen aquí un AVL de altura 12, por debajo incluso del log2(8000) de referencia, 13.0, gracias a que las rotaciones evitan la degeneración sin importar el orden de llegada. Es más, esta altura de 12 queda por debajo de los 35 que el Tema 3 midió al insertar esos mismos valores en orden aleatorio sobre un ABB simple, la garantía del AVL no es solo mejor que el peor caso del ABB, es mejor que su caso promedio. El tiempo de búsqueda, 0.0030 segundos para tres mil consultas, es del mismo orden de magnitud que el tiempo medido en el Tema 3 sobre el ABB con inserción aleatoria, y muy por debajo de los 0.4898 segundos que costó buscar en el árbol degenerado. Además, insertar y buscar aquí siguen usando la versión recursiva sin ningún problema, porque la altura nunca se acerca al límite de recursión de Python, a diferencia del RecursionError que el Tema 3 encontró al insertar en orden ascendente sobre un ABB simple.

2 Árboles 2-3: crecer sin desbalancearse nunca

Un árbol AVL sigue siendo binario y corrige el desbalance después de que aparece. Un árbol 2-3 ataca el problema desde otro ángulo, cambia la forma del nodo para que la inserción nunca produzca un desbalance que corregir. La pieza básica ya no es “un valor con hasta dos hijos”, es “uno o dos valores con hasta tres hijos”.

Nodo de 2 y nodo de 3

Un nodo de 2 guarda un único valor y tiene hasta dos hijos, uno con todo lo menor que ese valor y otro con todo lo mayor, exactamente como un nodo del ABB del Tema 3. Un nodo de 3 guarda dos valores, ordenados, y tiene hasta tres hijos, uno con todo lo menor que el primer valor, otro con todo lo que queda entre los dos valores, y un tercero con todo lo mayor que el segundo valor.

Buscar un valor en un árbol 2-3 se parece a buscar en el ABB del Tema 3, en cada nodo comparas el valor buscado contra las claves que el nodo guarda, una o dos, y bajas por el hijo que corresponde según en qué rango cae. La diferencia con el ABB no está en cómo se busca, está en cómo se inserta.

El invariante: todas las hojas a la misma profundidad

Un árbol 2-3 mantiene una regla que ningún ABB ni AVL garantiza por diseño, todas sus hojas están exactamente a la misma profundidad, sin excepción. No es que queden “razonablemente parejas” como en un AVL, es que no existe forma de que una quede más profunda que otra mientras el árbol respete cómo se construye. La razón de esa garantía está en cómo funciona la inserción, que el resto de esta sección explica.

Insertar: división y propagación hacia arriba

Insertar en un árbol 2-3 baja por el árbol comparando contra las claves de cada nodo, igual que buscar, hasta llegar a una hoja. Ahí el valor nuevo se agrega a las claves de esa hoja, ordenado junto a las que ya tenía. Si la hoja tenía una clave, ahora tiene dos, cabe sin problema en un nodo de 3. Si la hoja ya tenía dos claves, ahora tendría tres, y un nodo de 3 no admite tres claves, así que el nodo se divide, la clave del medio sube al padre, y las otras dos quedan como dos nodos nuevos, cada uno con una sola clave e hijos de la mitad correspondiente.

Si el nodo que recibe la clave promovida es a su vez un nodo de 3, ese nodo también se desborda a tres claves, y el mismo proceso se repite un nivel más arriba, la clave del medio sube y el nodo se divide en dos. Esa propagación puede llegar hasta la raíz, y cuando la raíz misma se divide, aparece una raíz nueva con una sola clave, la que subió desde la raíz anterior, y sus dos mitades como hijos. Ese es el único momento en que un árbol 2-3 crece en altura, y crece desde arriba, no desde abajo como una lista o un ABB, así que el crecimiento afecta a todas las hojas por igual, ninguna se queda más profunda que las demás.

public class Nodo23 {
    java.util.List<Integer> claves = new java.util.ArrayList<>();
    java.util.List<Nodo23> hijos = new java.util.ArrayList<>();
    boolean hoja = true;
}

public class Arbol23 {
    private Nodo23 raiz;

    private static class Division {
        int claveSubida;
        Nodo23 izquierdo;
        Nodo23 derecho;

        Division(int claveSubida, Nodo23 izquierdo, Nodo23 derecho) {
            this.claveSubida = claveSubida;
            this.izquierdo = izquierdo;
            this.derecho = derecho;
        }
    }

    public void insertar(int valor) {
        if (raiz == null) {
            raiz = new Nodo23();
            raiz.claves.add(valor);
            return;
        }
        Division division = insertar(raiz, valor);
        if (division != null) {
            Nodo23 nuevaRaiz = new Nodo23();
            nuevaRaiz.hoja = false;
            nuevaRaiz.claves.add(division.claveSubida);
            nuevaRaiz.hijos.add(division.izquierdo);
            nuevaRaiz.hijos.add(division.derecho);
            raiz = nuevaRaiz;
        }
    }

    private Division insertar(Nodo23 nodo, int valor) {
        int pos = 0;
        while (pos < nodo.claves.size() && nodo.claves.get(pos) < valor) {
            pos++;
        }
        if (nodo.hoja) {
            nodo.claves.add(pos, valor);
            return nodo.claves.size() <= 2 ? null : dividirHoja(nodo);
        }
        Division division = insertar(nodo.hijos.get(pos), valor);
        if (division == null) {
            return null;
        }
        nodo.claves.add(pos, division.claveSubida);
        nodo.hijos.set(pos, division.izquierdo);
        nodo.hijos.add(pos + 1, division.derecho);
        return nodo.claves.size() <= 2 ? null : dividirInterno(nodo);
    }

    private Division dividirHoja(Nodo23 nodo) {
        Nodo23 izquierdo = new Nodo23();
        izquierdo.claves.add(nodo.claves.get(0));
        Nodo23 derecho = new Nodo23();
        derecho.claves.add(nodo.claves.get(2));
        return new Division(nodo.claves.get(1), izquierdo, derecho);
    }

    private Division dividirInterno(Nodo23 nodo) {
        Nodo23 izquierdo = new Nodo23();
        izquierdo.hoja = false;
        izquierdo.claves.add(nodo.claves.get(0));
        izquierdo.hijos.add(nodo.hijos.get(0));
        izquierdo.hijos.add(nodo.hijos.get(1));
        Nodo23 derecho = new Nodo23();
        derecho.hoja = false;
        derecho.claves.add(nodo.claves.get(2));
        derecho.hijos.add(nodo.hijos.get(2));
        derecho.hijos.add(nodo.hijos.get(3));
        return new Division(nodo.claves.get(1), izquierdo, derecho);
    }
}
class Nodo23:
    def __init__(self):
        self.claves = []   # una o dos, ordenadas
        self.hijos = []    # cero, o len(claves) + 1
        self.hoja = True


class Arbol23:
    def __init__(self):
        self.raiz = None

    def insertar(self, valor):
        if self.raiz is None:
            nodo = Nodo23()
            nodo.claves = [valor]
            self.raiz = nodo
            return
        resultado = self._insertar(self.raiz, valor)
        if resultado is not None:
            clave_subida, izquierdo, derecho = resultado
            nueva_raiz = Nodo23()
            nueva_raiz.claves = [clave_subida]
            nueva_raiz.hijos = [izquierdo, derecho]
            nueva_raiz.hoja = False
            self.raiz = nueva_raiz

    def _insertar(self, nodo, valor):
        pos = 0
        while pos < len(nodo.claves) and nodo.claves[pos] < valor:
            pos += 1
        if nodo.hoja:
            nodo.claves.insert(pos, valor)
            return None if len(nodo.claves) <= 2 else self._dividir_hoja(nodo)
        resultado = self._insertar(nodo.hijos[pos], valor)
        if resultado is None:
            return None
        clave_subida, izquierdo, derecho = resultado
        nodo.claves.insert(pos, clave_subida)
        nodo.hijos[pos] = izquierdo
        nodo.hijos.insert(pos + 1, derecho)
        return None if len(nodo.claves) <= 2 else self._dividir_interno(nodo)

    def _dividir_hoja(self, nodo):
        izquierdo = Nodo23()
        izquierdo.claves = [nodo.claves[0]]
        derecho = Nodo23()
        derecho.claves = [nodo.claves[2]]
        return (nodo.claves[1], izquierdo, derecho)

    def _dividir_interno(self, nodo):
        izquierdo = Nodo23()
        izquierdo.hoja = False
        izquierdo.claves = [nodo.claves[0]]
        izquierdo.hijos = nodo.hijos[0:2]
        derecho = Nodo23()
        derecho.hoja = False
        derecho.claves = [nodo.claves[2]]
        derecho.hijos = nodo.hijos[2:4]
        return (nodo.claves[1], izquierdo, derecho)

_insertar devuelve None cuando el nodo no se desbordó, y una tupla con la clave que subió y las dos mitades cuando sí, exactamente el mismo dato que la versión Java devuelve como un objeto Division. Quien recibe esa tupla, ya sea insertar en la raíz o el nivel de arriba dentro de _insertar, decide si la incorpora sin desbordarse o si tiene que dividirse a su vez, la propagación hacia arriba es esa cadena de decisiones repetidas.

TipReto 2. Insertar sin dividir

Sobre el árbol 2-3 con raíz [20, 40] e hijos [10], [30], [50], el resultado de insertar 10, 20, 30, 40 y 50 en ese orden, vas a insertar 25. Antes de seguir, decide en qué hoja cae y si dispara alguna división.

NotaSolución del Reto 2

La primera es correcta. La raíz tiene las claves 20 y 40, así que 25 cae en el rango intermedio, entre 20 y 40, que corresponde al segundo hijo, la hoja [30]. Insertar 25 ahí la deja con dos claves, [25, 30], y un nodo de 3 admite dos claves sin ningún problema, así que no hace falta dividir nada. La inserción solo dispara una división cuando la hoja de destino ya tenía dos claves antes de insertar la nueva, este caso no llega a eso.

El árbol 2-3 sobre el mismo caso que degeneró al ABB

El Tema 3 insertó 10, 20, 30, 40 y 50 ya ordenados en un ABB simple y obtuvo una cadena de altura 4, el peor caso posible. Insertar esos mismos cinco valores, en ese mismo orden ascendente, en un árbol 2-3 produce el resultado que el diagrama de la división de arriba ya mostró en su tercer paso, una raíz [20] con dos hijas, [10] y [30], sin necesitar insertar más valores para volver a dividirse hasta llegar a 40 y 50. Si sigues insertando en el mismo orden hasta llegar a 70, la secuencia completa 10, 20, 30, 40, 50, 60, 70 produce este árbol.

Todas las hojas quedan a profundidad 2, sin excepción, y ningún nodo tuvo que reorganizarse con una rotación, cada nodo se creó ya en su posición final o se dividió una sola vez. En este resultado concreto cada nodo terminó siendo un nodo de 2, con una sola clave, una coincidencia del orden exacto en que se insertaron estos siete valores, no una regla general, el diagrama de la división de arriba ya mostró un nodo de 3 con dos claves en un paso intermedio de la misma construcción.

Por qué el balanceo es perfecto por construcción

Un ABB, incluso un AVL, cuelga cada nodo nuevo justo debajo de una hoja existente, así que la profundidad de esa hoja concreta crece uno mientras el resto del árbol se queda igual, y solo las rotaciones del AVL evitan que esa diferencia se acumule sin control. Un árbol 2-3 nunca cuelga un nodo nuevo debajo de una hoja, un valor nuevo siempre se incorpora a las claves de una hoja que ya existe. La única forma en que el árbol gana profundidad es que una división se propague hasta la raíz y la raíz misma se divida, y cuando eso pasa, la raíz nueva queda por encima de todo el árbol anterior, así que la profundidad de cada hoja existente aumenta en uno, todas a la vez, en el mismo instante. No hay ningún paso del algoritmo que pueda dejar una hoja más profunda que otra, la construcción misma lo impide, a diferencia del AVL, que sí permite un desbalance temporal y lo corrige después con una rotación.

3 AVL y 2-3, comparados

Los dos árboles de este tema resuelven el mismo problema, que insertar datos en cualquier orden nunca deje una altura mayor que un múltiplo pequeño de log2(n), pero llegan ahí por caminos distintos. El AVL conserva la forma binaria del Tema 3 y corrige el desbalance después de que aparece, con una rotación local que dura un tiempo constante por nivel. El árbol 2-3 cambia la forma del nodo para que el desbalance nunca llegue a existir, absorbe una inserción de más en el mismo nodo antes de dividirse, y cuando se divide, crece siempre desde la raíz hacia abajo, nunca desde una hoja hacia arriba. El AVL necesita el campo extra altura en cada nodo para decidir cuándo rotar, el árbol 2-3 no necesita ningún campo de contabilidad, su invariante de profundidad uniforme es una consecuencia directa de cómo se construye, no algo que haya que medir aparte.

Ninguno de los dos es la última palabra en árboles balanceados. El árbol rojo-negro, que la mayoría de las bibliotecas estándar de Java y C++ usan por dentro para sus mapas y conjuntos ordenados, es una forma distinta de representar la misma idea del árbol 2-3, cada nodo del 2-3 se descompone en uno o dos nodos binarios con un color asociado, rojo o negro, que codifica si ese nodo forma parte de un nodo de 2 o de un nodo de 3 del árbol original. El B-tree, que usan la mayoría de los motores de bases de datos para organizar sus índices en disco, generaliza la misma idea de los árboles 2-3 permitiendo muchas más claves por nodo, para que cada nodo ocupe exactamente una página de disco y minimizar cuántas veces hay que leer del disco para encontrar un dato. Esta guía no implementa ninguno de los dos, quedan como el siguiente paso natural una vez que el mecanismo de división y el de rotación, los dos pilares que hoy viste, ya son claros.

TipReto 3. Sin ejecutar nada

Vas a insertar mil valores ya ordenados, del 1 al 1000, primero en un árbol 2-3 vacío y después en un árbol AVL vacío. Antes de seguir, decide qué le pasa a la altura final de cada uno, comparada con la que tendría un ABB simple con esos mismos mil valores.

NotaSolución del Reto 3

La primera y la segunda son correctas, la tercera es el error de pensar que el orden de llegada afecta al AVL igual que afecta al ABB simple. El ABB simple del Tema 3 no tiene ninguna defensa contra datos ya ordenados, así que mil valores ascendentes producen una cadena de altura 999, exactamente n - 1. El AVL parte de la misma estructura binaria, pero cada inserción pasa por balancear en la vuelta de la recursión, así que cualquier intento de formar una cadena se corta con una rotación antes de llegar muy lejos, la altura se queda cerca de log2(1000), unos 10 niveles. El árbol 2-3 nunca cuelga un nodo nuevo debajo de una hoja, así que ni siquiera necesita corregir nada, la altura también se queda cerca de log2(1000) por construcción. El orden de llegada de los datos, que era la variable que decidía todo en el Tema 3, deja de importar en los dos árboles de este tema.
