Unidad Unidad 3. Estructuras dinámicas
Tema Tema 3. Árboles binarios de búsqueda

Los dos temas anteriores de esta unidad eran estructuras lineales, cada nodo con exactamente un siguiente, una sola forma de recorrerlas, de principio a fin. Hoy eso cambia. El árbol binario de búsqueda le da a cada nodo dos caminos posibles, izquierdo y derecho, y esa segunda referencia es lo que le permite hacer algo que ninguna lista enlazada puede hacer sola, mantener sus datos ordenados mientras los guarda, sin necesitar un paso aparte de ordenamiento. El Tema 2 cerró anunciando este momento, la misma pieza Nodo con dos referencias en vez de una, y una promesa concreta, apoyarte en la Cola que construiste para programar uno de los recorridos. Esa promesa se cumple en la sección de recorrido por niveles.

1 Qué es un árbol y qué lo vuelve un árbol binario de búsqueda

Un árbol, en esta estructura de datos, es un conjunto de nodos conectados de forma jerárquica, no lineal. Hay un nodo especial sin padre, la raíz, y cada nodo tiene cero, uno o más nodos hijos. Un nodo sin hijos es una hoja. Cuando cada nodo tiene como máximo dos hijos, distinguibles como izquierdo y derecho, el árbol es binario. Todavía no hay ningún orden implicado en esa definición, un árbol binario cualquiera podría tener los datos acomodados de cualquier forma.

Lo que convierte un árbol binario en un árbol binario de búsqueda, ABB de aquí en adelante, es una regla adicional que se cumple en cada nodo del árbol, no solo en la raíz, todo valor guardado en el subárbol izquierdo de un nodo es menor que el valor de ese nodo, y todo valor guardado en su subárbol derecho es mayor. Esta guía trabaja con una política explícita para los valores repetidos, ningún dato puede aparecer dos veces en el árbol, así que insertar un valor que ya existe no modifica nada y lo descarta sin lanzar ningún error, la misma decisión que toma la clase BinarySearchTree de Weiss en su implementación de referencia.

Este árbol de siete nodos es el resultado de insertar, en este orden, 50, 30, 70, 20, 40, 60 y 80. Vas a verlo reaparecer en el resto de esta guía, porque cada operación se explica sobre el mismo ejemplo en vez de saltar de un árbol a otro.

La altura de un árbol es la distancia, en número de enlaces, desde la raíz hasta la hoja más lejana. La profundidad de un nodo es la distancia desde la raíz hasta ese nodo. En el árbol de arriba la raíz tiene profundidad 0, 30 y 70 tienen profundidad 1, y las cuatro hojas tienen profundidad 2, así que la altura completa del árbol es 2. Esta cuenta vuelve a aparecer más adelante, porque es la que decide cuánto trabajo cuesta cada operación.

2 El nodo con dos caminos: NodoArbol

El Nodo del Tema 1 guardaba un dato y una sola referencia, siguiente. Un árbol necesita dos referencias por nodo, así que esta guía usa una clase nueva, NodoArbol, con la misma forma que Nodo pero con izquierdo y derecho en vez de un único siguiente.

public class NodoArbol {
    int dato;
    NodoArbol izquierdo;
    NodoArbol derecho;

    public NodoArbol(int dato) {
        this.dato = dato;
        this.izquierdo = null;
        this.derecho = null;
    }
}

public class ArbolBinarioBusqueda {
    private NodoArbol raiz;
}
class NodoArbol:
    def __init__(self, dato):
        self.dato = dato
        self.izquierdo = None
        self.derecho = None


class ArbolBinarioBusqueda:
    def __init__(self):
        self.raiz = None

Esta guía usa int para el dato, en vez de un tipo genérico como el Object que usaron Pila y Cola. La razón es concreta, insertar y buscar necesitan comparar valores con < y >, y Object no ofrece esa operación en Java sin pedirle al tipo que implemente Comparable<T>, un paso extra que esta guía deja fuera para no distraer de la estructura del árbol. Python no tiene ese problema, < funciona sobre cualquier tipo que lo soporte sin declarar nada aparte.

3 Insertar: bajar hasta el hueco correcto

Insertar un valor nuevo consiste en compararlo contra la raíz, decidir si baja a la izquierda o a la derecha según el resultado de esa comparación, y repetir la misma decisión en cada nodo siguiente hasta llegar a una referencia vacía, que es exactamente el lugar donde el valor nuevo debe colgar. El Tema 3 de la Unidad 1 ya explicó qué necesita una función recursiva, un caso base y un caso recursivo que avanza hacia él, y insertar encaja en ese molde sin ningún ajuste, el caso base es un subárbol vacío, null en Java o None en Python, y el caso recursivo compara el dato y desciende por la referencia que corresponda.

public void insertar(int dato) {
    raiz = insertar(raiz, dato);
}

private NodoArbol insertar(NodoArbol nodo, int dato) {
    if (nodo == null) {
        return new NodoArbol(dato); // caso base: aqui va el nodo nuevo
    }
    if (dato < nodo.dato) {
        nodo.izquierdo = insertar(nodo.izquierdo, dato);
    } else if (dato > nodo.dato) {
        nodo.derecho = insertar(nodo.derecho, dato);
    }
    // dato == nodo.dato: valor repetido, no se hace nada
    return nodo;
}
def insertar(self, dato):
    self.raiz = self._insertar(self.raiz, dato)

def _insertar(self, nodo, dato):
    if nodo is None:
        return NodoArbol(dato)  # caso base: aqui va el nodo nuevo
    if dato < nodo.dato:
        nodo.izquierdo = self._insertar(nodo.izquierdo, dato)
    elif dato > nodo.dato:
        nodo.derecho = self._insertar(nodo.derecho, dato)
    # dato == nodo.dato: valor repetido, no se hace nada
    return nodo

El patrón de este método es el mismo que ya trabajaste con fibonacci en la Unidad 1, cada llamada combina su propio resultado con el de la llamada recursiva, en este caso reasignando nodo.izquierdo o nodo.derecho al resultado de bajar un nivel más. Ese reasignar en cada nivel es lo que permite que el mismo método sirva tanto para colgar un nodo nuevo cuando el árbol está vacío en ese punto, como para no cambiar nada cuando el subárbol ya existe, nodo = insertar(nodo, dato) deja nodo intacto salvo en el nivel exacto donde apareció el hueco vacío.

TipReto 1. Dónde cuelga el nodo nuevo

Sobre el árbol de ejemplo de esta guía, raíz 50, con 30 y 70 como hijos, y 20, 40, 60 y 80 como hojas, vas a insertar el valor 65. Antes de seguir, traza a mano las comparaciones, empezando en la raíz, y decide de qué nodo va a colgar 65 y de qué lado.

NotaSolución del Reto 1

La segunda es correcta. La primera comparación es 65 contra la raíz, 50, y 65 es mayor, así que baja a la derecha, hacia 70. La segunda comparación es 65 contra 70, y 65 es menor, así que baja a la izquierda, hacia 60. La tercera comparación es 65 contra 60, y 65 es mayor, así que baja a la derecha de 60, que está vacía, y ahí se cuelga el nodo nuevo. El resultado final es 65 como hijo derecho de 60, tres comparaciones en total, una por cada nivel que el árbol tiene de altura más uno.

4 Buscar: el mismo camino que insertar

Buscar un valor recorre exactamente el mismo camino que seguiría insertarlo, la única diferencia es qué pasa al llegar a una referencia vacía, insertar cuelga ahí un nodo nuevo, buscar concluye que el valor no está en el árbol.

public boolean buscar(int dato) {
    return buscar(raiz, dato);
}

private boolean buscar(NodoArbol nodo, int dato) {
    if (nodo == null) {
        return false; // caso base: se acabo el arbol y no aparecio
    }
    if (dato == nodo.dato) {
        return true; // caso base: lo encontro
    }
    return dato < nodo.dato ? buscar(nodo.izquierdo, dato) : buscar(nodo.derecho, dato);
}
def buscar(self, dato):
    return self._buscar(self.raiz, dato)

def _buscar(self, nodo, dato):
    if nodo is None:
        return False  # caso base: se acabo el arbol y no aparecio
    if dato == nodo.dato:
        return True  # caso base: lo encontro
    return self._buscar(nodo.izquierdo, dato) if dato < nodo.dato else self._buscar(nodo.derecho, dato)

Cada llamada recursiva baja exactamente un nivel, así que el número de comparaciones que hace buscar nunca pasa de la altura del árbol más uno. Sobre el árbol de ejemplo, con altura 2, ningún valor tarda más de tres comparaciones en encontrarse o en descartarse. Esa relación entre altura y costo real es el hilo que conecta el resto de esta guía.

5 Recorridos: cuatro formas de visitar el mismo árbol

Recorrer un árbol es visitar cada uno de sus nodos exactamente una vez, y a diferencia de una lista, en un árbol no hay un único orden natural de hacerlo. Los primeros tres recorridos que siguen comparten la misma estructura recursiva, el caso base es un subárbol vacío, que no aporta nada al recorrido, y el caso recursivo visita el nodo actual y desciende a sus dos subárboles, la única diferencia entre los tres es el momento exacto en que cada método decide “visitar” el nodo actual, antes de bajar, entre las dos bajadas, o después de las dos.

Fíjate en la fila de inorden, el número dentro de cada nodo coincide exactamente con la posición horizontal del nodo en el dibujo, 1 a la izquierda del todo, 7 a la derecha del todo. No es coincidencia, es la razón por la que este recorrido se llama así, visita primero todo el subárbol izquierdo, después el nodo, después todo el subárbol derecho, y como el invariante del ABB garantiza que el subárbol izquierdo tiene todo lo menor y el derecho todo lo mayor, el resultado siempre sale ordenado de menor a mayor, sin ningún paso adicional de ordenamiento.

public java.util.List<Integer> inorden() {
    java.util.List<Integer> resultado = new java.util.ArrayList<>();
    inorden(raiz, resultado);
    return resultado;
}

private void inorden(NodoArbol nodo, java.util.List<Integer> resultado) {
    if (nodo == null) {
        return; // caso base: subarbol vacio, nada que visitar
    }
    inorden(nodo.izquierdo, resultado);
    resultado.add(nodo.dato);
    inorden(nodo.derecho, resultado);
}

public java.util.List<Integer> preorden() {
    java.util.List<Integer> resultado = new java.util.ArrayList<>();
    preorden(raiz, resultado);
    return resultado;
}

private void preorden(NodoArbol nodo, java.util.List<Integer> resultado) {
    if (nodo == null) {
        return;
    }
    resultado.add(nodo.dato);
    preorden(nodo.izquierdo, resultado);
    preorden(nodo.derecho, resultado);
}

public java.util.List<Integer> postorden() {
    java.util.List<Integer> resultado = new java.util.ArrayList<>();
    postorden(raiz, resultado);
    return resultado;
}

private void postorden(NodoArbol nodo, java.util.List<Integer> resultado) {
    if (nodo == null) {
        return;
    }
    postorden(nodo.izquierdo, resultado);
    postorden(nodo.derecho, resultado);
    resultado.add(nodo.dato);
}
def inorden(self):
    resultado = []
    self._inorden(self.raiz, resultado)
    return resultado

def _inorden(self, nodo, resultado):
    if nodo is None:
        return  # caso base: subarbol vacio, nada que visitar
    self._inorden(nodo.izquierdo, resultado)
    resultado.append(nodo.dato)
    self._inorden(nodo.derecho, resultado)

def preorden(self):
    resultado = []
    self._preorden(self.raiz, resultado)
    return resultado

def _preorden(self, nodo, resultado):
    if nodo is None:
        return
    resultado.append(nodo.dato)
    self._preorden(nodo.izquierdo, resultado)
    self._preorden(nodo.derecho, resultado)

def postorden(self):
    resultado = []
    self._postorden(self.raiz, resultado)
    return resultado

def _postorden(self, nodo, resultado):
    if nodo is None:
        return
    self._postorden(nodo.izquierdo, resultado)
    self._postorden(nodo.derecho, resultado)
    resultado.append(nodo.dato)

Preorden y postorden se usan menos que inorden para leer datos ordenados, pero tienen su propio uso. Preorden visita cada nodo antes que a sus hijos, así que sirve para copiar un árbol o para serializarlo de una forma que después se puede reconstruir insertando en ese mismo orden. Postorden visita cada nodo después que a sus dos hijos, así que sirve para liberar la memoria de un árbol de abajo hacia arriba, o para evaluar una expresión donde primero hay que resolver las dos ramas antes de aplicar la operación de la raíz.

Recorrido por niveles: la aplicación real de la Cola del Tema 2

Los tres recorridos de arriba avanzan en profundidad, se meten todo lo que pueden por una rama antes de volver. El recorrido por niveles hace lo contrario, visita todos los nodos de una profundidad antes de pasar a la siguiente, la raíz primero, después sus dos hijos, después los cuatro nietos. Ese orden no sale de la recursión de forma natural, sale de una estructura FIFO, exactamente la Cola que construiste en el Tema 2, y esta es la aplicación real que ese tema prometió.

public java.util.List<Integer> porNiveles() {
    java.util.List<Integer> resultado = new java.util.ArrayList<>();
    if (raiz == null) {
        return resultado;
    }
    Cola cola = new Cola();
    cola.encolar(raiz);
    while (!cola.estaVacia()) {
        NodoArbol actual = (NodoArbol) cola.desencolar();
        resultado.add(actual.dato);
        if (actual.izquierdo != null) {
            cola.encolar(actual.izquierdo);
        }
        if (actual.derecho != null) {
            cola.encolar(actual.derecho);
        }
    }
    return resultado;
}
def por_niveles(self):
    resultado = []
    if self.raiz is None:
        return resultado
    cola = Cola()
    cola.encolar(self.raiz)
    while not cola.esta_vacia():
        actual = cola.desencolar()
        resultado.append(actual.dato)
        if actual.izquierdo is not None:
            cola.encolar(actual.izquierdo)
        if actual.derecho is not None:
            cola.encolar(actual.derecho)
    return resultado

porNiveles no usa ninguna recursión, es el mismo bucle mientras la cola no esta vacia que ya escribiste en simularAtencion en el Tema 2, solo que en vez de clientes encola nodos del árbol. La línea (NodoArbol) cola.desencolar() en Java es obligatoria porque Cola guarda Object, tal como se definió en el Tema 2, así que hay que devolver el dato a su tipo real antes de leer izquierdo y derecho, el mismo costo del tipo genérico que ya pagaste al usar Pila y Cola con cualquier otro dato. Python no necesita ese paso, porque no exige declarar el tipo de lo que sale de desencolar.

TipReto 2. Completa el recorrido por niveles

Sobre el árbol de ejemplo, si en vez de Cola alguien usa por error una Pila dentro de porNiveles, cambiando cola.encolar por pila.apilar y cola.desencolar por pila.desapilar, sin tocar ninguna otra línea. Antes de seguir, decide qué le pasa al orden de salida.

NotaSolución del Reto 2

La segunda es correcta. NodoArbol se puede guardar en cualquiera de las dos estructuras sin problema, el error no está ahí, está en el orden en que salen. Con Cola, el primer nodo que se procesa después de la raíz es el primero que se encoló entre sus hijos, FIFO, así que el recorrido respeta cada nivel completo antes de pasar al siguiente. Con Pila, el primer nodo que se procesa después de la raíz es el último que se apiló, LIFO, así que después de procesar 50 y apilar 30 y 70, el siguiente en salir es 70, y su hijo 80 se apila encima de 60, así que el orden termina siendo 50, 70, 80, 60, 30, 40, 20, una mezcla de niveles que no corresponde a ningún recorrido con nombre reconocido. La estructura que se elige detrás de un recorrido no es un detalle de implementación, es lo que define qué recorrido es.

6 Eliminar: el caso que rompe más implementaciones

Eliminar un valor del árbol tiene que dejarlo intacto como ABB después de sacar el nodo, y eso obliga a tratar tres situaciones distintas según cuántos hijos tenga el nodo que se va.

Si el nodo es una hoja, sin hijos, basta con quitar la referencia que el padre tenía hacia él, no queda ningún hueco que llenar. Si el nodo tiene un solo hijo, ese hijo simplemente toma el lugar del nodo eliminado, el padre pasa a apuntar directo al nieto. El tercer caso, un nodo con dos hijos, es el que de verdad exige cuidado, porque no hay ningún hijo único que pueda subir a ocupar su lugar sin romper el invariante de orden.

El caso difícil: un nodo con dos hijos

Cuando el nodo a eliminar tiene dos hijos, ni el izquierdo ni el derecho pueden simplemente subir a tomar su lugar, porque cada uno arrastra su propio subárbol completo y no hay forma de conectarlos a los dos sin romper el invariante. La solución estándar, la misma que usa la implementación de referencia de Weiss, es reemplazar el dato del nodo eliminado por su sucesor inorden, el siguiente valor más grande que existe en el árbol, y después eliminar ese sucesor de su posición original, donde el problema ya se volvió uno de los dos casos simples de arriba.

El sucesor inorden de un nodo con dos hijos siempre es el valor más pequeño de su subárbol derecho, y encontrarlo es sencillo, basta con bajar por la izquierda desde ese subárbol derecho hasta que ya no haya más hijo izquierdo. Ese nodo mínimo nunca tiene hijo izquierdo, por definición es el más pequeño de su rama, así que al eliminarlo de su posición original siempre cae en el caso de hoja o de un solo hijo, nunca de vuelta en el caso difícil.

public void eliminar(int dato) {
    raiz = eliminar(raiz, dato);
}

private NodoArbol eliminar(NodoArbol nodo, int dato) {
    if (nodo == null) {
        return null; // el dato no estaba en el arbol
    }
    if (dato < nodo.dato) {
        nodo.izquierdo = eliminar(nodo.izquierdo, dato);
    } else if (dato > nodo.dato) {
        nodo.derecho = eliminar(nodo.derecho, dato);
    } else if (nodo.izquierdo != null && nodo.derecho != null) {
        // dos hijos: copia el sucesor inorden y elimina ese sucesor de su lugar
        nodo.dato = minimo(nodo.derecho);
        nodo.derecho = eliminar(nodo.derecho, nodo.dato);
    } else {
        // hoja o un solo hijo: el hijo que exista, o null, toma el lugar
        nodo = (nodo.izquierdo != null) ? nodo.izquierdo : nodo.derecho;
    }
    return nodo;
}

private int minimo(NodoArbol nodo) {
    while (nodo.izquierdo != null) {
        nodo = nodo.izquierdo;
    }
    return nodo.dato;
}
def eliminar(self, dato):
    self.raiz = self._eliminar(self.raiz, dato)

def _eliminar(self, nodo, dato):
    if nodo is None:
        return None  # el dato no estaba en el arbol
    if dato < nodo.dato:
        nodo.izquierdo = self._eliminar(nodo.izquierdo, dato)
    elif dato > nodo.dato:
        nodo.derecho = self._eliminar(nodo.derecho, dato)
    elif nodo.izquierdo is not None and nodo.derecho is not None:
        # dos hijos: copia el sucesor inorden y elimina ese sucesor de su lugar
        nodo.dato = self._minimo(nodo.derecho)
        nodo.derecho = self._eliminar(nodo.derecho, nodo.dato)
    else:
        # hoja o un solo hijo: el hijo que exista, o None, toma el lugar
        nodo = nodo.izquierdo if nodo.izquierdo is not None else nodo.derecho
    return nodo

def _minimo(self, nodo):
    while nodo.izquierdo is not None:
        nodo = nodo.izquierdo
    return nodo.dato

Los dos ramales else if con un solo hijo y el ramal final con cero o un hijo comparten una misma línea, nodo = nodo.izquierdo != null ? nodo.izquierdo : nodo.derecho, que cubre a la vez el caso de la hoja, donde los dos son null y el resultado es null, y el caso de un hijo, donde el hijo que exista ocupa el lugar. La rama de los dos hijos es la única que necesita una segunda llamada recursiva a eliminar, porque después de copiar el dato del sucesor todavía queda pendiente sacarlo de su posición original, para no dejarlo duplicado en el árbol.

TipReto 3. Traza la eliminación de un nodo con dos hijos

Sobre el árbol de ejemplo completo, raíz 50 con hijos 30 y 70, y hojas 20, 40, 60 y 80, vas a eliminar 70, que tiene dos hijos, 60 y 80. Antes de seguir, decide cuál es el sucesor inorden de 70 y qué dato queda en su lugar después de eliminarlo.

NotaSolución del Reto 3

La primera es correcta. El sucesor inorden se busca siempre en el subárbol derecho, nunca en el izquierdo, así que la segunda opción parte de un subárbol equivocado desde el inicio. El subárbol derecho de 70 tiene un único nodo, 80, sin ningún hijo izquierdo propio, así que minimo se detiene ahí mismo en el primer paso, el sucesor es 80. El nodo que tenía dato 70 pasa a tener dato 80, y como la operación de eliminar solo tocó el subárbol derecho, para sacar de ahí al 80 original que quedó duplicado, el hijo izquierdo, 60, sigue exactamente donde estaba, intacto. Si el subárbol derecho de 70 hubiera tenido más de un nodo, por ejemplo 80 con un hijo izquierdo 75, el procedimiento seguiría siendo el mismo, bajar por la izquierda del subárbol derecho hasta que ya no haya más hijo izquierdo, y en ese caso el sucesor habría sido 75, no 80.

7 Altura del árbol: por qué importa

Cada operación que viste en esta guía, insertar, buscar y eliminar, hace como máximo una comparación por nivel de altura antes de terminar. Esa es la razón concreta por la que la altura del árbol no es un detalle técnico, es lo que decide si estas operaciones son rápidas o lentas.

Si el árbol se mantiene razonablemente equilibrado, con más o menos la misma cantidad de nodos a cada lado en cada nivel, su altura crece de forma logarítmica respecto al número de nodos, log2(n), porque cada nivel adicional duplica aproximadamente cuántos nodos caben. Con mil nodos bien repartidos, la altura ronda diez, con un millón, ronda veinte. Ese es el caso promedio de un ABB construido con datos que llegan en un orden razonablemente variado, y es lo que le da al árbol su fama, operaciones en O(log n).

Pero nada en el algoritmo de insertar obliga a que el árbol quede equilibrado. Si los datos llegan ya ordenados, cada valor nuevo es mayor que todos los anteriores, así que siempre baja por la derecha y siempre cuelga como hijo derecho del último nodo insertado. El resultado es una cadena, cada nodo con un solo hijo, exactamente la forma de una lista enlazada, y la altura deja de ser log2(n) para convertirse en n - 1, el peor caso posible, O(n).

Los dos árboles del diagrama guardan exactamente los mismos cinco valores, la única diferencia es el orden en que se insertaron, y esa diferencia sola cambia la altura de 4 a 2. En un árbol de miles de nodos la diferencia entre O(log n) y O(n) deja de ser una curiosidad y se convierte en la diferencia entre un programa que responde de inmediato y uno que se arrastra.

El árbol degenerado, medido de verdad

Para que esta diferencia no quede en teoría, vale la pena medirla. El siguiente script en Python construye dos árboles con los mismos ocho mil valores enteros, uno insertándolos ya ordenados, el caso degenerado, y otro insertándolos en un orden aleatorio, y compara la altura resultante y el tiempo que toma buscar tres mil valores en cada uno.

import random
import time
import math

N = 8000
datos_ordenados = list(range(N))
datos_aleatorios = list(range(N))
random.seed(42)
random.shuffle(datos_aleatorios)

arbol_degenerado = ArbolBinarioBusqueda()
for x in datos_ordenados:
    arbol_degenerado.insertar(x)

arbol_aleatorio = ArbolBinarioBusqueda()
for x in datos_aleatorios:
    arbol_aleatorio.insertar(x)

print(f"altura del arbol degenerado: {arbol_degenerado.altura()}")
print(f"altura del arbol con insercion aleatoria: {arbol_aleatorio.altura()}")
print(f"log2(N) de referencia: {math.log2(N):.1f}")

busquedas = random.sample(range(N), 3000)

inicio = time.perf_counter()
for x in busquedas:
    arbol_degenerado.buscar(x)
tiempo_degenerado = time.perf_counter() - inicio

inicio = time.perf_counter()
for x in busquedas:
    arbol_aleatorio.buscar(x)
tiempo_aleatorio = time.perf_counter() - inicio

print(f"tiempo en el arbol degenerado: {tiempo_degenerado:.4f} s")
print(f"tiempo en el arbol aleatorio: {tiempo_aleatorio:.4f} s")
print(f"razon: {tiempo_degenerado / tiempo_aleatorio:.1f}x mas lento")

insertar y buscar en este script se escribieron en su versión iterativa, con un bucle en vez de llamadas recursivas, no por preferencia de estilo. La versión recursiva de esta misma guía, corriendo sobre un árbol degenerado de ocho mil nodos, se estrella antes de terminar:

El límite de recursión por defecto de Python es 1000 llamadas activas a la vez, y un árbol degenerado de tres mil nodos ya necesita el doble de eso solo para bajar hasta la última hoja, así que RecursionError aparece incluso antes de terminar de construir el árbol. Es la misma familia de error que el Tema 3 de la Unidad 1 explicó con factorial y el desbordamiento de pila, StackOverflowError en Java, RecursionError en Python, aplicada ahora a una estructura de datos completa en vez de a un solo número. Un árbol degenerado no solo vuelve las operaciones más lentas, en un lenguaje con límite de recursión puede volverlas imposibles de ejecutar tal como se escribieron en esta guía.

Con las versiones iterativas, que no dependen de la pila de llamadas del intérprete, el script sobre ocho mil elementos corrió sin problema y produjo esta salida real:

El resultado exacto varía según el equipo donde se ejecute, lo que importa es la dirección y la magnitud, la altura del árbol degenerado es exactamente n - 1, 7999 con 8000 nodos, mientras que la altura del árbol con inserción aleatoria, 35, queda cerca del log2(n) de referencia, 13, más alta por la variación natural de un orden aleatorio, pero de un orden de magnitud completamente distinto. Esa diferencia en altura se traduce directo en el tiempo de búsqueda, 167 veces más lento en el árbol degenerado sobre este equipo en particular, una proporción que crece todavía más a medida que crece N, porque la altura degenerada crece de forma lineal mientras la altura equilibrada apenas se mueve.

Este es exactamente el gancho hacia el próximo tema. Un árbol binario de búsqueda, tal como lo construiste hoy, no tiene ninguna defensa contra este escenario, insertar datos ordenados es una entrada perfectamente válida y el árbol se degrada sin avisar ni lanzar ningún error. El Tema 4 de esta unidad resuelve justo este problema con dos familias de árboles que se reorganizan solos durante la inserción y la eliminación para mantener la altura cerca de log2(n) sin importar en qué orden lleguen los datos, los árboles 2-3 y los árboles AVL.

NotaSolución del Reto 4

La segunda y la tercera son correctas, la primera es el error más común de subestimar cuánto importa el orden de inserción. Insertando 5, 3, 8, 1, 4, 7, 9 en ese orden, 5 queda de raíz, 3 y 8 como sus hijos, y 1, 4, 7, 9 se acomodan como hojas de esos dos, un árbol de altura 2 con los siete nodos razonablemente repartidos. Insertando los mismos siete valores ya ordenados, 1 es la raíz, 3 cuelga a su derecha porque es mayor, 4 cuelga a la derecha de 3 por la misma razón, y así sucesivamente, una cadena de siete nodos donde cada uno solo tiene hijo derecho, altura 6, exactamente n - 1. El contenido final del árbol, los mismos siete valores, no dice nada sobre su forma, la forma la decide por completo el orden de llegada.
