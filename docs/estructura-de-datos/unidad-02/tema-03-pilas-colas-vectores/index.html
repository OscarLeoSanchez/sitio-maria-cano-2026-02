Autor/a

Oscar Leonel Sánchez Conde

Fecha de publicación

17 de agosto de 2026

Unidad Unidad 2. Estructuras fijas
Tema Tema 3. Pilas y colas usando vectores

El Tema 2 de esta unidad recorrió la matriz, un arreglo de arreglos donde cada posición se ubica por fila y columna. Hoy vuelves a un arreglo de una sola dimensión, pero con una tarea distinta, ya que no vas a recorrerlo libremente sino a esconderlo por completo detrás de dos contratos que ya conoces. La Unidad 1 cerró su Tema 2 con una clase Pila cuyos cuatro métodos, apilar, desapilar, cima y estaVacia, lanzaban UnsupportedOperationException con el mensaje "llega en la Unidad 2". Ese momento llegó. Hoy completas esa misma clase con un arreglo por dentro, resuelves el problema de qué hacer cuando el arreglo se llena, y construyes desde cero el contrato hermano de la pila, la cola, con una técnica que la primera vez sorprende a casi todo el mundo, el arreglo circular.

1 El contrato que quedó pendiente

Antes de tocar código, vale la pena mirar de nuevo la clase tal como quedó al final del Tema 2 de la Unidad 1, porque hoy no la reescribes desde cero, la completas.

public class Pila {
    public void apilar(Object elemento) {
        throw new UnsupportedOperationException("llega en la Unidad 2");
    }

    public Object desapilar() {
        throw new UnsupportedOperationException("llega en la Unidad 2");
    }

    public Object cima() {
        throw new UnsupportedOperationException("llega en la Unidad 2");
    }

    public boolean estaVacia() {
        throw new UnsupportedOperationException("llega en la Unidad 2");
    }
}

Los cuatro nombres, y qué recibe y devuelve cada uno, quedaron fijos desde entonces, así que nada de lo que sigue les cambia la firma. Lo único que faltaba decidir era la memoria, si por dentro hay un arreglo o una lista enlazada, y esa decisión es justamente el tema de hoy. La Unidad 3 va a resolver el mismo contrato con una lista enlazada, sin que ese cambio futuro obligue a tocar ni una línea del código que ya use Pila hoy, que es exactamente la promesa que el encapsulamiento hace posible.

2 Diseñando la Pila y la Cola con arreglo por dentro

Las dos clases de hoy comparten la misma idea de fondo, guardar un arreglo privado y dos enteros que llevan la cuenta de dónde está cada cosa. En la pila basta con un contador de elementos, tamaño, porque siempre se entra y se sale por el mismo extremo. En la cola hace falta un dato más, frente, porque el extremo de entrada y el de salida son distintos, y como vas a ver más adelante en el tema, ese detalle es justo lo que obliga al arreglo circular.

Ninguno de los dos campos internos es público, así que el código que ya usa Pila desde el Tema 2 de la Unidad 1 no ve ningún cambio en cómo se llama, solo deja de ver la excepción.

3 Qué pasa cuando el arreglo se llena

El método privado redimensionar es el corazón técnico de la pila con arreglo. Cuando apilar encuentra que tamaño ya alcanzó el largo del arreglo actual, no hay ninguna casilla libre donde escribir, así que la única salida es crear un arreglo nuevo más grande, copiar ahí todo lo que había, y descartar el arreglo viejo.

Nota el orden exacto de los pasos, primero se agranda el arreglo, después se copia lo que ya había, y solo al final se escribe el elemento nuevo que motivó todo esto. Invertir ese orden, por ejemplo tratar de escribir el elemento nuevo antes de tener dónde ponerlo, es la forma más común de romper esta implementación cuando se escribe por primera vez.

4 Cómo apilar, desapilar y cima operan sobre el arreglo interno

apilar escribe el elemento nuevo en la posición tamaño del arreglo y después incrementa tamaño en uno, salvo que el arreglo esté lleno, caso que ya viste en la sección anterior. desapilar hace lo contrario, decrementa tamaño y devuelve lo que había en esa posición, después de comprobar que la pila no esté vacía. cima simplemente lee datos[tamaño - 1] sin tocar nada.

public class Pila {
    private Object[] datos;
    private int tamaño;

    public Pila() {
        datos = new Object[10];
        tamaño = 0;
    }

    public void apilar(Object elemento) {
        if (tamaño == datos.length) {
            redimensionar();
        }
        datos[tamaño] = elemento;
        tamaño++;
    }

    public Object desapilar() {
        if (estaVacia()) {
            throw new IllegalStateException("la pila esta vacia");
        }
        tamaño--;
        Object elemento = datos[tamaño];
        datos[tamaño] = null;
        return elemento;
    }

    public Object cima() {
        if (estaVacia()) {
            throw new IllegalStateException("la pila esta vacia");
        }
        return datos[tamaño - 1];
    }

    public boolean estaVacia() {
        return tamaño == 0;
    }

    private void redimensionar() {
        Object[] datosNuevos = new Object[datos.length * 2];
        System.arraycopy(datos, 0, datosNuevos, 0, datos.length);
        datos = datosNuevos;
    }
}
class Pila:
    def __init__(self):
        self._datos = [None] * 10
        self._tamaño = 0

    def apilar(self, elemento):
        if self._tamaño == len(self._datos):
            self._redimensionar()
        self._datos[self._tamaño] = elemento
        self._tamaño += 1

    def desapilar(self):
        if self.esta_vacia():
            raise IndexError("la pila esta vacia")
        self._tamaño -= 1
        elemento = self._datos[self._tamaño]
        self._datos[self._tamaño] = None
        return elemento

    def cima(self):
        if self.esta_vacia():
            raise IndexError("la pila esta vacia")
        return self._datos[self._tamaño - 1]

    def esta_vacia(self):
        return self._tamaño == 0

    def _redimensionar(self):
        datos_nuevos = [None] * (len(self._datos) * 2)
        for i in range(self._tamaño):
            datos_nuevos[i] = self._datos[i]
        self._datos = datos_nuevos

Fíjate en un detalle que fácilmente se pasa por alto, desapilar no solo decrementa tamaño, también deja la casilla que queda libre en None o en null. Eso no hace falta para que el código funcione, la próxima llamada a apilar va a sobrescribir esa casilla de todas formas, y sin embargo dejarla así tal cual es un error real y bien documentado que vale la pena entender antes de seguir, así que vuelve sobre él más adelante en este mismo tema.

5 Cuanto debe crecer el arreglo nuevo

La decisión de cuánto más grande hacer el arreglo nuevo, el factor de crecimiento, no tiene una única respuesta correcta, y las estructuras equivalentes de la biblioteca estándar de Java y de Python lo resuelven de formas distintas, con compromisos distintos entre memoria desperdiciada y frecuencia de copias.

El Javadoc de Vector en Java SE 17 lo dice de forma explícita, si el incremento de capacidad no se configura, que es el caso por defecto, la capacidad del vector se duplica cada vez que necesita crecer. ArrayList, en cambio, deja la política de crecimiento fuera del contrato público, su Javadoc dice únicamente que agregar un elemento tiene costo amortizado constante, sin comprometerse a un factor exacto, así que aunque en la práctica de OpenJDK el crecimiento observado ronda 1.5 veces, presentar esa cifra como una garantía del lenguaje sería un error, porque el propio fabricante la deja fuera de lo que promete. CPython resuelve el mismo problema con una fórmula concreta y visible en su código fuente, en la función que redimensiona listas dentro de listobject.c, que agrega aproximadamente un octavo del tamaño nuevo, más 3 si ese tamaño nuevo es menor que nueve o más 6 en caso contrario, y trunca el resultado hacia abajo a un múltiplo de cuatro con una operación AND a nivel de bits. La documentación oficial de Python explica el motivo en su sección de preguntas frecuentes, cuando el arreglo debe crecer se reserva algo de espacio extra para que las próximas operaciones no necesiten otro realojamiento, lo que da un comportamiento amortizado lineal sobre una secuencia larga de append. La clase Pila de esta guía usa la opción más simple de las tres, duplicar, la misma que Vector, porque el objetivo aquí es que entiendas el mecanismo, no que memorices una fórmula de producción.

6 Por qué “amortizado” y no simplemente O(1)

La tabla resume las cuatro operaciones de la pila:

Operación Peor caso Amortizado
apilar O(n), cuando toca redimensionar O(1)
desapilar O(1) O(1)
cima O(1) O(1)
estaVacia O(1) O(1)

Que una operación individual pueda costar O(n) y que aun así se hable de O(1) en promedio no es una contradicción, es el resultado central del análisis amortizado, la técnica que reparte el costo caro de unas pocas operaciones entre todas las operaciones baratas que las rodean. Si la capacidad se duplica cada vez, el costo de copiar en cada redimensión sucesiva forma una serie geométrica, la misma idea que Cormen, Leiserson, Rivest y Stein analizan bajo el nombre de tablas dinámicas.

Para n apilamientos consecutivos desde una pila vacía que duplica su capacidad cada vez, el costo total de todas las copias de redimensión, sumadas, queda acotado por menos de 2n, ya que la serie 1 + 2 + 4 + … + n/2 nunca supera a n. Repartir ese costo total entre las n operaciones da menos de 2 unidades de trabajo por operación en promedio, sin importar cuál operación en particular fue la cara. Ese es exactamente el sentido de “amortizado”, no que cada operación cueste poco, sino que el total para una secuencia larga crece de forma lineal, y por lo tanto cada operación cuesta poco en promedio. Existe además la variante de achicar el arreglo cuando queda muy vacío, que desarrollan Cormen y sus coautores, con el cuidado de no reducirlo apenas cruza la mitad, porque alternar entre apilar y desapilar justo en ese punto produciría una redimensión en cada operación y arruinaría la cota amortizada; esta guía no implementa ese achicamiento, pero vale la pena que sepas que existe y por qué el umbral no puede ser exactamente la mitad.

TipReto 1. Traza las redimensiones

Imagina una pila que arranca con capacidad 4 y duplica su capacidad cada vez que se llena, igual que Vector. Vas a apilar ocho elementos seguidos, uno tras otro, sin desapilar ninguno. Antes de seguir, responde, ¿en qué apilamiento exacto, el primero, el segundo, y así, ocurre cada redimensión, y qué capacidad tiene el arreglo justo después de cada una?

NotaSolución del Reto 1

La pila arranca con capacidad 4 y tamaño 0. Los apilamientos 1, 2, 3 y 4 caben sin problema, porque tamaño == datos.length solo se cumple justo antes del quinto. Al llegar el quinto apilamiento, tamaño vale 4 y datos.length también vale 4, así que se dispara la redimensión antes de escribir ese quinto elemento, la capacidad pasa de 4 a 8, y el quinto elemento se escribe ya en el arreglo nuevo. Los apilamientos 6, 7 y 8 caben en las casillas que quedaron libres, así que no vuelve a redimensionar dentro de esta secuencia de ocho. La respuesta correcta es entonces la primera opción, la redimensión ocurre en el quinto apilamiento, y la tercera, la capacidad queda en 8, no en 16, porque solo hizo falta una redimensión para las ocho inserciones.

7 Un error silencioso que dejan las referencias que sobran

Antes de dejar la pila y pasar a la cola, conviene detenerse en por qué desapilar deja la casilla liberada en null, un detalle que en el código de arriba puede parecer un capricho de estilo. Piensa en el siguiente caso de estudio.

Un equipo escribe una pila con arreglo por dentro, prácticamente idéntica a la de esta guía, salvo que su desapilar solo decrementa tamaño y devuelve el elemento, sin poner null en la casilla que queda libre. El programa compila, corre, y en las pruebas de todos los días funciona sin ningún error visible, apila y desapila miles de veces sin que nada se rompa. Ya que el código nunca vuelve a leer esa casilla porque tamaño ya no la incluye, ¿hay algún problema real, o es solo una cuestión de prolijidad?

Sí hay un problema real. Aunque el código lógicamente ya olvidó ese elemento, porque tamaño dice que ya no forma parte de la pila, el arreglo interno todavía guarda una referencia física a él en esa casilla, y mientras esa referencia exista, el recolector de basura no puede liberar la memoria del objeto, sin importar que el resto del programa nunca vuelva a usarlo. Joshua Bloch llama a esto una referencia obsoleta en Effective Java, en el ítem sobre eliminar referencias obsoletas, que usa precisamente una pila con arreglo por dentro como caso de estudio: una referencia que el programa nunca más va a desreferenciar pero que sigue viva desde el punto de vista de la memoria. El síntoma no aparece de inmediato, ya que el programa sigue funcionando bien durante mucho tiempo, y solo se manifiesta como una fuga de memoria lenta, cada vez más lenta o más pesada, o como un OutOfMemoryError mucho después y muy lejos de la línea donde en realidad ocurrió el error. Falla rápido y en voz alta es preferible a un fallo silencioso, la misma idea aplicada ahora no a un método sin terminar sino a una estructura de datos que retiene memoria que ya no le pertenece a nadie.

8 Por qué no basta con mover el índice 0 en una cola simple

Con la pila resuelta, toca construir el contrato hermano. Antes de llegar al arreglo circular, vale la pena ver por qué la solución ingenua no sirve. Si desencolar siempre libera la posición 0 del arreglo y encolar siempre escribe al final, entonces cada desencolar obliga a recorrer y desplazar una posición hacia la izquierda a todos los elementos que quedan, uno por uno, para que la posición 0 vuelva a quedar disponible para el próximo elemento. Eso convierte a desencolar, que debería ser una operación barata, en una operación O(n), y en una cola que se usa mucho, ese desplazamiento repetido es justo el tipo de costo escondido que este curso quiere que aprendas a detectar.

La solución no es mover los elementos, es dejar de moverlos por completo. En vez de eso, se mueven los índices, frente y la posición donde toca escribir a continuación, y el arreglo se trata como si el final se enrollara hacia el principio en cuanto se acaba el espacio físico.

9 Los índices que le dan la vuelta al arreglo en una cola circular

El campo frente guarda la posición del primer elemento lógico de la cola, no necesariamente la posición 0 del arreglo. El campo tamaño cuenta cuántos elementos hay guardados en este momento. Con esos dos datos, la posición donde escribir el próximo elemento se calcula como (frente + tamaño) % capacidad, y el operador módulo es justamente lo que hace que ese cálculo “de la vuelta” al llegar al final físico del arreglo y siga contando desde la posición 0.

Aquí aparece la trampa que sorprende a casi todo el mundo la primera vez que implementa una cola circular. Si en vez de un contador de tamaño se usan solo dos índices desnudos, frente y fin, sin nada más, entonces frente == fin es ambiguo, porque tanto una cola vacía como una cola completamente llena llegan exactamente a esa misma condición, y no hay forma de distinguir los dos casos con solo esa comparación. Hay dos soluciones estándar para esa ambigüedad. Una es guardar un contador de elementos aparte, que es la técnica que usa esta guía. La otra es sacrificar deliberadamente una casilla del arreglo, nunca llenarla del todo, de modo que cuando fin alcanza a frente el buffer está vacío, y cuando fin queda una posición detrás de frente está lleno, sin ambigüedad y sin necesitar ningún contador aparte; esta segunda técnica es la que documenta la página oficial del núcleo de Linux dedicada a los buffers circulares. El mismo documento describe además una optimización real de bajo nivel, si la capacidad del buffer es una potencia de dos, el módulo se puede reemplazar por una máscara AND bit a bit, mucho más barata en hardware que una división. Esta guía usa el contador explícito por ser la opción más fácil de razonar para quien construye su primera cola circular, pero vale la pena que sepas que la alternativa de sacrificar una casilla existe, se usa de verdad en sistemas donde cada instrucción cuenta, y es la que documenta el núcleo de Linux.

10 Cómo encolar, desencolar y frente operan sobre el arreglo

Con frente y tamaño ya definidos, las cuatro operaciones quedan cortas.

public class Cola {
    private Object[] datos;
    private int frente;
    private int tamaño;

    public Cola() {
        datos = new Object[10];
        frente = 0;
        tamaño = 0;
    }

    public void encolar(Object elemento) {
        if (tamaño == datos.length) {
            redimensionar();
        }
        int posicion = (frente + tamaño) % datos.length;
        datos[posicion] = elemento;
        tamaño++;
    }

    public Object desencolar() {
        if (estaVacia()) {
            throw new IllegalStateException("la cola esta vacia");
        }
        Object elemento = datos[frente];
        datos[frente] = null;
        frente = (frente + 1) % datos.length;
        tamaño--;
        return elemento;
    }

    public Object frente() {
        if (estaVacia()) {
            throw new IllegalStateException("la cola esta vacia");
        }
        return datos[frente];
    }

    public boolean estaVacia() {
        return tamaño == 0;
    }
}
class Cola:
    def __init__(self):
        self._datos = [None] * 10
        self._frente = 0
        self._tamaño = 0

    def encolar(self, elemento):
        if self._tamaño == len(self._datos):
            self._redimensionar()
        posicion = (self._frente + self._tamaño) % len(self._datos)
        self._datos[posicion] = elemento
        self._tamaño += 1

    def desencolar(self):
        if self.esta_vacia():
            raise IndexError("la cola esta vacia")
        elemento = self._datos[self._frente]
        self._datos[self._frente] = None
        self._frente = (self._frente + 1) % len(self._datos)
        self._tamaño -= 1
        return elemento

    def frente(self):
        if self.esta_vacia():
            raise IndexError("la cola esta vacia")
        return self._datos[self._frente]

    def esta_vacia(self):
        return self._tamaño == 0

desencolar avanza frente con el mismo cálculo módulo que usa encolar para la posición de escritura, así que los dos extremos dan la vuelta al arreglo de la misma forma. Igual que en la pila, desencolar deja en null la casilla que libera, por la misma razón de referencias obsoletas que ya viste arriba, solo que ahora aplicada al extremo de salida de la cola.

TipReto 2. Encuentra el error de esta cola circular

El siguiente fragmento en Java compila y corre sin ningún error visible en pruebas rápidas, pero tiene un error de diseño serio. Léelo con calma antes de seguir.

public class ColaConError {
    private Object[] datos = new Object[6];
    private int frente = 0;
    private int fin = 0;

    public void encolar(Object elemento) {
        datos[fin] = elemento;
        fin = (fin + 1) % datos.length;
    }

    public Object desencolar() {
        Object elemento = datos[frente];
        frente = (frente + 1) % datos.length;
        return elemento;
    }

    public boolean estaVacia() {
        return frente == fin;
    }
}

Antes de seguir, responde en una frase, ¿qué le pasa a esta cola si se encolan seis elementos seguidos sin desencolar ninguno, y por qué estaVacia no puede detectarlo?

NotaSolución del Reto 2

ColaConError no tiene ningún contador de tamaño, solo dos índices desnudos, así que hereda exactamente la ambigüedad que describe la documentación del núcleo de Linux citada arriba. Si se encolan seis elementos seguidos en un arreglo de capacidad 6, fin avanza de 0 a 1, 2, 3, 4, 5 y de vuelta a 0 con el módulo, así que después del sexto encolar, fin vuelve a valer 0, exactamente el mismo valor que frente. En ese punto estaVacia devuelve true, porque compara frente == fin, sin poder distinguir entre una cola recién creada y una cola completamente llena. Peor todavía, si alguien llama a encolar una séptima vez creyendo que hay espacio, porque estaVacia dijo que sí lo había, el código escribe en datos[0], sobrescribiendo en silencio el primer elemento que se había encolado, sin lanzar ningún error ni ninguna advertencia. Las respuestas correctas son la segunda, estaVacia devuelve true de forma incorrecta cuando la cola está llena, y la tercera, el séptimo encolar sobrescribe el primer elemento sin avisar. La corrección exige agregar el contador tamaño, exactamente como hace la clase Cola de esta guía, y usarlo tanto en encolar como en desencolar y en estaVacia, en vez de comparar frente con fin directamente.

11 Por qué redimensionar una cola circular no es una copia directa

Redimensionar la pila fue una copia simple, porque sus elementos siempre ocupan desde la posición 0 hasta tamaño - 1. En la cola circular eso ya no es cierto, los elementos pueden estar “envueltos”, parte al final físico del arreglo y parte al principio, así que copiar el arreglo posición por posición tal cual produciría un desorden lógico, el elemento que era el frente dejaría de estarlo.

La corrección es recorrer desde frente, dando la vuelta con módulo tantas veces como haga falta, y escribir cada elemento en su orden lógico dentro del arreglo nuevo, empezando en la posición 0, para terminar reiniciando frente a 0.

private void redimensionar() {
    Object[] datosNuevos = new Object[datos.length * 2];
    for (int i = 0; i < tamaño; i++) {
        datosNuevos[i] = datos[(frente + i) % datos.length];
    }
    datos = datosNuevos;
    frente = 0;
}
def _redimensionar(self):
    capacidad_vieja = len(self._datos)
    datos_nuevos = [None] * (capacidad_vieja * 2)
    for i in range(self._tamaño):
        datos_nuevos[i] = self._datos[(self._frente + i) % capacidad_vieja]
    self._datos = datos_nuevos
    self._frente = 0

Es el punto donde más se equivoca quien implementa esto por primera vez, así que vale la pena decirlo una vez más de forma directa, redimensionar una cola circular no es System.arraycopy ni un simple recorte de lista, es recorrer en orden lógico, empezando por frente, y volver a escribir desde cero.

12 Complejidad de la cola

Operación Peor caso Amortizado
encolar O(n), cuando toca redimensionar O(1)
desencolar O(1) O(1)
frente O(1) O(1)
estaVacia O(1) O(1)

El razonamiento amortizado es idéntico al que ya viste para la pila, la serie geométrica de las copias de redimensión sucesivas queda acotada por menos de 2n para n encolamientos, así que el costo por operación en promedio sigue siendo O(1), aunque una operación puntual, la que dispara la redimensión, cueste O(n) esa vez.

13 Lo que ArrayDeque y deque ya resuelven en el lenguaje

Lo que construiste hoy no es un ejercicio aislado, es en esencia una versión simplificada de una herramienta que Java y Python ya traen resuelta. El Javadoc de java.util.ArrayDeque, en Java SE 17, describe la clase literalmente como una implementación de arreglo redimensionable de la interfaz Deque, cuyas operaciones principales corren en tiempo constante amortizado, y agrega una recomendación explícita, que es probable que ArrayDeque sea más rápida que Stack cuando se usa como pila, y más rápida que LinkedList cuando se usa como cola, precisamente porque usa un arreglo circular interno en vez de heredar de Vector como hace la vieja Stack, un problema clásico de heredar de una clase concreta en lugar de usar composición.

En Python, collections.deque resuelve el mismo problema desde una implementación distinta, y la documentación oficial aclara la diferencia con una lista común, deque da aproximadamente el mismo rendimiento O(1) en ambos extremos, mientras que una list de Python incurre en costos de movimiento de memoria O(n) para las operaciones pop(0) e insert(0, v). Eso explica por qué una lista de Python es excelente como pila, append y pop al final son O(1) amortizado, pero mala como cola si se intenta usar pop(0) para sacar por el frente, y es exactamente la razón por la que hace falta la disciplina del arreglo circular si se insiste en resolver una cola con un solo arreglo plano en vez de usar deque directamente.
