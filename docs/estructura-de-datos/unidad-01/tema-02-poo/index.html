Autor/a

Unidad Unidad 1. Introducción a las estructuras de datos
Tema Tema 2. Paradigma de programación orientada a objetos

El Tema 1 mostró que un contrato admite varias implementaciones: pila y cola se pueden montar sobre un arreglo o sobre una lista enlazada, y quien usa la pila no necesita saberlo. Hoy construyes la herramienta con la que ese contrato se escribe en código: la clase.

1 El molde y las arepas

Doña Marta también vende arepas hechas en la casa. Tiene un solo molde de metal: un círculo de cierto diámetro con un borde de cierta altura. Con ese molde hace veinte arepas al día, y cada una es un objeto distinto: esta pesa 90 gramos, esa otra 85, una lleva queso y otra no.

El molde no es ninguna arepa. Es la forma que define qué campos tiene una arepa (peso, relleno) y qué se puede hacer con ella (venderla, describirla). Cada arepa que sale del molde es una instancia: ocupa su propio espacio, tiene sus propios valores, y puede cambiar sin afectar a las demás ni al molde.

En programación, el molde es la clase y cada arepa es un objeto. La clase se escribe una sola vez; los objetos se crean tantas veces como haga falta, cada uno con su propio estado.

La misma clase, en los dos lenguajes del curso. Fíjate en qué cambia (la sintaxis) y qué no cambia (la idea: un molde, muchos objetos):

public class Producto {
    private String nombre;
    private double precio;

    public Producto(String nombre, double precio) {
        this.nombre = nombre;
        this.precio = precio;
    }

    public String describir() {
        return nombre + ": $" + precio;
    }

    public static void main(String[] args) {
        Producto arroz = new Producto("arroz", 4200.0);
        Producto leche = new Producto("leche", 3900.0);
        System.out.println(arroz.describir());
        System.out.println(leche.describir());
    }
}
class Producto:
    def __init__(self, nombre, precio):
        self.nombre = nombre
        self.precio = precio

    def describir(self):
        return f"{self.nombre}: ${self.precio}"


arroz = Producto("arroz", 4200)
leche = Producto("leche", 3900)
print(arroz.describir())
print(leche.describir())

arroz y leche son dos objetos de la misma clase Producto. Comparten la forma, no el contenido: cambiar el precio de arroz no toca a leche. La Especificación del Lenguaje Java lo dice en el capítulo 8: una declaración de clase define un nuevo tipo por referencia y especifica cómo se implementa, con sus campos, sus métodos y sus constructores.

2 Encapsulamiento: por qué el TDA esconde sus datos

En el ejemplo de arriba, nombre y precio son private en Java. Eso significa, según el tutorial oficial de Oracle, que solo se pueden acceder desde dentro de la propia clase. Nadie fuera de Producto puede escribir arroz.precio = -500 directamente, porque el campo no es visible desde afuera.

Esto no es una manía del lenguaje. Es la misma idea que el Tema 1 llamó tipo de dato abstracto: el código que usa la pila no cambia si mañana cambia la implementación, porque solo conoce apilar, desapilar, cima y estaVacia, nunca lo que hay por dentro. Con una clase pasa igual: el código que usa Producto solo conoce describir() y los métodos que la clase decida exponer, nunca si por dentro hay un double o una cadena de texto con formato. Esconder los campos y exponer métodos es la forma concreta, en código, de cumplir ese contrato.

Un método público puede además vigilar una regla que un campo público no vigila. Compara:

public class Producto {
    private String nombre;
    private double precio;

    public Producto(String nombre, double precio) {
        this.nombre = nombre;
        fijarPrecio(precio);
    }

    public void fijarPrecio(double precio) {
        if (precio < 0) {
            throw new IllegalArgumentException("el precio no puede ser negativo");
        }
        this.precio = precio;
    }

    public double precio() {
        return precio;
    }
}
class Producto:
    def __init__(self, nombre, precio):
        self.nombre = nombre
        self.fijar_precio(precio)

    def fijar_precio(self, precio):
        if precio < 0:
            raise ValueError("el precio no puede ser negativo")
        self._precio = precio

    def precio(self):
        return self._precio


arroz = Producto("arroz", 4200)
print(arroz.precio())        # 4200
arroz.fijar_precio(-10)      # lanza ValueError: el precio no puede ser negativo

Con precio público, cualquiera podría dejarlo en negativo sin que nada lo impida. Con precio privado y fijarPrecio como único camino para cambiarlo, la regla se cumple siempre, sin importar cuántos archivos usen la clase. Python no impone la privacidad por el compilador como Java: la documentación oficial dice que las variables verdaderamente privadas no existen en Python, y que un nombre con un guion bajo al inicio (_precio) es solo una convención que avisa “esto es un detalle interno, no lo toques directo”. La disciplina es la misma; quien la hace cumplir cambia de lenguaje a lenguaje.

3 Herencia: reutilizar sin repetir

Cuando dos clases comparten campos y métodos, y una de ellas además agrega algo propio, tiene sentido que la segunda herede de la primera en lugar de copiar el código. En Java se escribe con extends; en Python, poniendo la clase base entre paréntesis.

Un ProductoPerecedero es un Producto que además vence en una fecha. Hereda nombre, precio y describir(), y solo agrega lo que le falta:

public class ProductoPerecedero extends Producto {
    private String fechaVencimiento;

    public ProductoPerecedero(String nombre, double precio, String fechaVencimiento) {
        super(nombre, precio);
        this.fechaVencimiento = fechaVencimiento;
    }

    public String fechaVencimiento() {
        return fechaVencimiento;
    }
}
class ProductoPerecedero(Producto):
    def __init__(self, nombre, precio, fecha_vencimiento):
        super().__init__(nombre, precio)
        self.fecha_vencimiento = fecha_vencimiento

super(nombre, precio) (Java) y super().__init__(nombre, precio) (Python) llaman al constructor de Producto para que arme la parte que ya sabe armar. El curso no entra en polimorfismo avanzado ni en patrones de diseño sobre herencia: la carta descriptiva de esta unidad no los pide, y con lo de aquí alcanza para lo que viene.

4 La clase Pila: el contrato de hoy, la memoria de mañana

El Tema 1 definió el contrato de la pila por su comportamiento: apilar, desapilar, consultar la cima y preguntar si está vacía, sin decir si por dentro hay un arreglo o una lista enlazada. Esa decisión es justamente la que la Unidad 2 va a tomar. Hoy escribes la clase vacía por dentro: el contrato en código, sin implementación de memoria todavía.

public class Pila {
    public void apilar(Object elemento) {
        throw new UnsupportedOperationException("llega en la Unidad 2");
    }

    public Object desapilar() {
        throw new UnsupportedOperationException("llega en la Unidad 2");
    }

    public Object cima() {
        throw new UnsupportedOperationException("llega en la Unidad 2");
    }

    public boolean estaVacia() {
        throw new UnsupportedOperationException("llega en la Unidad 2");
    }
}
class Pila:
    def apilar(self, elemento):
        raise NotImplementedError("llega en la Unidad 2")

    def desapilar(self):
        raise NotImplementedError("llega en la Unidad 2")

    def cima(self):
        raise NotImplementedError("llega en la Unidad 2")

    def esta_vacia(self):
        raise NotImplementedError("llega en la Unidad 2")

Las dos clases compilan y corren tal cual: si las llamas, lanzan el error a propósito, porque todavía no hay dónde guardar nada. Lo que sí queda fijo desde hoy son los cuatro nombres y qué recibe y devuelve cada uno. Eso es exactamente lo que la Unidad 2 va a llenar con un arreglo, y la Unidad 3 con una lista enlazada, sin que ninguna de las dos toque esta firma.

TipReto. Diseña el TDA Cola

Diseña la clase Cola con sus operaciones (encolar, desencolar, frente, esta_vacia o estaVacia), en Java o en Python, el que prefieras. Solo la interfaz: sin decidir todavía si por dentro hay un arreglo o una lista enlazada, igual que hicimos con Pila.

Cuando termines, responde en una frase: ¿por qué el encapsulamiento te deja cambiar de opinión más adelante sobre cómo se guarda la memoria de la cola, sin que se rompa el código que ya la usa?
