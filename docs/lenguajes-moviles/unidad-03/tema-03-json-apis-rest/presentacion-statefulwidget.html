Predice antes de ejecutar

¿Qué lees después de tres toques?

class ContadorRoto extends StatelessWidget {
  const ContadorRoto({super.key});

  @override
  Widget build(BuildContext context) {
    int cuenta = 0;
    return TextButton(
      onPressed: () {
        cuenta = cuenta + 1;
        debugPrint('cuenta vale $cuenta');
      },
      child: Text('Llevas $cuenta'),
    );
  }
}

La app muestra un botón con Llevas 0. Lo tocas tres veces. ¿Qué dice el botón?

Dice Llevas 0, siempre. La variable sí cambia en memoria (la consola imprime 1, 2 y 3), pero hay dos razones por las que la pantalla no se entera: nadie le pidió a Flutter que dibuje de nuevo, y aunque build corriera otra vez, volvería a ejecutar int cuenta = 0; y arrancaría en cero.

Modelo mental

El estado es un dato que cambia

EstadoLa memoria de la pantalla
El estado es un dato que cambia mientras la pantalla está viva y que la pantalla debe mostrar.
El marcador de un partido: el número cambia y el tablero tiene que mostrar el nuevo.
La cantidad en la canasta, si la lista está cargando, el texto de un campo.
Llamar estado a todo. El título de la app no cambia: es un texto fijo.

Dos preguntas

  1. ¿Este dato puede cambiar mientras la persona usa la pantalla?
  2. Si cambia, ¿la pantalla tiene que verse distinta?
Si las dos respuestas son sí, es estado.

Analogía

Menú impreso o pizarra

La analogíaDos formas de mostrar un precio
Un StatelessWidget se dibuja con lo que recibe. Para mostrar otro dato hay que construir otro widget.
Menú impreso: si sube el tomate, imprimes otro menú. Pizarra: borras el precio y escribes el nuevo en la misma pizarra.
Pensar que la pizarra es "mejor". Si el precio nunca cambia, el menú impreso es más simple y suficiente.

Modelo mental

Dos clases: el widget y su State

Por qué dosUna se recrea, la otra vive
Flutter crea widgets nuevos con mucha frecuencia: son baratos y no cambian. El State se crea una vez y se conserva mientras la pantalla viva.
El widget es el marco de la pizarra, que se puede cambiar por otro igual. El State es lo escrito en ella.
Guardar cuenta en la clase del widget: sus campos son final y el widget se recrea.
class Contador extends StatefulWidget {
  const Contador({super.key});

  @override
  State<Contador> createState() => _ContadorState();
}

class _ContadorState extends State<Contador> {
  int cuenta = 0;

  @override
  Widget build(BuildContext context) {
    return Text('Llevas $cuenta');
  }
}

Segundo ejemplo

Un bool que se invierte

El operador !Invierte un bool
!esFavorito es lo contrario de esFavorito: si era false da true, y al revés.
esFavorito ? Icons.favorite : Icons.favorite_border elige el ícono según el valor.
Cambiar el bool sin setState: el valor cambia y el corazón no.

Toca el corazón.

class _FavoritoState extends State<Favorito> {
  bool esFavorito = false;

  @override
  Widget build(BuildContext context) {
    return IconButton(
      onPressed: () {
        setState(() {
          esFavorito = !esFavorito;
        });
      },
      icon: Icon(
        esFavorito ? Icons.favorite : Icons.favorite_border,
      ),
    );
  }
}

Predice antes de ejecutar

¿Cuántas veces corre build?

@override
void initState() {
  super.initState();
  debugPrint('initState: la pantalla nació');
}

@override
void dispose() {
  debugPrint('dispose: la pantalla murió');
  super.dispose();
}

@override
Widget build(BuildContext context) {
  debugPrint('build: dibujando con cuenta = $cuenta');
  return TextButton(onPressed: sumar, child: Text('Llevas $cuenta'));
}

Abres la pantalla, tocas el botón dos veces (cada toque llama a sumar) y vuelves atrás. ¿Cuántas veces imprime la consola build:?

3: una al nacer la pantalla y una por cada setState. initState corrió una vez y dispose una vez, al volver atrás.

Simulación

Un State nace, vive y muere

Tres momentosinitState, build, dispose
initState corre una vez al nacer. build corre muchas veces. dispose corre una vez al morir.
Abrir el puesto, atender todo el día, cerrar y apagar las luces.

Criterio

¿Hace falta un StatefulWidget?

Elige para cada pantalla

Nace como StatelessWidget. Pasa a StatefulWidget cuando aparece un dato que cambia y se ve.

Comparación

Antes de cerrar

Seis errores que reconocerás

Declarar el dato dentro de buildEl contador vuelve a 0 en cada build
Declara int cuenta = 0; en la clase State, fuera de build.
Cambiar el dato sin setStateLa consola cambia y la pantalla no
setState(() { cuenta = cuenta + 1; });
Llamar setState mientras se dibujaDentro de build no sirve, y en un hijo lanza error
Llama a setState desde un evento, como onPressed. Si un hijo llama el setState del padre mientras se dibuja, Flutter lanza: setState() or markNeedsBuild() called during build.
No liberar el controladorNo hay error visible, pero queda memoria ocupada
En dispose: controlador.dispose(); y después super.dispose();.
Poner super en el lugar equivocadoFlutter lo exige primero o al final
super.initState(); va primero en initState. super.dispose(); va al final de dispose.
Llamar setState cuando la pantalla ya se cerróPasa después de un await
Después de cada await y antes de setState: if (!mounted) return;. Se explica con await en la Parte 4 de la guía.
