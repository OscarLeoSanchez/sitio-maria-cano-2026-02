Diapositivas de la sesión

La Unidad 2 cerró con el navegador convertido en un taller completo de depuración, un concepto claro de para qué sirve empaquetar código con un bundler, y un criterio de diseño, mobile-first, que aplica sin importar qué framework termine usando el proyecto. También dejó fijada la decisión que abre esta unidad, el framework de interfaz de la Unidad 3 es Flutter, con React como punto de comparación. Antes de escribir la primera línea de código con Flutter conviene recorrer el terreno completo en el que se mueve, porque Flutter responde a un problema que no nace con él, cómo construir una aplicación que llegue a varias plataformas sin escribir el mismo trabajo varias veces. Este primer tema de la Unidad 3 recorre ese terreno en dos partes. La primera compara las tres estrategias que existen hoy para lograr multiplataforma, con qué se escribe cada una y qué gana y qué pierde frente a las otras. La segunda profundiza en la Progressive Web App, la variante que corre dentro del propio navegador, retomando desde donde la Unidad 1 dejó sus tres requisitos para llegar a construir un ejemplo real que se instala y funciona sin conexión.

1 Multiplataforma no es una sola idea, son tres caminos distintos

Construir software multiplataforma para móviles significa que una misma aplicación llega a más de un sistema operativo, casi siempre Android e iOS, sin escribir un proyecto completamente independiente para cada uno. El problema que resuelve es de fondo económico y de tiempo, ya que las dos plataformas dominantes exponen lenguajes, kits de desarrollo y patrones de interfaz distintos entre sí, así que un equipo que quiere atender a ambas se enfrenta de entrada a la pregunta de cuánto código puede compartir entre ellas sin sacrificar lo que cada una hace mejor.

Existen hoy tres respuestas distintas a esa pregunta, y cada una se ubica en un punto diferente entre dos extremos, escribir el máximo código posible una sola vez, o aprovechar al máximo lo que cada plataforma ofrece por separado.

La primera es el desarrollo nativo, que escribe un proyecto distinto para cada sistema operativo con el lenguaje y el kit de desarrollo propios de esa plataforma, Kotlin o Java con el SDK de Android, y Swift u Objective-C con el SDK de iOS. Cada aplicación corre directamente sobre las herramientas que el fabricante de la plataforma diseñó para ella, sin ninguna capa intermedia entre el código y el sistema operativo.

La segunda es el desarrollo híbrido, que empaqueta una aplicación web dentro de un contenedor nativo instalable desde la tienda de aplicaciones. Apache Cordova documenta su propia arquitectura como una ventana de navegador especial, el WebView, que sirve de contenedor para la interfaz de la aplicación, y dentro de esa ventana corre el código HTML, CSS y JavaScript del proyecto igual que correría en cualquier sitio web. Cuando la aplicación necesita algo que el navegador no expone por sí solo, cámara, sensores, estado de la batería, un plugin actúa de puente entre el código JavaScript y el componente nativo correspondiente, ya que un WebView por sí mismo no tiene acceso directo a esas capacidades del dispositivo. Capacitor, el sucesor espiritual de Cordova según su propia documentación, sigue la misma idea de fondo con una forma distinta de empaquetar los plugins como librerías nativas del proyecto en vez de copiar su código fuente.

La tercera es la multiplataforma con compilación real, que escribe un único código fuente en el lenguaje del framework y ese código compila a elementos de interfaz nativos en cada plataforma, sin pasar por un WebView. Flutter, que la propia documentación oficial describe como un kit de herramientas de interfaz portátil para crear aplicaciones compiladas de forma nativa desde una sola base de código, es el representante de esta estrategia que trabaja el Tema 2. React Native sigue el mismo principio general con otra tecnología de base.

Ninguna de las tres estrategias es superior en abstracto, cada una ordena las cuatro preguntas de la tabla de un modo distinto según lo que el proyecto necesite. Una aplicación bancaria que depende de lectores biométricos y de animaciones muy exigentes probablemente justifica el costo de mantener dos bases nativas. Un catálogo de productos que ya existe como sitio web y solo necesita llegar a las tiendas de aplicaciones sin gastar mucho tiempo puede resolverse bien con un contenedor híbrido. Y un proyecto que quiere una sola base de código con una experiencia visual cercana a la nativa, sin duplicar el trabajo por plataforma, es el terreno de la multiplataforma con compilación real que Flutter trabaja en el Tema 2.

Un banco encarga una aplicación con lector de huella dactilar, notificaciones push confiables en Android y en iOS, y animaciones fluidas para un lector de código QR en tiempo real. El banco tiene presupuesto para mantener dos equipos de desarrollo trabajando en paralelo. Antes de leer la solución, marca la estrategia que mejor responde a esos requisitos:

NotaSolución del Reto 1

La respuesta correcta es desarrollo nativo. El requisito que descarta al híbrido es el rendimiento de las animaciones en tiempo real del lector de código QR, porque un WebView agrega una capa entre el código y el hardware que penaliza justo ese tipo de tarea, y el requisito que hace innecesaria la multiplataforma compilada es que el banco ya tiene presupuesto para dos equipos, así que no necesita ahorrar el costo de mantener dos bases de código, que es la ventaja principal que ofrecen tanto el híbrido como la multiplataforma compilada.

Si el banco no tuviera ese presupuesto extra, la respuesta razonable cambiaría hacia una multiplataforma con compilación real, porque el acceso a hardware como el lector de huella sigue siendo amplio a través de paquetes del framework, y el rendimiento queda mucho más cerca del nativo que en un WebView.

2 Progressive Web Apps: retomando los tres requisitos

La Unidad 1 ya presentó la Progressive Web App como la variante que se construye enteramente con tecnologías de la plataforma web y que instala, opera sin conexión y se integra con el sistema operativo, con sus tres requisitos sumándose entre sí, un manifiesto web, un servicio por HTTPS y un service worker registrado. Esta sección no repite esa base, la profundiza, entra en el contenido concreto de cada uno de esos tres requisitos hasta el punto de poder construir y probar una PWA real y mínima.

El manifiesto web app

El manifiesto es un archivo JSON que describe la aplicación al navegador y al sistema operativo, y se enlaza desde el HTML con una etiqueta <link rel="manifest">. MDN documenta más de veinte campos posibles dentro de ese archivo, y en la especificación técnica todos son opcionales, pero en la práctica un navegador solo ofrece instalar la aplicación cuando el manifiesto trae un conjunto mínimo de esos campos completos. Conviene agruparlos según lo que resuelven en vez de memorizarlos todos sueltos.

El grupo de identidad cubre name, el nombre completo que aparece en la pantalla de presentación al abrir la aplicación, y short_name, la versión corta que se muestra debajo del ícono en la pantalla de inicio cuando el nombre completo no cabe. El grupo de apariencia cubre icons, un arreglo de imágenes en distintos tamaños que el sistema operativo usa según el contexto, display, que en modo standalone hace que la aplicación abra sin la barra de direcciones del navegador, y theme_color junto con background_color, que pintan la pantalla de presentación mientras la aplicación termina de cargar. El grupo de navegación cubre start_url, la página con la que abre la aplicación instalada, y scope, el conjunto de rutas que la aplicación considera parte de sí misma, de forma que un enlace que salga de ese alcance abre en el navegador normal en vez de dentro de la aplicación instalada.

El service worker

MDN documenta el service worker como un worker de JavaScript dirigido por eventos que actúa de proxy entre la aplicación, el navegador y la red. Corre en un hilo separado de la página, sin acceso al DOM, se registra contra un origen y una ruta concretos con navigator.serviceWorker.register(), y solo funciona dentro de un contexto seguro, ya sea HTTPS o http://localhost durante el desarrollo.

Su ciclo de vida pasa por tres eventos. El evento install se dispara cuando el navegador descarga una versión nueva del archivo del service worker, y es el momento típico para abrir una caché y guardar en ella los archivos que la aplicación va a necesitar sin conexión. El evento activate se dispara una vez la instalación termina, y es el momento típico para borrar cachés de versiones anteriores que ya no hacen falta. El evento fetch se dispara cada vez que la página pide un recurso, imágenes, hojas de estilo, el propio HTML, y el service worker puede interceptar esa petición con FetchEvent.respondWith() para decidir de dónde sale la respuesta, en vez de dejar que el navegador vaya directo a la red.

Esa decisión de dónde sale la respuesta admite más de un orden posible, y dos de los más comunes tienen nombre propio en la documentación de Chrome for Developers sobre estrategias de caché para service workers, cache-first y network-first.

Cache-first revisa primero la caché y solo va a la red si el recurso no está guardado, así que responde de inmediato cuando ya lo tiene y funciona igual con o sin conexión, la estrategia que Chrome for Developers recomienda para archivos estáticos, hojas de estilo, scripts, imágenes, que no cambian con frecuencia. Network-first invierte el orden, intenta la red primero para traer siempre el dato más reciente y solo cae a la caché cuando la red falla, la estrategia recomendada para contenido que cambia seguido, como una respuesta de una API o el HTML de una página con datos en vivo. Ninguna de las dos es universalmente mejor, la elección depende de si el recurso concreto prioriza velocidad y disponibilidad sin conexión, o prioriza estar siempre actualizado.

Una aplicación de noticias sirve dos tipos de recurso, el logo del periódico, que casi nunca cambia, y el texto de las noticias del día, que cambia constantemente a medida que se publican actualizaciones. Antes de leer la solución, marca la estrategia que conviene para cada recurso:

NotaSolución del Reto 2

El logo debe servirse con cache-first y el texto de las noticias con network-first. El logo casi nunca cambia, así que no tiene sentido esperar a la red cada vez que se necesita, cache-first lo entrega de inmediato desde la primera visita en adelante. El texto de las noticias es justo lo contrario, un usuario que abre la aplicación espera ver la última actualización disponible, así que network-first intenta la red primero y solo cae a la copia guardada si la conexión falla, en vez de arriesgarse a mostrar una noticia desactualizada cuando sí hay red disponible.

HTTPS y el contexto seguro

El tercer requisito, servir la aplicación por HTTPS, no es una recomendación aparte de las otras dos, es la condición que hace posible registrar el service worker. MDN define un contexto seguro como una ventana o un worker que cumple unos estándares mínimos de autenticación y confidencialidad, pensado para que un atacante que intercepta la conexión, un ataque de intermediario o MITM (del inglés man in the middle), no pueda leer ni alterar lo que viaja entre el navegador y el servidor. Como el service worker puede interceptar cada petición de red que hace la página, registrar uno sobre una conexión sin cifrar abriría una puerta enorme para ese tipo de ataque, así que el navegador simplemente no lo permite. La única excepción documentada es http://localhost, que cuenta como contexto seguro sin necesitar certificado, pensada para que el desarrollo local no dependa de configurar HTTPS antes de poder probar nada.

3 Construye un ejemplo real y mínimo de PWA

Con los tres requisitos ya explicados en detalle, esta sección construye una PWA mínima que cumple los tres, una página que se llama “Guía de bolsillo”, con un manifiesto que la hace instalable y un service worker que la deja funcionando sin conexión.

El manifiesto declara la identidad, la apariencia y el alcance de navegación, con un solo ícono en formato SVG para mantener el ejemplo autocontenido sin depender de generar varios tamaños de PNG:

{
  "name": "Guía de bolsillo",
  "short_name": "Guía",
  "start_url": "./index.html",
  "scope": "./",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#12324f",
  "icons": [
    {
      "src": "icon.svg",
      "sizes": "any",
      "type": "image/svg+xml"
    }
  ]
}

El HTML enlaza ese manifiesto y registra el service worker apenas carga la página, comprobando antes que el navegador soporte la API:

<!DOCTYPE html>
<html lang="es">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Guía de bolsillo</title>
  <link rel="manifest" href="manifest.json">
  <meta name="theme-color" content="#12324f">
</head>
<body>
  <h1>Guía de bolsillo</h1>
  <p id="estado">Comprobando el service worker...</p>
  <script>
    const estado = document.getElementById("estado");
    if ("serviceWorker" in navigator) {
      navigator.serviceWorker.register("sw.js")
        .then(() => {
          estado.textContent = "Service worker registrado.";
        })
        .catch((error) => {
          estado.textContent = "No se pudo registrar el service worker: " + error;
        });
    } else {
      estado.textContent = "Este navegador no soporta service workers.";
    }
  </script>
</body>
</html>

Y el service worker sigue la estrategia cache-first explicada arriba, precarga los tres archivos durante install y responde desde la caché en cada fetch, cayendo a la red solo si el recurso no está guardado:

// Service worker mínimo: cache-first para que la página cargue sin conexión.
const CACHE_NOMBRE = "guia-bolsillo-v1";
const ARCHIVOS_A_CACHEAR = [
  "./",
  "./index.html",
  "./manifest.json",
  "./icon.svg"
];

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NOMBRE).then((cache) => cache.addAll(ARCHIVOS_A_CACHEAR))
  );
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys().then((nombres) => {
      return Promise.all(
        nombres
          .filter((nombre) => nombre !== CACHE_NOMBRE)
          .map((nombre) => caches.delete(nombre))
      );
    })
  );
});

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((respuestaCacheada) => {
      return respuestaCacheada || fetch(event.request);
    })
  );
});

Este ejemplo se probó completo con un navegador automatizado en vez de darlo por bueno solo por lectura del código. Primero se validó la sintaxis de los tres archivos, el JSON del manifiesto parsea sin error, el JavaScript del service worker pasa la verificación de sintaxis de Node, y el HTML se parsea sin excepciones. Después se cargó la página con un servidor local, se confirmó que el service worker quedaba registrado y que Cache Storage guardaba los cuatro recursos, y finalmente se simuló la pérdida de conexión y se recargó la página. La salida real de esa última prueba confirma que el contenido de la caché coincide con lo esperado y que la página sigue respondiendo:

"cacheContents": {
  "guia-bolsillo-v1": [
    "http://localhost:8912/",
    "http://localhost:8912/index.html",
    "http://localhost:8912/manifest.json",
    "http://localhost:8912/icon.svg"
  ]
}
"offlineReloadOk": true
"offlineTitle": "Guia de bolsillo"

Puedes abrir el ejemplo completo, Guía de bolsillo, directamente en el navegador. Cárgalo primero con conexión para que el service worker precargue la caché y después prueba a recargarlo sin conexión, tal como se describió en la prueba anterior.

4 Caso de estudio: Twitter Lite

Twitter, la red social hoy conocida como X, enfrentaba en 2017 una tensión entre dos objetivos. Quería llegar a mercados emergentes donde buena parte de los usuarios navega con conexiones lentas y dispositivos de gama baja, pero su aplicación nativa de Android pesaba 23,5 megabytes para instalar, un costo alto de datos y de espacio para alguien con una conexión limitada. Antes de seguir, conviene preguntarse qué gana Twitter si construye una Progressive Web App en vez de seguir invirtiendo solo en mejorar la aplicación nativa.

La respuesta, documentada en el caso de estudio oficial publicado en web.dev, es que Twitter Lite se convirtió en la experiencia web móvil por defecto para todos los usuarios en abril de 2017, con un peso de apenas 600 kilobytes por la red frente a los 23,5 megabytes de la aplicación nativa. Los resultados medidos después del lanzamiento incluyeron un aumento del 65% en páginas vistas por sesión, un aumento del 75% en tweets enviados y una reducción del 20% en la tasa de rebote, además de una reducción de hasta el 70% en el consumo de datos gracias a la optimización de imágenes. La página cargaba en menos de 5 segundos incluso sobre una red 3G, y las cargas posteriores eran casi instantáneas gracias al service worker cacheando los recursos ya vistos.

Métrica Resultado reportado
Peso de instalación 600 KB (PWA) frente a 23,5 MB (app nativa de Android)
Páginas vistas por sesión Aumento del 65%
Tweets enviados Aumento del 75%
Tasa de rebote Reducción del 20%
Consumo de datos por imágenes Reducción de hasta el 70%

El manifiesto y el service worker que acabas de construir en el ejemplo mínimo son, en esencia, la misma maquinaria detrás de estos números: una aplicación liviana, instalable y que sigue respondiendo con datos guardados cuando la red falla o es lenta.

5 Un paso más allá del navegador

Todo lo que viste hoy, el manifiesto, el service worker y sus estrategias de caché, corre dentro del navegador y depende de lo que la plataforma web decida exponer en cada versión. El Tema 2 construye con Flutter una aplicación que compila a interfaz nativa real en cada plataforma, sin pasar por un navegador en ningún punto, un paso más allá de lo que una PWA puede ofrecer dentro de ese entorno, con acceso directo al SDK de cada sistema operativo y sin las limitaciones de soporte desigual entre navegadores que ya viste en la Unidad 1 para notificaciones push y sensores.
