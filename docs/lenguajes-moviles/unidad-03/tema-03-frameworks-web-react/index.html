Tema Tema 3. Qué resuelve un framework web, y cómo React lo resuelve distinto de Flutter

Diapositivas de la sesión

El Tema 2 construyó una aplicación real con Flutter, un solo código en Dart que compila directo a interfaz nativa en Android, iOS y web, con widgets, con la diferencia entre StatelessWidget y StatefulWidget, y con el hot reload como forma de ver cada cambio sin reiniciar la aplicación. Hoy das un paso atrás antes de cerrar, primero para entender en general qué resuelve cualquier framework de desarrollo web que no resolverías escribiendo HTML, CSS y JavaScript a mano, y con qué criterios un equipo elige uno para un proyecto concreto, el mismo criterio que ya aplicó el docente cuando decidió construir esta unidad con Flutter en lugar de Angular o React, tal como los nombraba la carta descriptiva original de este curso. Segundo, miras React en sus conceptos centrales, comparado punto por punto contra lo que ya conoces de Flutter, para que la comparación funcione como espejo y no como contenido nuevo aislado. Con este tema cierra la Unidad 3 y el curso completo, así que la última sección conecta las tres unidades en una sola idea.

1 Qué resuelve un framework, y con qué criterio se elige uno

Escribir una interfaz de usuario a mano con HTML, CSS y JavaScript puro es perfectamente posible, y de hecho así se construyeron las primeras páginas web durante años. El problema aparece cuando esa interfaz crece, cuando tiene partes que se repiten en varias pantallas, datos que cambian y que la pantalla tiene que reflejar sin que el programador escriba a mano cada actualización del DOM, y un equipo de varias personas que necesita entender rápido el código de otra persona. MDN Web Docs lo resume al presentar a React, el objetivo principal de un framework como React es reducir los errores que aparecen al construir interfaces de usuario, y lo logra con componentes, piezas de código autocontenidas y con un propósito claro que describen una porción de la interfaz y que se combinan entre sí para armar la pantalla completa. El framework se encarga de la parte repetitiva de dibujar y actualizar esa interfaz, y deja al programador concentrado en decidir qué debe mostrar cada componente, no en cómo escribir cada línea de DOM que lo logra.

Elegir un framework concreto para un proyecto no es una decisión que se tome por moda, ni por cuál suena mejor en una entrevista de trabajo. Un equipo que decide bien revisa al menos cinco criterios. La familiaridad del equipo pesa porque un framework que el equipo ya conoce reduce el riesgo de entregar tarde, aunque no sea el más nuevo del mercado. El ecosistema y la disponibilidad de bibliotecas importa porque pocas aplicaciones se construyen desde cero, así que conviene que ya existan piezas resueltas para lo común, autenticación, formularios, componentes visuales. La curva de aprendizaje determina cuánto tiempo pasa antes de que una persona nueva en el equipo sea productiva con ese framework. Las necesidades de rendimiento del proyecto concreto, si la aplicación anima gráficos complejos o mueve datos pesados en tiempo real, pesan distinto que en una aplicación de formularios sencillos. Y las plataformas objetivo, si el proyecto necesita llegar a Android, a iOS, a la web o a las tres a la vez, decide de entrada qué frameworks quedan siquiera en la conversación.

Esos cinco criterios ya se aplicaron una vez en este curso, y en un caso real. La carta descriptiva de esta asignatura nombra literalmente Angular y React como los temas de esta unidad, que ella misma titula desarrollo web multiplataforma. El docente decidió construir la unidad con Flutter en su lugar, porque las plataformas objetivo del curso son Android e iOS de forma nativa, y porque Flutter resuelve eso sin depender de una capa adicional, la razón técnica exacta aparece más adelante en este tema. React se conserva mencionado como punto de comparación, para que conozcas la misma idea de componentes resuelta desde otra filosofía, y Angular queda como referencia de contexto, sin ser la base de ninguna entrega del curso.

2 React en sus conceptos centrales, con Flutter como espejo

React se presenta en su propia documentación oficial con una frase corta, React es la biblioteca para interfaces de usuario web y nativas (en inglés, the library for web and native user interfaces), y agrega que construyes esas interfaces a partir de piezas individuales llamadas componentes, escritas en JavaScript. Esa idea de piezas pequeñas que se combinan es exactamente la misma que ya usaste en Flutter con los widgets del Tema 2, aunque cada framework la implementa con su propia sintaxis y su propio mecanismo por dentro. Tres conceptos concretos dejan ver dónde se parecen y dónde no.

El componente como función que retorna JSX

En Flutter, un widget describe su apariencia dentro del método build, que retorna el árbol de widgets que representa esa parte de la pantalla. En React, un componente es, según lo explica MDN Web Docs, un módulo reutilizable que renderiza una parte de la aplicación completa, y en la práctica más común se escribe como una función de JavaScript que retorna JSX. React.dev define JSX como una extensión de sintaxis para JavaScript que permite escribir marcado parecido a HTML dentro de un archivo JavaScript, de forma que la estructura de la interfaz queda descrita casi como si fuera HTML, aunque en realidad se traduce a código JavaScript antes de ejecutarse.

Con la comparación ya dibujada, un ejemplo mínimo de código JSX real deja ver la sintaxis. Este componente toma un nombre como propiedad y lo muestra dentro de un encabezado, tal como lo describe MDN Web Docs en su guía de introducción a React:

function Saludo({ nombre }) {
  return <h1>Hola, {nombre}</h1>;
}

Saludo es una función normal de JavaScript, no una clase, y { nombre } extrae la propiedad nombre que recibe el componente. La parte entre <h1> y </h1> es JSX, se ve como HTML pero es JavaScript, y las llaves dentro de {nombre} dejan insertar el valor de una variable en medio del marcado, algo parecido a lo que en Flutter harías al interpolar una variable dentro de un Text.

El estado con useState, frente a setState

El Tema 2 ya mostró que un StatefulWidget guarda su propio estado y que llamar a setState le avisa a Flutter que debe reconstruir ese widget con el nuevo valor. React resuelve el mismo problema con una función llamada useState, uno de los hooks de React, funciones especiales que dejan engancharse a capacidades de React desde un componente escrito como función. React.dev explica el problema que resuelve useState con dos puntos concretos, una variable común de JavaScript declarada dentro de un componente no conserva su valor entre un renderizado y el siguiente, porque React vuelve a ejecutar la función completa desde cero cada vez, y cambiar una variable común tampoco le avisa a React que debe volver a dibujar la pantalla. useState resuelve ambos problemas a la vez, entrega una variable de estado que sí se conserva entre renderizados, y una función para actualizarla que, al llamarse, le indica a React que debe volver a ejecutar el componente con el nuevo valor.

Con el mecanismo ya comparado, un contador mínimo en JSX deja ver la sintaxis completa de useState, la versión web del mismo contador que el Tema 2 construyó en Flutter:

import { useState } from 'react';

function Contador() {
  const [conteo, setConteo] = useState(0);

  function incrementar() {
    setConteo(conteo + 1);
  }

  return (
    <div>
      <p>Has presionado el botón {conteo} veces</p>
      <button onClick={incrementar}>Incrementar</button>
    </div>
  );
}

useState(0) entrega dos cosas a la vez, el valor actual, conteo, que arranca en 0, y la función para actualizarlo, setConteo. Cada vez que el usuario hace clic en el botón, incrementar llama a setConteo con el valor siguiente, y esa llamada hace que React vuelva a ejecutar Contador con el nuevo conteo, exactamente el mismo efecto que produce setState en el StatefulWidget del Tema 2, aunque la forma de escribirlo sea distinta, un arreglo con dos posiciones en vez de un método que envuelve el cambio.

El DOM virtual, frente al motor de renderizado propio de Flutter

El tercer concepto es el que más distingue a los dos frameworks por dentro. React necesita actualizar el DOM real del navegador cada vez que algo cambia en la pantalla, pero manipular el DOM real es una operación relativamente costosa si se hace sin cuidado. Para resolverlo, React mantiene lo que se conoce como DOM virtual, una estructura de datos en memoria parecida al DOM real. Cuando el estado de un componente cambia, React construye una nueva versión de esa estructura en memoria, la compara contra la versión anterior en un proceso llamado reconciliación, y aplica sobre el DOM real del navegador únicamente las diferencias que encontró, en vez de reconstruir toda la página desde cero. El DOM virtual no reemplaza al DOM real, es un paso intermedio que calcula el cambio mínimo necesario antes de tocarlo.

Flutter, que el Tema 2 ya presentó, resuelve el mismo problema sin pasar nunca por un DOM, porque no corre dentro de un navegador. Flutter trae su propio motor de renderizado, que dibuja cada widget directamente como píxeles en la pantalla del dispositivo, sin ninguna representación intermedia parecida al DOM que un navegador tendría que interpretar. Son dos estrategias distintas para resolver el mismo objetivo, actualizar la pantalla de forma eficiente cuando algo cambia, una compara y aplica diferencias sobre un DOM, la otra dibuja directamente sin que exista ningún DOM de por medio.

3 Por qué React necesita React Native, y Flutter no

Todo lo que viste en la sección anterior, componentes, JSX, useState y el DOM virtual, describe a React tal como corre dentro de un navegador, produciendo elementos de un DOM que existe porque hay un navegador interpretándolo. Eso deja a React limitado a la web por sí solo, así que para construir una aplicación móvil nativa con esos mismos conceptos, un equipo necesita adoptar React Native, un proyecto relacionado con React pero técnicamente distinto, con su propia documentación y sus propios componentes, que ya no son div ni h1 sino equivalentes pensados para móvil, como View en vez de div. El propio sitio oficial de React Native resume su idea central con la frase aprende una vez, escribe donde quieras (en inglés, learn once, write anywhere), y aclara un punto importante, la interfaz de una aplicación construida con React Native se dibuja con componentes nativos, no con una vista web incrustada, así que el resultado se ve y se siente como una aplicación nativa de verdad. Lo que se traslada de React a React Native es el conocimiento, componentes, propiedades, estado y hooks, la forma de pensar la interfaz como una función de los datos, pero no el código exacto que escribiste para la web, porque ese div que usabas todo el tiempo simplemente no existe en React Native. Si en algún momento de tu carrera quieres profundizar en cómo React llega a nativo con este puente, React Native es un tema aparte que se estudia por su cuenta, este curso no entra en su detalle.

Flutter resuelve el mismo objetivo, llegar a Android y a iOS con una sola base de código, sin necesitar ningún proyecto puente. El mismo código en Dart que el Tema 2 usó para construir la aplicación del curso compila directo a código de máquina nativo en cada plataforma, sin pasar por un DOM, sin depender de un navegador ni de una vista web, y sin necesitar un segundo framework distinto para llegar a móvil. Esa diferencia, un solo framework que compila directo contra dos frameworks encadenados, React más React Native, es la razón técnica de fondo detrás de la decisión del docente de construir esta unidad con Flutter en vez de React.

4 Cierre de la Unidad 3

Con este tema termina la Unidad 3. El Tema 1 mostró el espectro completo de estrategias para construir software para móvil desde la web, de sitio responsivo a app nativa, con la Progressive Web App como el punto donde un sitio empieza a instalarse y a funcionar sin conexión sobre la misma base de HTML, CSS y JavaScript. El Tema 2 tomó una decisión concreta dentro de ese espectro y la llevó hasta el final, Flutter, con una aplicación real construida, widgets, estado y hot reload como el ciclo de trabajo diario. Hoy diste un paso atrás para entender por qué existe cualquier framework en primer lugar, con qué criterios se elige uno, y miraste React como la comparación que deja ver la misma idea de componentes resuelta de otra forma, con JSX en vez de un método build, con useState en vez de setState, con un DOM virtual en vez de un motor de renderizado propio, y con React Native como el proyecto aparte que React necesita para llegar a donde Flutter llega directo.

5 Cierre del curso

Con este tema terminan las tres unidades de Lenguajes de computación para móviles. La Unidad 1 mostró de qué está hecho un dispositivo móvil por dentro, sus componentes físicos, su procesador optimizado para consumo antes que para potencia bruta, sus sensores y su sistema operativo, y qué límites físicos y de sistema operativo le impone a cualquier aplicación, memoria, batería y un ciclo de vida que el programador no controla del todo. La Unidad 2 dio las herramientas de trabajo con las que se construye y se depura ese software, la línea de comandos, Git y GitHub para guardar y compartir el historial de un proyecto, y el navegador convertido en taller completo de depuración con Chrome DevTools. La Unidad 3 cerró con las estrategias y los frameworks concretos para construir la interfaz, del espectro completo entre sitio web y app nativa hasta un framework concreto elegido con criterio, terminando en Flutter como la herramienta con la que el curso construyó su primera aplicación real, con React como la comparación que deja ver la misma idea resuelta desde otra filosofía.

La idea que conecta las tres unidades es una sola. El dispositivo impone límites físicos que ninguna línea de código cambia, batería que se agota, memoria que no es infinita, un sistema operativo que decide cuándo tu aplicación sigue corriendo y cuándo se detiene. Las herramientas de trabajo hacen manejable el esfuerzo diario de escribir, depurar y compartir ese código, para que ese límite no se vuelva además un caos de trabajo desorganizado. Y el framework que elijas, con el criterio que viste hoy, decide cuánto de ese límite físico y de ese trabajo diario maneja por ti y cuánto te toca a ti resolver a mano, la misma decisión, con el mismo criterio, que ya tomó este curso al elegir Flutter para construir su primera aplicación real.
