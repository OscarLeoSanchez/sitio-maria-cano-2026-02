Unidad Unidad 2. Herramientas de trabajo en desarrollo de aplicaciones para dispositivos móviles
Tema Tema 1. Entorno de trabajo y línea de comandos

Hasta ahora este curso se movió en el terreno de los conceptos, los lenguajes y los paradigmas que hacen posible una aplicación móvil. Esta unidad cambia de terreno y entra al taller donde de verdad se construye software, con las herramientas que vas a abrir todos los días del resto de tu carrera. El primer tema de esa caja de herramientas es el que más se subestima porque parece el más básico, la terminal y la línea de comandos, junto con los gestores de paquetes que instalan lo que tu código necesita, los editores e IDE (entorno de desarrollo integrado por sus siglas en inglés, integrated development environment) donde ese código se escribe, y los comandos que te dejan moverte por el sistema operativo y controlar lo que corre en él sin soltar el teclado.

1 La terminal, el shell y la línea de comandos

Estas tres palabras se usan como sinónimos en la conversación diaria, pero MDN (siglas del inglés Mozilla Developer Network), la documentación de Mozilla para desarrollo web, las distingue con precisión porque son tres cosas distintas que trabajan juntas. Vale la pena separarlas antes de tocar un solo comando.

  • La terminal es el programa que abres, la ventana con fondo oscuro y texto monoespaciado que ves en la pantalla. Existe como interfaz de texto para ejecutar programas desde hace décadas y hoy está disponible en todos los sistemas operativos modernos, incluidos los móviles.
  • El shell es la sesión que corre dentro de esa ventana, con su propio prompt personalizable, sus atajos de teclado y sus variables de entorno. Dos terminales distintas pueden abrir el mismo shell, y un mismo shell se puede configurar de formas muy distintas según quien lo use.
  • La línea de comandos es el renglón exacto donde escribes, el lugar donde parpadea el cursor esperando la siguiente instrucción.

En Windows conviven varios shells a la vez, y no todos ofrecen lo mismo. cmd, el intérprete de comandos más antiguo, carece de paridad con las herramientas Unix que vas a encontrar en casi cualquier tutorial de desarrollo móvil. MDN recomienda para Windows usar WSL, el subsistema de Windows para Linux (siglas del inglés Windows Subsystem for Linux), como la mejor opción para tener esa paridad, y menciona a Git Bash y a PowerShell como alternativas razonables cuando instalar WSL no es posible.

PowerShell merece un vistazo aparte porque viene preinstalado en todas las versiones modernas de Windows y no funciona como cmd. Según Microsoft Learn, PowerShell es un shell de línea de comandos y un entorno de scripting pensado para automatizar tareas administrativas de sistemas Windows. En vez de comandos sueltos como dir o copy trabaja con cmdlets, que siguen la convención Verbo-Sustantivo, Get-ChildItem para listar, Set-Location para cambiar de carpeta, Get-Process para ver qué está corriendo, Stop-Service para detener un servicio. Aprenderte esa convención vale más que memorizar cmdlets sueltos, porque en cuanto sabes que Get- lee información y Set- la cambia, puedes adivinar el nombre de un cmdlet que nunca usaste antes.

PS C:\Users\estudiante> Get-Location
PS C:\Users\estudiante> Get-ChildItem
PS C:\Users\estudiante> Set-Location proyectos
PS C:\Users\estudiante\proyectos> Get-Process | Select-Object -First 5

Caso de estudio: el script que funciona a mano pero no al ejecutarlo

Un estudiante escribe un script corto en PowerShell, revisar.ps1, que imprime la fecha y limpia una carpeta temporal. Lo prueba escribiendo cada línea directamente en la consola y todo funciona. Guarda esas mismas líneas en el archivo, hace doble clic o lo ejecuta con .\revisar.ps1, y PowerShell responde con un error que menciona UnauthorizedAccess y dice que ejecutar scripts está deshabilitado en el sistema. Antes de seguir leyendo, piensa en la pregunta, si el comando funcionó perfecto escrito a mano en la misma consola, ¿por qué falla exactamente el mismo comando al venir de un archivo .ps1?

La respuesta está en la execution policy, la política de ejecución de PowerShell, que Microsoft Learn documenta como Restricted por defecto en Windows 10 y 11 para equipos cliente, y como RemoteSigned en Windows Server. Esa política no evalúa lo que hace el script, evalúa únicamente si el archivo tiene permiso de correr como script, y Restricted bloquea todos los .ps1 sin excepción, aunque el mismo código escrito a mano en la consola se ejecute sin ningún problema. Es una medida de seguridad deliberada, pensada para que un archivo descargado de internet no se ejecute solo con hacerle doble clic, no un límite infranqueable ni un error del script.

2 Comandos básicos de navegación y gestión de archivos

Sea cual sea el shell, un puñado de operaciones se repiten todos los días, saber dónde estás parado, ver qué hay en una carpeta, moverte a otra, crear, copiar, mover y borrar archivos. MDN documenta estos comandos para Unix y macOS, y la tabla siguiente resume su equivalente en cmd y en PowerShell.

Acción Unix, macOS, Linux Windows (cmd) Windows (PowerShell)
Ver directorio actual pwd cd sin argumentos Get-Location
Listar contenido ls, ls -l, ls -lah dir Get-ChildItem
Cambiar de directorio cd carpeta, cd .. cd carpeta Set-Location
Crear directorio mkdir nombre mkdir nombre New-Item -ItemType Directory
Crear archivo vacío touch archivo (no existe un equivalente directo) New-Item
Copiar cp origen destino copy Copy-Item
Mover o renombrar mv origen destino move, ren Move-Item, Rename-Item
Eliminar rm archivo, rm -r carpeta del Remove-Item
Ayuda de un comando man comando comando /? Get-Help comando

La mayoría de estos comandos aceptan opciones con guion, también llamadas flags, que se pueden combinar, ls -ltrh en una sola invocación lista en formato largo, ordenado por fecha, del más antiguo al más reciente y con tamaños legibles para una persona en vez de en bytes crudos.

Dos rutas te llevan al mismo archivo, y confundirlas es otra fuente común de errores. Una ruta absoluta empieza desde la raíz del sistema de archivos, con / en Unix o macOS o con la letra de la unidad en Windows, y funciona sin importar dónde estés parado. Una ruta relativa no empieza con / y se interpreta a partir del directorio donde te encuentras en ese momento, así que la misma ruta relativa apunta a archivos distintos según donde la escribas.

cd /home/estudiante/proyectos
ls -la
mkdir app-móvil
cd app-móvil
touch main.py
mv main.py principal.py
cp principal.py respaldo.py
rm respaldo.py

El separador de ruta también cambia entre sistemas, / en Unix, macOS y Linux, y \ en Windows. MDN señala esa diferencia sintáctica como parte de lo que cambia entre plataformas, y en la práctica es una causa real de que un script de shell escrito y probado en un sistema falle o se comporte distinto al copiarlo a otro. Es una explicación razonable de por qué las instrucciones de instalación de un mismo tutorial a veces funcionan para un compañero de clase y para otro no, aunque ambos hayan copiado exactamente el mismo comando.

3 Gestión de procesos: ver y detener lo que corre

Cada programa que corre en tu equipo, desde el emulador de Android hasta el propio editor de código, es un proceso, y saber listarlos y detenerlos es tan básico como saber navegar carpetas. En sistemas Unix y Linux el comando ps reporta el estado de los procesos en ejecución, ps aux y ps -ef son las invocaciones más comunes, y kill envía una señal a un proceso. Esa última palabra importa, kill no significa necesariamente matar de un tajo, significa enviar una señal, y el proceso que la recibe puede reaccionar de formas distintas según cuál sea.

Por defecto, kill envía SIGTERM, la señal número 15, que le pide al proceso que termine mientras le da la oportunidad de hacer una limpieza ordenada antes, guardar un archivo a medio escribir, cerrar una conexión de red, liberar un recurso. SIGKILL, la señal número 9, es distinta de raíz, el proceso no puede interceptarla ni reaccionar a ella de ninguna forma, termina de inmediato sin ninguna oportunidad de limpieza. Preferir TERM sobre KILL como primer intento es una práctica ampliamente recomendada en la comunidad Unix por esta misma razón, aunque conviene verificar la redacción exacta antes de citar textualmente una versión puntual de la página de manual de kill.

ps aux | grep java
kill 4821
kill -9 4821

En Windows, el equivalente en cmd es tasklist, que lista procesos locales o remotos con filtros por identificador, por nombre de imagen o por usuario, y taskkill para terminarlos; en PowerShell, Get-Process y Stop-Process cumplen exactamente el mismo rol con la sintaxis de cmdlet que ya viste antes.

Get-Process | Where-Object { $_.ProcessName -like "*studio*" }
Stop-Process -Name "studio64" -Force

Caso de estudio: el emulador que se cierra a la fuerza

Un estudiante deja el emulador de Android congelado, sin responder, mientras estaba a punto de guardar el estado de una prueba. Por costumbre, abre otra terminal y ejecuta kill -9 contra el proceso del emulador porque en clases anteriores le funcionó para cerrar programas colgados. Antes de seguir, piensa qué diferencia real hay entre usar kill sin argumentos adicionales y usar kill -9 en este caso concreto.

La diferencia es justo la que explica la sección anterior. SIGTERM, la señal por defecto, le da al emulador la oportunidad de escribir a disco el estado que tenía pendiente antes de cerrar; SIGKILL elimina esa oportunidad por completo, el proceso desaparece en el instante exacto en que recibe la señal, sin importar que estuviera a mitad de escribir un archivo. Un estudiante que usa -9 por costumbre, sin pensar en la diferencia, puede terminar con archivos de estado del emulador corruptos o a medio escribir, un problema silencioso que solo aparece la siguiente vez que intenta abrir ese mismo emulador. La recomendación práctica, ampliamente extendida entre quienes administran procesos Unix, es intentar primero sin -9 y reservar SIGKILL para cuando el proceso de verdad no responde a nada más.

NotaSolución del Reto 2

La segunda opción es la correcta. kill sin argumentos envía SIGTERM, que le da al programa la oportunidad de terminar de escribir lo que tenía pendiente o de cerrar el archivo de forma ordenada antes de salir, justo la señal que la comunidad Unix recomienda preferir como primer intento. kill -9 fuerza SIGKILL, que el proceso no puede interceptar ni usar para hacer ninguna limpieza, así que si el programa estaba a mitad de escribir el archivo, ese archivo puede quedar corrupto o incompleto. Apagar el equipo es todavía peor, porque no solo termina ese proceso sin limpieza, sino todos los demás procesos que estuvieran corriendo en ese momento, con el mismo riesgo multiplicado.

4 Gestores de paquetes: instalar sin repetir el trabajo

Un gestor de paquetes automatiza instalar, actualizar y eliminar software junto con las dependencias que ese software necesita, en vez de que cada persona busque, descargue y ubique manualmente cada librería por separado. El desarrollo móvil no tiene un único gestor, tiene varios, cada uno atado al ecosistema donde vive.

npm es el gestor de paquetes de JavaScript, viene incluido con Node.js, y su repositorio oficial se presenta a sí mismo como el gestor de paquetes para JavaScript, aunque conviene confirmar la redacción exacta en github.com/npm/cli antes de citar esa frase palabra por palabra en un trabajo. Vale la pena aclarar un malentendido común, la sigla no significa “Node Package Manager”, en español “gestor de paquetes de Node”; la propia documentación de npm aclara que npm no es una sigla de nada, sino un retroacrónimo recursivo que la comunidad adoptó como nombre propio en vez de como abreviatura de otra cosa. Esto importa en la práctica porque significa que no hay una expansión “oficial” que buscar o memorizar, npm es simplemente el nombre de la herramienta.

Gradle es el sistema de build que usa Android Studio para compilar proyectos Android y gestionar sus dependencias. Según documenta developer.android.com, un proyecto nuevo de Android Studio configura por defecto tanto el repositorio de Google (google()) como Maven Central (mavenCentral()) en el archivo settings.gradle.kts; dependencias de AndroidX como androidx.core:core-ktx, la que aparece en el ejemplo más abajo, se resuelven principalmente contra el repositorio de Google, no contra Maven Central. Los archivos de configuración de un proyecto Gradle son build.gradle.kts, en Kotlin y es la forma recomendada hoy, o build.gradle, en Groovy, la forma anterior que todavía se encuentra en proyectos existentes.

CocoaPods es el gestor de dependencias que usa la comunidad de iOS para proyectos Xcode en Swift o en Objective-C. Funciona a partir de un archivo llamado Podfile, donde se declaran las dependencias del proyecto, y del comando pod install, que las descarga e integra al proyecto. Esta descripción es conocimiento ampliamente asentado en el ecosistema iOS, y si vas a citar una redacción oficial palabra por palabra en un trabajo, confirma primero en cocoapods.org en vez de tomar esta guía como esa fuente.

Homebrew es el gestor de paquetes de facto en macOS, ampliamente usado también en Linux, y su repositorio en GitHub lo describe como una herramienta para instalar paquetes que no vienen incluidos en el sistema operativo; conviene confirmar la redacción exacta en github.com/Homebrew/brew antes de citar cualquier frase suya palabra por palabra, en vez de tomar esta guía como esa fuente. brew update actualiza el índice de paquetes disponibles, y brew doctor diagnostica problemas de configuración del sistema, en la práctica su salida suele apuntar bastante cerca del problema real, así que vale la pena leerla con calma en vez de descartarla como ruido.

npm install
brew update
brew doctor
pod install
// build.gradle.kts de un módulo de app Android
dependencies {
    implementation("androidx.core:core-ktx:1.13.1")
    testImplementation("junit:junit:4.13.2")
}

5 Editores e IDE para desarrollo móvil

Un editor de código y un IDE, entorno de desarrollo integrado por sus siglas en inglés, no son exactamente lo mismo. Un editor edita texto con ayudas para programar; un IDE integra además el compilador o intérprete, el depurador, el sistema de build y, en desarrollo móvil, el emulador o simulador del dispositivo, todo dentro de la misma aplicación.

Android Studio es, según developer.android.com, el IDE oficial para el desarrollo de apps Android, construido sobre el editor de código y las herramientas de IntelliJ IDEA. Trae un editor con inspecciones de código y lint, el sistema de build basado en Gradle que ya viste arriba, el Android Emulator con soporte para múltiples configuraciones de dispositivo virtual conocidas como AVD (siglas del inglés Android Virtual Device), y herramientas de depuración y perfilado que incluyen el Layout Inspector, perfiladores de CPU y memoria, y Logcat, la vista donde aparecen en vivo los logs del dispositivo y la salida de adb (Android Debug Bridge, la herramienta de línea de comandos para depurar dispositivos Android que se explica más adelante en este tema).

Xcode es el IDE oficial de Apple para desarrollar, probar y distribuir apps en iOS, iPadOS, macOS, tvOS, visionOS y watchOS, según developer.apple.com. Incluye un editor con autocompletado predictivo, el Simulator para prototipar y probar sin necesitar un dispositivo físico, Instruments para perfilar CPU, disco, memoria y GPU en tiempo real, los frameworks de pruebas Swift Testing y XCTest/XCUIAutomation, y Xcode Cloud para integración y entrega continua.

Visual Studio Code, según su propia documentación oficial, combina la simplicidad de un editor de código fuente con herramientas de desarrollo potentes, como autocompletado IntelliSense y un depurador integrado. No es un IDE completo por sí mismo, es un editor extensible que se convierte en uno según las extensiones que instales, para C#, para Kotlin, para PowerShell o para lo que necesites. Corre en macOS, Linux y Windows, está construido sobre Electron, y trae soporte nativo para Git, lo que permite ver los cambios pendientes de un archivo sin salir del editor.

6 Caso de estudio: un día de trabajo con adb

Android Debug Bridge, conocido por su forma corta adb, es la herramienta de línea de comandos incluida en el Android SDK (siglas del inglés Software Development Kit) Platform Tools que conecta tu terminal con un emulador o con un dispositivo Android físico. Según developer.android.com, es una herramienta versátil que permite comunicarse con un dispositivo para instalar y depurar apps, y que además da acceso a un shell Unix corriendo dentro del propio dispositivo.

adb no es un solo programa, es una arquitectura de tres piezas. El cliente se invoca desde la terminal de tu máquina de desarrollo cada vez que escribes un comando adb. El daemon, adbd, corre en segundo plano en cada dispositivo o emulador conectado. Entre los dos media el servidor, que corre en tu máquina de desarrollo, escucha en el puerto TCP (siglas del inglés Transmission Control Protocol) local 5037, y localiza emuladores escaneando puertos impares entre el 5555 y el 5585.

adb devices -l
adb install app-debug.apk
adb shell
adb shell pm list packages
adb pull /sdcard/DCIM/foto.jpg .
adb push config.json /sdcard/
adb logcat

adb devices -l lista los dispositivos y emuladores conectados. adb install instala un APK (siglas del inglés Android Package, el archivo empaquetado de una app Android). adb shell abre un shell interactivo dentro del dispositivo, y adb shell comando ejecuta un único comando ahí sin quedarte dentro. adb pull y adb push copian archivos entre tu máquina y el dispositivo, en ambos sentidos. adb logcat muestra en vivo los logs del sistema y de tu app, la herramienta que más vas a usar para depurar un comportamiento que no entiendes.

El emulador que no aparece

Un estudiante tiene dos emuladores de Android abiertos al mismo tiempo, uno para probar en una versión antigua de Android y otro en la más reciente, además de un dispositivo físico conectado por cable. Ejecuta adb devices y ve que uno de los emuladores no aparece en la lista, o aparece marcado como offline. Antes de reiniciar todo el equipo, que en teoría arreglaría el problema pero cuesta varios minutos, vale la pena preguntarse por qué pasa esto justamente cuando hay varios emuladores abiertos a la vez y no cuando hay uno solo.

La explicación está en cómo el servidor de adb localiza emuladores, escaneando puertos impares en pares secuenciados dentro del rango 5555 a 5585. Con un solo emulador abierto, ese escaneo casi nunca falla. Con varios emuladores abiertos a la vez, o con otra herramienta de terceros usando ese mismo rango de puertos, el servidor puede perder la pista de cuál daemon corresponde a cuál emulador, y el resultado es exactamente lo que el estudiante ve, un dispositivo que no aparece o que aparece offline sin que nada esté roto de verdad. Es un problema real y documentado en la práctica de laboratorio, no un fallo aleatorio del emulador.

El cable USB del dispositivo físico no tiene nada que ver con que un emulador aparezca o no, y una ventana de emulador abierta no garantiza que el emulador siga respondiendo. La causa documentada es el escaneo de puertos, el servidor de adb busca emuladores recorriendo puertos impares entre 5555 y 5585, y con varios emuladores abiertos a la vez ese escaneo puede perder la pista de cuál daemon corresponde a cuál instancia. Antes de reiniciar todo el equipo, una alternativa más rápida es cerrar los emuladores sobrantes y volver a ejecutar adb devices, o reiniciar únicamente el servidor de adb con adb kill-server seguido de adb start-server, que reinicia el escaneo sin tocar el resto del sistema.

8 Antes del Tema 2

  1. Abre una terminal en tu equipo, identifica qué shell estás usando, y navega hasta una carpeta de proyecto usando tanto una ruta absoluta como una ruta relativa.
  2. Si tienes Android Studio o Xcode instalado, abre un emulador o el Simulator, conéctalo y, si tienes Android Studio, ejecuta adb devices -l para confirmar que lo detecta.
  3. Instala o confirma que tienes instalado el gestor de paquetes de tu sistema operativo, npm, Homebrew o el que corresponda, y ejecuta el comando que lista las versiones instaladas.

Con la terminal, los comandos básicos y las herramientas de este tema ya en tu caja, el Tema 2 entra al control de versiones con Git y GitHub, el sistema que va a guardar el historial completo de cada cambio que hagas en tu código, y el que vas a usar para compartir ese código con tus compañeros a través de un repositorio remoto.
