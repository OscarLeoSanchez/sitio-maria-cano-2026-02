Unidad Unidad 2. Herramientas de trabajo en desarrollo de aplicaciones para dispositivos móviles
Tema Tema 2. Repositorio de software con Git y servicios web de control de versiones

El Tema 1 te dejó cómodo en la terminal, sabes moverte entre carpetas con cd y ls, instalar paquetes con un gestor y abrir tu proyecto en un editor o un IDE (del inglés Integrated Development Environment, entorno de desarrollo integrado) para escribir código. Ese dominio de la línea de comandos es exactamente lo que necesitas hoy, porque Git, la herramienta de este tema, se maneja casi siempre escribiendo comandos en esa misma terminal, no haciendo clic en un botón de guardar versión. El tema de hoy resuelve un problema que seguramente ya viviste sin nombrarlo, qué hacer cuando dañas un archivo que funcionaba bien ayer, cuando dos personas editan el mismo proyecto al mismo tiempo, o cuando necesitas volver a una versión anterior de tu código sin terminar con carpetas duplicadas con nombres como proyecto_final_v2_bueno_ahora_si. Vas a aprender qué es un repositorio de software, cómo Git guarda el historial de cambios en tu propia máquina, y cómo GitHub convierte ese historial local en un espacio de trabajo compartido con pull requests, revisión de código y colaboración en equipo.

1 Qué es Git y por qué es distribuido

Git es un sistema de control de versiones distribuido, conocido por sus siglas en inglés como DVCS (Distributed Version Control System), de código abierto y publicado bajo la licencia GNU GPL (siglas en inglés de General Public License, licencia pública general) versión 2.0. Nació para manejar el desarrollo del kernel de Linux, un proyecto de millones de líneas de código escritas por miles de personas distintas, lo que explica por qué está diseñado para moverse rápido incluso con un historial enorme. La propia documentación oficial de Git señala que el historial completo del proyecto Linux, 1.4 millones de commits acumulados a lo largo de años, ocupa apenas 5.5 gigabytes en disco, una cifra que ilustra cuánto le importó al proyecto la eficiencia de almacenamiento desde el diseño.

Lo que distingue a Git de sistemas de control de versiones anteriores, como CVS (siglas en inglés de Concurrent Versions System) o Subversion, es justo la palabra distribuido de su nombre. En esos sistemas más antiguos y centralizados existe un único servidor que guarda el historial completo, y cada operación cotidiana, confirmar un cambio, revisar quién modificó una línea, comparar dos versiones, exige contactar ese servidor por red. Git invierte esa relación. Según el glosario de MDN (Mozilla Developer Network, la documentación web de Mozilla), un sistema de control de versiones distribuido te deja hacer las operaciones comunes, crear ramas, confirmar cambios, en tu propia máquina de desarrollo, sin necesidad de tocar el repositorio maestro ni siquiera tener permiso de escritura sobre él. La copia que tienes en tu computador no es un resumen ni un caché parcial, es el historial completo del proyecto, con cada commit desde el principio.

Fíjate en la diferencia clave del diagrama. En el modelo centralizado, la flecha entre tu máquina y el servidor se usa para casi todo. En Git, esa flecha hacia el remoto solo aparece cuando de verdad necesitas compartir tu trabajo o traer el de alguien más, con comandos como git push o git pull. El resto del tiempo, que es la mayor parte de una sesión de trabajo normal, tu máquina no necesita internet para nada.

2 Las tres áreas de trabajo y los tres estados de un archivo

Git organiza el trabajo diario alrededor de tres estados por los que pasa un archivo. Modified (modificado) significa que cambiaste el archivo pero Git todavía no lo tiene guardado en su base de datos. Staged (preparado) significa que marcaste ese cambio para que entre en la próxima confirmación. Committed (confirmado) significa que el cambio ya quedó guardado de forma permanente en el historial local del repositorio. Estos tres estados son la idea central que hay que entender antes de usar Git en serio (Chacon y Straub, Pro Git, el libro oficial del proyecto).

Estos tres estados corresponden a tres áreas físicas dentro de tu proyecto. El directorio de trabajo (working directory) es la copia normal de tus archivos, la que ves y editas con tu editor. El área de preparación o índice (staging area) es un archivo, casi siempre dentro de la carpeta .git, que guarda información sobre qué va a entrar en el próximo commit. El directorio Git (.git, el repositorio propiamente dicho) es donde Git guarda de forma permanente los metadatos y la base de datos de objetos del proyecto, y es exactamente lo que se copia cuando alguien clona tu repositorio.

El flujo básico documentado en el tutorial oficial de Git (gittutorial) es justamente ese recorrido de las tres áreas, escrito en comandos. Pruébalo tú mismo en tu terminal:

mkdir mi-proyecto
cd mi-proyecto
git init
Initialized empty Git repository in /home/usuario/mi-proyecto/.git/

La ruta exacta que veas depende de dónde crees la carpeta en tu propio sistema, pero el mensaje confirma que ya existe un directorio .git vacío. Ahora crea un archivo y revisa su estado:

echo "documentacion del proyecto" > README.md
git status
On branch main
No commits yet
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md
nothing added to commit but untracked files present (use "git add" to track)

README.md aparece como untracked, ni siquiera está en la categoría modified todavía, porque Git nunca lo ha visto antes. Prepáralo y vuelve a mirar:

git add README.md
git status
On branch main
No commits yet
Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   README.md

Ahora sí está en el área de preparación, listo para el próximo commit. El paso final:

git commit -m "Agrega README con la documentacion inicial"
git log
[main (root-commit) a1b2c3d] Agrega README con la documentacion inicial
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
commit a1b2c3d4e5f6789012345abcdef67890fedcba1 (HEAD -> main)
Author: Tu Nombre <tu@correo.com>
Date:   Mon Aug 17 10:00:00 2026 -0500

    Agrega README con la documentacion inicial

El hash a1b2c3d… es solo ilustrativo, el tuyo va a ser distinto siempre, porque Git lo calcula a partir del contenido exacto del archivo, la fecha, el autor y el mensaje, así que nunca dos commits distintos comparten el mismo hash. La documentación oficial recomienda que ese mensaje de commit empiece con una línea corta, de no más de 50 caracteres, que resuma el cambio, seguida de una línea en blanco y una descripción más detallada si hace falta.

3 Qué guarda un commit por dentro

Cuando ejecutas git commit, Git no guarda una lista de diferencias respecto a la versión anterior, como sí hacen otros sistemas de control de versiones, guarda una instantánea completa del estado del proyecto en ese momento. Concretamente, cada versión de un archivo se guarda como un objeto blob, identificado por un checksum SHA-1 (siglas en inglés de Secure Hash Algorithm 1, un algoritmo de resumen criptográfico) calculado sobre su contenido. Se crea también un objeto tree, que mapea nombres de archivo y de carpeta a esos blobs y representa la estructura de directorios del proyecto. Y se crea un objeto commit, que apunta al tree raíz, guarda los metadatos de quien lo hizo y el mensaje, y contiene uno o más punteros a su o sus commits padre, cero padres en el primer commit del proyecto, uno en un commit normal, y dos o más en un commit de fusión.

La página de manual oficial de git commit lo resume así, en inglés, “Create a new commit containing the current contents of the index and the given log message describing the changes. The new commit is a direct child of HEAD”. Traducido, git commit crea un commit nuevo con el contenido actual del índice y el mensaje que le des, y ese commit nuevo es hijo directo de HEAD, es decir, se engancha justo después de donde estabas parado. Esa es la razón por la que el historial de Git nunca se reescribe hacia atrás por accidente durante el uso normal, cada commit nuevo solo agrega un eslabón más a la cadena.

4 Ramas: punteros que se mueven, no copias de carpetas

Una rama en Git no es una copia del proyecto, es apenas un puntero, un pequeño archivo de 41 bytes que contiene el checksum SHA-1 de 40 caracteres del commit al que apunta esa rama, más un salto de línea, guardado dentro de la carpeta .git/refs/heads/. Esa es la razón por la que crear una rama en Git es una operación prácticamente instantánea sin importar el tamaño del proyecto, a diferencia de otros sistemas de control de versiones donde ramificar implica copiar carpetas completas.

HEAD es otro puntero especial, distinto de una rama normal, que indica en qué rama local estás trabajando en este momento. HEAD no apunta directamente a un commit, apunta a la rama activa, así que cuando confirmas un cambio nuevo, esa rama avanza al nuevo commit y HEAD la sigue en automático. Cuando cambias de rama con git checkout o con git switch, HEAD se reubica hacia la otra rama y tu directorio de trabajo se actualiza para que coincida con la instantánea de esa rama.

En la terminal, crear y moverte a una rama nueva se ve así:

git checkout -b feature-precios
git branch
Switched to a new branch 'feature-precios'
* feature-precios
  main

El asterisco marca la rama activa, exactamente la que apunta HEAD en el diagrama de arriba. Como cada commit guarda el puntero a su propio commit padre, Git puede reconstruir el historial completo del proyecto y calcular automáticamente el ancestro común entre dos ramas que se separaron en algún punto, lo que es la base del algoritmo de fusión que ves más adelante en esta guía.

5 El repositorio remoto: qué es origin

Un remoto es una referencia a otro repositorio, normalmente alojado en un servidor como GitHub, cuyas ramas puedes rastrear desde tu copia local. La documentación oficial de git remote lo define como el comando para administrar el conjunto de repositorios remotos cuyas ramas sigues. El remoto por defecto que se crea al clonar un proyecto se llama origin, un nombre que es solo una convención, no una palabra especial del lenguaje de Git.

git clone no se limita a copiar archivos, configura automáticamente ese remoto origin y crea ramas de rastreo remoto para cada rama del repositorio que clonaste, de modo que después puedas usar git fetch o git pull sin tener que escribir argumentos adicionales cada vez.

git clone https://github.com/tu-usuario/mi-proyecto.git
cd mi-proyecto
git remote -v
origin  https://github.com/tu-usuario/mi-proyecto.git (fetch)
origin  https://github.com/tu-usuario/mi-proyecto.git (push)

Cada remoto aparece dos veces porque Git guarda por separado la URL (siglas en inglés de Uniform Resource Locator, la dirección de un recurso en internet) para traer cambios (fetch) y la URL para subirlos (push), aunque casi siempre sean la misma dirección. Subir y traer cambios se hace así:

git push origin main
git pull origin main

6 Fusionar ramas: fast-forward, fusión de tres vías y conflictos

git merge incorpora en la rama actual los cambios hechos en otra rama desde que sus historiales divergieron, según la documentación oficial. Hay dos formas en que eso puede pasar. La primera se llama fast-forward, y ocurre cuando la rama actual es simplemente un ancestro directo de la rama que estás fusionando, es decir, nadie hizo commits nuevos en la rama actual mientras trabajabas en la otra. En ese caso Git no crea ningún commit de fusión, solo mueve el puntero de la rama actual hacia adelante hasta el último commit de la otra rama. La segunda es una fusión de tres vías (three-way merge), y ocurre cuando ambas ramas tienen commits nuevos desde que se separaron, así que Git crea un commit de fusión con dos o más padres que combina ambos historiales.

Un conflicto de fusión aparece cuando ambas ramas modificaron la misma zona del mismo archivo, y Git no tiene forma de adivinar cuál versión es la correcta. La documentación oficial lo explica sin rodeos, en inglés, “Git cannot randomly pick one side over the other, and asks you to resolve it”. Traducido, Git no puede elegir al azar entre las dos versiones, así que te pide a ti que lo resuelvas. Git marca la zona en conflicto directamente dentro del archivo con marcadores de texto:

<<<<<<< HEAD
el precio del arroz es 4200
=======
el precio del arroz es 4500
>>>>>>> feature-precios

Todo lo que va entre <<<<<<< HEAD y ======= es tu versión, la que ya estaba en la rama sobre la que estás parado. Todo lo que va entre ======= y >>>>>>> es la versión que trae la otra rama. Tienes que editar el archivo, decidir cuál texto final quieres conservar, borrar por completo los tres tipos de marcador, y después avisarle a Git que el conflicto ya quedó resuelto:

git add precios.txt
git commit

git add marca el archivo como resuelto exactamente igual que marcarías cualquier otro cambio, y git commit sin mensaje nuevo abre el editor con un mensaje que Git ya sugiere para cerrar la fusión.

7 Caso de estudio: el push forzado que borra el trabajo de otra persona

Imagina un equipo de dos personas, Ana y Luis, que colaboran sobre la misma rama main de un repositorio en GitHub. El viernes a las tres de la tarde Ana confirma un cambio y lo sube con git push. Más tarde, ese mismo viernes, Luis también confirma un cambio distinto y lo sube sin ningún problema, porque su rama local ya tenía el commit de Ana como ancestro. El lunes, Ana decide que su commit del viernes tenía un error en el mensaje, así que lo corrige localmente con git commit –amend, lo que en realidad crea un commit nuevo con un hash distinto para reemplazar al anterior, y luego intenta subirlo con git push. Git rechaza ese push, porque la rama remota ya avanzó con el commit de Luis y el historial local de Ana ya no es un ancestro directo de lo que hay en GitHub. Ana entonces prueba con git push –force para forzar la subida.

Antes de seguir, piensa en esta pregunta de análisis, qué pasa con el commit que Luis subió el viernes después del de Ana, si Ana fuerza su historial reescrito por encima de todo lo que hay en la rama remota.

La documentación oficial de git push responde sin rodeos sobre la bandera –force, en inglés, “It can cause the remote repository to lose commits; use it with care”. Traducido, puede hacer que el repositorio remoto pierda commits, así que hay que usarla con cuidado. Eso es exactamente lo que le pasa al commit de Luis, al forzar la subida, Ana reemplaza por completo el historial de la rama remota con el suyo, que en ningún punto de su cadena incluye el commit de Luis, así que ese commit deja de ser visible en main en GitHub, aunque técnicamente pueda seguir existiendo unos días en el historial interno de Git antes de que el recolector de basura lo elimine. El propio manual de Git resume la situación con una frase clara, en inglés, “git push –force is a method reserved for a case where you do mean to lose history”. Traducido, –force es un método reservado para el caso en el que de verdad quieres perder historial, no algo que se use por costumbre.

Por esta razón, en equipos reales que colaboran sobre una misma rama compartida rara vez se usa –force directamente sobre ella. Es más común preferir –force-with-lease, que rechaza la subida si alguien más subió cambios desde la última vez que revisaste la rama remota, o simplemente prohibir el push forzado sobre ramas compartidas como main, y reservarlo para ramas propias que nadie más está usando.

8 GitHub como servicio web de control de versiones

Git por sí solo no necesita ningún servicio en la nube, puedes usarlo completamente en tu propia máquina, sin conexión a internet, y ya tendrías control de versiones funcionando. GitHub agrega otra capa encima de Git, aloja repositorios en la nube y añade herramientas de colaboración que Git, como programa, no ofrece por sí mismo. La documentación de GitHub lo describe como una plataforma que soporta todo el proceso de desarrollo de software, desde planear el trabajo hasta desplegar y operar el software en producción, organizado en seis etapas, Plan (planear), Create (crear), Review (revisar), Test (probar), Deploy (desplegar) y Operate (operar).

GitHub documenta oficialmente dos modelos para colaborar sobre un mismo repositorio. En el modelo de bifurcación y solicitud de extracción (fork and pull model), cualquier persona con acceso de lectura puede crear un fork, una copia independiente del repositorio original, llamado upstream, trabajar libremente sobre esa copia sin coordinarse con nadie de antemano, y después proponer sus cambios de vuelta al repositorio original mediante un pull request. Es el modelo típico de los proyectos de código abierto, porque reduce la fricción para que cualquier persona externa pueda contribuir. En el modelo de repositorio compartido (shared repository model), las personas colaboradoras tienen acceso de escritura directo sobre un único repositorio, y en vez de bifurcarlo crean ramas temáticas para cada cambio. Es el modelo más común en equipos pequeños que trabajan sobre un proyecto privado, como el que vas a usar tú con tus compañeros de equipo en este curso.

9 El flujo de trabajo de GitHub

GitHub documenta oficialmente un flujo de seis pasos conocido como GitHub Flow, pensado para trabajar en equipo sobre una misma rama principal sin pisarse el trabajo unos a otros.

Primero se crea una rama con nombre descriptivo para aislar el trabajo de la rama principal. Segundo, se hacen cambios en esa rama, se confirman con commits y se suben con push. Tercero, se abre un pull request para pedir retroalimentación de otras personas colaboradoras. Cuarto, se atienden los comentarios de revisión, con nuevos commits que se suben a la misma rama y actualizan el pull request en automático. Quinto, una vez aprobado, se fusiona el pull request, lo que integra los cambios en la rama por defecto. Sexto, se elimina la rama que ya cumplió su propósito, para evitar que alguien la use por accidente más adelante pensando que sigue vigente.

10 Qué es un pull request

La documentación oficial de GitHub lo define en una sola frase, en inglés, “Pull requests are proposals to merge code changes into a project”. Traducido, un pull request es una propuesta para fusionar cambios de código dentro de un proyecto. No es el mecanismo que efectivamente mueve el código, es la conversación estructurada alrededor de esa fusión, un espacio donde otras personas revisan lo que hiciste antes de que se integre a la rama principal, comentan líneas específicas, piden cambios, y solo cuando todo eso queda resuelto, alguien aprueba la fusión.

Un pull request en GitHub organiza esa conversación en varias vistas. Conversación reúne la descripción del cambio, la línea de tiempo de eventos y los comentarios generales. Commits muestra cada confirmación que forma parte de la rama, en el orden en que se hicieron. Checks muestra el resultado de cualquier automatización configurada sobre el repositorio, como pruebas automáticas o procesos de construcción que corren solos cada vez que subes un cambio nuevo. Files changed muestra el diff completo, línea por línea, de todo lo que cambiaría si se fusiona el pull request, y es ahí donde se dejan la mayoría de los comentarios de revisión sobre líneas concretas de código. Un indicador de estado de fusión, visible en la parte inferior del pull request, resalta si falta alguna aprobación o si algún check todavía no pasa, antes de dejarte fusionar.

TipReto 1. Fast-forward o fusión de tres vías

La rama main tiene los commits C1, C2 y C3. Creaste la rama feature-login exactamente sobre C3 y le agregaste dos commits propios, C4 y C5. Mientras tanto, nadie más tocó main, sigue exactamente en C3. Ahora ejecutas git checkout main seguido de git merge feature-login.

Antes de seguir, marca la opción que creas correcta.

Después responde en una frase, qué tendría que haber pasado en main mientras trabajabas en feature-login para que Git sí tuviera que crear un commit de fusión.

NotaSolución del Reto 1

La segunda opción es la correcta. Git mueve el puntero de main hasta C5 sin crear ningún commit nuevo. Esto es un fast-forward, como main no se movió desde que feature-login se creó a partir de C3, main es literalmente un ancestro directo de C5, así que fusionar no exige combinar dos historiales distintos, solo adelantar el puntero al final de la cadena que ya incluye todo lo de main más los dos commits nuevos.

Para que Git tuviera que crear un commit de fusión de verdad, alguien habría tenido que confirmar al menos un commit nuevo directamente sobre main después de que creaste feature-login, por ejemplo un C3b. En ese caso main y feature-login habrían divergido, cada una con commits que la otra no tiene, y Git tendría que combinar ambos historiales en un commit nuevo con dos padres, uno apuntando a C3b y otro a C5.

TipReto 2. Resuelve el conflicto

Estás fusionando la rama feature-precios sobre main y Git se detiene con un conflicto en el archivo precios.txt. Al abrirlo, ves esto:

manzana: 3200
<<<<<<< HEAD
arroz: 4200
=======
arroz: 4500
>>>>>>> feature-precios
pan: 2100

Antes de seguir, responde por escrito, qué línea representa lo que ya había en main antes de la fusión, y cuál es la que trae feature-precios. Después escribe el archivo precios.txt ya resuelto, decidiendo tú qué precio del arroz debería quedar, y escribe los dos comandos que le faltan a Git para terminar la fusión después de guardar el archivo.

NotaSolución del Reto 2

La línea entre <<<<<<< HEAD y ======= es la versión que ya estaba en main, arroz: 4200, y la línea entre ======= y >>>>>>> feature-precios es la que trae la rama que estás fusionando, arroz: 4500. Git no puede decidir cuál de las dos es la correcta, porque las dos son cambios legítimos hechos por alguien, así que deja el archivo con las dos versiones marcadas y te pide a ti que decidas.

Una resolución válida, quedándote con el precio más reciente:

manzana: 3200
arroz: 4500
pan: 2100

Cualquier resolución sirve siempre que elimines las tres líneas de marcador y dejes el contenido final que quieres conservar. Los dos comandos que faltan son:

git add precios.txt
git commit

git add marca el archivo ya resuelto como listo para el próximo commit, exactamente igual que marcarías cualquier otro cambio, y git commit sin un mensaje nuevo abre el editor con un mensaje ya sugerido por Git que indica que es una fusión, lo que basta para cerrarla.

12 Antes del Tema 3

  1. Crea un repositorio Git en una carpeta de prueba, sigue el flujo del inicio de esta guía, init, add, commit, log, y después crea dos ramas que modifiquen el mismo archivo en la misma línea, para que al fusionarlas te aparezca un conflicto real y lo resuelvas tú mismo.
  2. Crea una cuenta en GitHub si todavía no tienes una, sube ese mismo repositorio con git remote add origin y git push, y abre un pull request de una rama tuya hacia main, aunque seas tú mismo la única persona revisando.
  3. Resuelve el Reto 1 y el Reto 2 si todavía no lo hiciste, y guarda tus respuestas para comparar en clase.

El Tema 3 cierra la Unidad 2 con las herramientas que vas a usar todos los días una vez que tu proyecto ya está en Git y en GitHub, las herramientas de depuración del navegador, una introducción conceptual a los bundlers que empaquetan tu código para el dispositivo, qué significa diseñar mobile-first, y una primera mirada a cómo se organiza una aplicación móvil en componentes, sin comprometerse todavía con Angular o con React, porque esa decisión la resuelve el docente con la pregunta 32 del diagnóstico de entrada.
