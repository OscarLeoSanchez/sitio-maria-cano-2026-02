De la Unidad 2 a las tablas

Un rombo no ejecuta ningún motor de base de datos. Hoy conviertes el diagrama de la cafetería en el único vocabulario que sí ejecuta, tablas, llaves primarias y llaves foráneas.

Cliente, Pedido, Producto, la relación Realiza uno a muchos y la relación Contiene muchos a muchos, exactamente el modelo con el que cerró la Unidad 2.

Seis reglas cubren cualquier diagrama

Regla 1. Entidad fuerte

El diagrama

Cliente, Pedido y Producto, cada una con su propio identificador.

La tabla

CREATE TABLE Cliente (
    id_cliente INT PRIMARY KEY,
    nombre     VARCHAR(80) NOT NULL,
    telefono   VARCHAR(20)
);

Pedido queda pendiente. Su llave foránea hacia Cliente llega recién en la Regla 5.

Regla 3. Atributo multivaluado

Si teléfono fuera multivaluado

Un celular y un fijo, los dos vigentes a la vez. Ya no cabe en una sola columna de Cliente.

La tabla propia

CREATE TABLE Cliente_Telefono (
  id_cliente INT NOT NULL
    REFERENCES Cliente(id_cliente),
  telefono   VARCHAR(20) NOT NULL,
  PRIMARY KEY (id_cliente, telefono)
);

Con un solo teléfono por cliente, la Regla 1 ya basta. Esta tabla solo hace falta si el negocio cambia.

Regla 4. Uno a uno

Opción A. Fusionar

numero_tarjeta y fecha_activacion dentro de Cliente, admitiendo nulos.

Opción B. Tabla separada

TarjetaFidelidad con id_cliente como llave primaria y foránea a la vez.

La cafetería usa la Opción B, porque Cliente tiene participación parcial en Tiene: no todo cliente saca tarjeta.

Regla 5. Uno a muchos

La llave foránea siempre vive en la tabla del lado muchos. Cliente Realiza Pedido, así que Pedido recibe cliente_id.

CREATE TABLE Pedido (
    id_pedido  INT PRIMARY KEY,
    fecha      DATE NOT NULL,
    cliente_id INT NOT NULL REFERENCES Cliente(id_cliente)
);
