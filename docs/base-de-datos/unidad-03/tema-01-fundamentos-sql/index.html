Unidad Unidad 3. Modelo relacional
Tema Tema 1. Del modelo entidad-relación a SQL

Abrir la presentación de la sesión

La presentación recorre, con una pregunta antes de cada respuesta, las mismas 28 etapas que esta guía desarrolla en detalle.

Tienes un modelo entidad-relación terminado. Sabes leerlo: entidades, atributos, relaciones, cardinalidades. La pregunta de este tema es la que viene justo después de dibujarlo: cómo haces para que ese modelo exista de verdad dentro de una base de datos, de modo que PostgreSQL, MySQL o SQL Server lo puedan almacenar, proteger y consultar. La respuesta es SQL, y la vas a construir por capas sobre un mismo caso, un sistema de ventas pequeño, desde la primera tabla hasta una consulta que combina cuatro tablas, agrupa y ordena. Cada etapa parte de una pregunta concreta, y el código aparece solo cuando esa pregunta lo hace necesario.

1 El caso: un sistema de ventas

Todo el tema usa el mismo negocio. Una tienda vende productos organizados por categorías; los clientes hacen pedidos, y cada pedido puede incluir varios productos, cada uno con su cantidad y con el precio que tenía en ese momento. El modelo entidad-relación de ese negocio es este:

Cuatro entidades y tres relaciones. CLIENTE realiza pedidos, uno a muchos: un cliente puede tener muchos pedidos, cada pedido pertenece a un solo cliente. PEDIDO contiene productos, muchos a muchos: un pedido lleva varios productos y un mismo producto aparece en muchos pedidos; esa relación tiene dos atributos propios, cantidad y precio_unitario, porque describen a la combinación pedido-producto y no a ninguno de los dos por separado. PRODUCTO pertenece a una categoría, muchos a uno.

El tema se organiza en seis partes. La primera convierte el modelo en tablas sin escribir código. La segunda crea esas tablas con SQL. La tercera las llena de datos. La cuarta consulta una tabla a la vez. La quinta cruza tablas siguiendo las relaciones. La sexta resume datos con funciones de agregación y agrupación.

2 Primera parte. Del modelo a las tablas

Etapa 1. Una entidad, sola

Empieza por la entidad más simple del modelo, CLIENTE, con sus cuatro atributos: id_cliente, nombre, correo y ciudad. Si esa entidad tuviera que guardarse dentro de una base de datos relacional, la única estructura disponible es la tabla: una rejilla de filas y columnas. La pregunta entonces es cómo queda CLIENTE dibujado como tabla. La respuesta es una tabla llamada cliente con una columna por cada atributo:

id_cliente nombre correo ciudad

Esa correspondencia es la primera regla del modelo relacional, y conviene fijarla con precisión porque todo lo que sigue se apoya en ella:

En el modelo entidad-relación En la base de datos
Entidad Tabla
Atributo Columna
Instancia (una entidad concreta) Fila

La tabla es el molde; la fila es cada ejemplar que se fabrica con ese molde. Un cliente concreto, Ana, con correo ana@email.com y ciudad Medellín, se convierte en una fila:

id_cliente nombre correo ciudad
1 Ana ana@email.com Medellín

Observa que el identificador, el 1, no venía en la descripción de Ana. Lo asigna el sistema, y su único trabajo es que ninguna fila se confunda con otra. Ese detalle es el tema de la etapa siguiente.

TipEjercicio 1.1

Toma la entidad PRODUCTO del modelo. Dibuja la tabla vacía que le corresponde, con sus columnas, y después escribe la fila que representa a un producto concreto: un teclado de 150.000 pesos del que hay 15 unidades en existencia.

NotaSolución
id_producto nombre precio stock
3 Teclado 150000 15

La entidad PRODUCTO produce la tabla producto; cada atributo es una columna; el teclado es una fila. El identificador 3 lo asigna el sistema, no viene en la descripción del producto.

Etapa 2. La clave primaria

Vuelve al modelo y pregúntate qué atributo identifica de manera única a cada cliente. No es el nombre: dos personas pueden llamarse igual. No es la ciudad: muchos clientes viven en la misma. El correo se acerca, pero un cliente puede cambiarlo. El atributo que existe justamente para eso es id_cliente. En el modelo relacional ese atributo recibe un nombre técnico, clave primaria (primary key, PK), y una definición exacta: una columna, o una combinación de columnas, cuyo valor no se repite en ninguna otra fila de la tabla y nunca está vacío.

id_cliente (PK) nombre correo ciudad
1 Ana ana@email.com Medellín
2 Carlos carlos@email.com Bogotá
3 Laura laura@email.com Cali

Con esa definición, la pregunta “¿podríamos tener dos clientes con id_cliente = 3?” tiene una sola respuesta: no. No porque alguien lo prohíba en una reunión, sino porque la base de datos, cuando declares esa clave más adelante, va a rechazar cualquier intento de insertar un segundo 3. La clave primaria es la primera regla del negocio que la base de datos vigila por sí misma.

TipEjercicio 2.1

Para cada una de las otras tres entidades del modelo, PEDIDO, PRODUCTO y CATEGORIA, indica cuál atributo es la clave primaria y explica en una frase por qué ninguno de los demás atributos sirve.

NotaSolución

PEDIDO usa id_pedido: la fecha se repite entre pedidos del mismo día y el estado toma solo unos pocos valores. PRODUCTO usa id_producto: dos productos pueden compartir nombre, precio o stock. CATEGORIA usa id_categoria: el nombre podría servir hoy, pero cambiarlo obligaría a corregir todas las referencias, y un identificador numérico nunca cambia.

Etapa 3. Una línea entre dos entidades

El modelo dice que CLIENTE se relaciona con PEDIDO, uno a muchos. Esa línea existe en el dibujo, pero una tabla no tiene líneas: solo columnas y filas. Mira las dos tablas convertidas de forma ingenua, cada una con sus propios atributos:

id_cliente (PK) nombre
1 Ana
2 Carlos
id_pedido (PK) fecha
101 2026-09-20
102 2026-09-21

Con estas dos tablas, ¿quién hizo el pedido 101? No hay forma de saberlo. La relación se perdió en el camino. Para recuperarla hace falta que cada pedido guarde a quién pertenece, y la única manera de guardar algo en una tabla es una columna más:

id_pedido (PK) fecha id_cliente
101 2026-09-20 1
102 2026-09-21 2

Ahora cada valor de pedido.id_cliente existe en cliente.id_cliente: el pedido 101 apunta a Ana, el 102 a Carlos. Esa columna que apunta a la clave primaria de otra tabla es una clave foránea (foreign key, FK). Y de aquí sale la segunda regla del modelo relacional, la regla de las relaciones uno a muchos:

La clave foránea vive en el lado N.

Es decir, en la tabla que está del lado “muchos” de la relación. Un cliente tiene muchos pedidos, así que es cada pedido el que carga el identificador de su cliente. Si intentaras hacerlo al revés, poner id_pedido dentro de cliente, un cliente con tres pedidos necesitaría tres valores en una sola celda, y una celda guarda un solo valor. La regla no es arbitraria: es la única que cabe en una tabla.

Hasta aquí el trabajo es puramente de modelo relacional: tablas, columnas, claves primarias y foráneas. Ese paso intermedio importa porque el SQL que escribas después es la transcripción literal de estas decisiones. Si el modelo relacional está bien, el CREATE TABLE sale solo.

Etapa 5. Muchos a muchos

Queda la relación más interesante: PEDIDO contiene PRODUCTO, muchos a muchos. Intenta aplicar la regla de la etapa 3 y verás que falla en los dos sentidos. Si pones id_producto dentro de pedido, cada pedido podría tener un solo producto, y un pedido real lleva varios. Si pones id_pedido dentro de producto, cada producto pertenecería a un solo pedido, y el mismo mouse se vende muchas veces. Ninguno de los dos lados puede cargar la clave foránea, porque los dos son el lado “muchos”.

La solución es una tabla nueva, que no estaba como entidad en el modelo, y que existe solo para representar la relación:

id_pedido (PK, FK) id_producto (PK, FK) cantidad precio_unitario
101 1 2 80000
101 3 1 150000

Se llama detalle_pedido, y cada fila suya es una línea de un pedido: el pedido 101 lleva dos unidades del producto 1 y una unidad del producto 3. Fíjate en tres cosas. Primera, la tabla tiene dos claves foráneas, una hacia pedido y otra hacia producto. Segunda, su clave primaria es la combinación de las dos: un mismo producto no debería aparecer dos veces dentro del mismo pedido, así que la pareja (id_pedido, id_producto) identifica a cada fila. Tercera, los atributos propios de la relación, cantidad y precio_unitario, viven aquí y en ningún otro lugar, porque describen a la línea, no al pedido ni al producto. De ahí la tercera regla:

Una relación muchos a muchos se convierte en una tabla nueva, y esa tabla puede tener atributos propios.

En el modelo, esto equivale a leer PEDIDO 1 --- N DETALLE_PEDIDO N --- 1 PRODUCTO: la relación N:M se descompone en dos relaciones 1:N que pasan por la tabla intermedia.

TipEjercicio 5.1

Guardar el precio en detalle_pedido parece redundante, porque producto ya tiene una columna precio. Explica por qué precio_unitario existe de todas formas.

NotaSolución

producto.precio es el precio de hoy; detalle_pedido.precio_unitario es el precio al que se vendió en ese pedido concreto. Si el mouse sube de 80.000 a 95.000 la semana próxima, los pedidos viejos deben seguir mostrando 80.000, porque eso fue lo que el cliente pagó. Sin esa columna, cambiar el precio de un producto reescribiría el historial de ventas.

Al reunir las tres reglas, el modelo entidad-relación completo se convierte en cinco tablas:

Cada flecha sale de una clave foránea y llega a la clave primaria que referencia. Si te preguntas qué parte de este esquema salió directamente del modelo entidad-relación, la respuesta es prácticamente todo: cada entidad es una tabla, cada relación 1:N es una clave foránea, y la relación N:M es una tabla más. Los dos mundos son el mismo, escrito de dos formas. Todo lo que sigue es escribir este esquema en SQL.

3 Segunda parte. Hacer que exista

Etapa 7. La primera tabla

SQL es el lenguaje con el que se le habla a un motor de base de datos relacional. Sus sentencias se escriben como texto, terminan en punto y coma, y no distinguen mayúsculas de minúsculas en las palabras reservadas; por convención se escriben en mayúsculas para que se distingan de los nombres que tú eliges. La sentencia que crea una tabla es CREATE TABLE:

CREATE TABLE cliente (
    id_cliente  INTEGER,
    nombre      VARCHAR(100),
    correo      VARCHAR(150),
    ciudad      VARCHAR(80)
);

Léela línea por línea. CREATE TABLE cliente crea una tabla llamada cliente. Entre paréntesis va la lista de columnas, separadas por coma, y cada columna tiene dos partes: su nombre y su tipo de dato, que le dice al motor qué clase de valores va a guardar. id_cliente INTEGER crea una columna que almacena números enteros. nombre VARCHAR(100) crea una columna de texto de longitud variable, hasta 100 caracteres. Al ejecutarla, la tabla existe, con sus cuatro columnas y ninguna fila:

id_cliente nombre correo ciudad

Estructura sí; datos, todavía no. Los tipos de dato que vas a usar en este curso son pocos:

Tipo Qué guarda Ejemplo
INTEGER Números enteros, positivos o negativos 20, -3
DECIMAL(p, s) Números con decimales, p dígitos en total y s después del punto DECIMAL(10,2) guarda hasta 99999999.99
VARCHAR(n) Texto de longitud variable, hasta n caracteres 'Medellín'
DATE Una fecha, sin hora '2026-09-20'
BOOLEAN Verdadero o falso TRUE, FALSE

Dos detalles que producen errores frecuentes. El texto y las fechas van siempre entre comillas simples, 'Ana', '2026-09-20'; los números, nunca. Y DECIMAL es el tipo correcto para dinero: los tipos de coma flotante como FLOAT redondean de formas que no conviene en un precio.

Etapa 8. Cada restricción nace de una necesidad

Compara la tabla que acabas de crear con el modelo relacional de la etapa 6. Se quedó por fuera la clave primaria. Sin ella, nada impide insertar dos clientes con el mismo identificador. Se declara con dos palabras a continuación del tipo de dato:

CREATE TABLE cliente (
    id_cliente  INTEGER PRIMARY KEY,
    nombre      VARCHAR(100),
    correo      VARCHAR(150),
    ciudad      VARCHAR(80)
);

PRIMARY KEY es una restricción (constraint): una regla que el motor verifica cada vez que alguien intenta insertar o modificar una fila, y que rechaza la operación si la regla se rompe. Hay otras dos que vas a necesitar en casi todas las tablas:

CREATE TABLE cliente (
    id_cliente  INTEGER PRIMARY KEY,
    nombre      VARCHAR(100) NOT NULL,
    correo      VARCHAR(150) UNIQUE,
    ciudad      VARCHAR(80)
);
Restricción Regla que impone Necesidad de negocio
PRIMARY KEY El valor no se repite y no puede estar vacío No puedo duplicar identificadores
NOT NULL La columna no puede quedar vacía Un cliente debe tener nombre
UNIQUE El valor no se repite, pero sí puede estar vacío No quiero dos clientes con el mismo correo

La diferencia entre PRIMARY KEY y UNIQUE es sutil pero real: las dos prohíben repetidos, pero UNIQUE admite valores vacíos y una tabla puede tener varias columnas UNIQUE, mientras que solo tiene una clave primaria. ciudad no lleva restricción a propósito: un cliente puede registrarse sin indicar su ciudad, y varios clientes comparten la misma.

Si ya creaste la tabla sin restricciones y quieres agregarlas sin borrarla, ALTER TABLE modifica una tabla existente:

ALTER TABLE cliente ADD CONSTRAINT correo_unico UNIQUE (correo);

Y si necesitas empezar de cero, DROP TABLE cliente; elimina la tabla con todo lo que contiene, sin confirmación y sin vuelta atrás.

Etapa 9. Las tablas categoría y producto

Escribe, sin mirar, el CREATE TABLE de categoria. Tiene dos columnas: el identificador, clave primaria, y el nombre, que no puede faltar.

NotaSolución 
CREATE TABLE categoria (
    id_categoria  INTEGER PRIMARY KEY,
    nombre        VARCHAR(100) NOT NULL
);

Ahora producto: identificador, nombre obligatorio, precio con decimales, stock entero, y la columna id_categoria que en el modelo relacional marcaste como clave foránea.

CREATE TABLE producto (
    id_producto   INTEGER PRIMARY KEY,
    nombre        VARCHAR(100) NOT NULL,
    precio        DECIMAL(10,2),
    stock         INTEGER,
    id_categoria  INTEGER
);

Esta sentencia es válida y crea la tabla. Pero pregúntate: ¿sabe SQL que id_categoria corresponde a la tabla categoria? No. Para el motor es un número entero más, igual que stock. Nada le impide guardar en esa columna un 999 que no corresponde a ninguna categoría. La relación existe en tu cabeza y en el diagrama, pero todavía no en la base de datos.

Etapa 10. Declarar la clave foránea

La clave foránea también se declara como restricción, con una línea adicional al final de la lista de columnas:

CREATE TABLE producto (
    id_producto   INTEGER PRIMARY KEY,
    nombre        VARCHAR(100) NOT NULL,
    precio        DECIMAL(10,2),
    stock         INTEGER,
    id_categoria  INTEGER,

    FOREIGN KEY (id_categoria)
        REFERENCES categoria(id_categoria)
);

FOREIGN KEY (id_categoria) nombra la columna de esta tabla que actúa como clave foránea; REFERENCES categoria(id_categoria) indica a qué tabla y a qué columna apunta. A partir de ese momento el motor exige que cada valor de producto.id_categoria exista en categoria.id_categoria, y rechaza cualquier fila que apunte a una categoría inexistente. FOREIGN KEY no es sintaxis arbitraria: es la relación del modelo entidad-relación, escrita en SQL.

Hay una consecuencia práctica: el orden de creación importa. categoria tiene que existir antes que producto, porque la restricción referencia una tabla que debe estar creada. En general, primero las tablas del lado 1, después las del lado N. Con esa regla, las cinco tablas del sistema de ventas se crean en este orden:

CREATE TABLE cliente (
    id_cliente  INTEGER PRIMARY KEY,
    nombre      VARCHAR(100) NOT NULL,
    correo      VARCHAR(150) UNIQUE,
    ciudad      VARCHAR(80)
);

CREATE TABLE categoria (
    id_categoria  INTEGER PRIMARY KEY,
    nombre        VARCHAR(100) NOT NULL
);

CREATE TABLE producto (
    id_producto   INTEGER PRIMARY KEY,
    nombre        VARCHAR(100) NOT NULL,
    precio        DECIMAL(10,2),
    stock         INTEGER,
    id_categoria  INTEGER,
    FOREIGN KEY (id_categoria) REFERENCES categoria(id_categoria)
);

CREATE TABLE pedido (
    id_pedido   INTEGER PRIMARY KEY,
    fecha       DATE NOT NULL,
    estado      VARCHAR(20) NOT NULL,
    id_cliente  INTEGER NOT NULL,
    FOREIGN KEY (id_cliente) REFERENCES cliente(id_cliente)
);

CREATE TABLE detalle_pedido (
    id_pedido        INTEGER,
    id_producto      INTEGER,
    cantidad         INTEGER NOT NULL,
    precio_unitario  DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (id_pedido, id_producto),
    FOREIGN KEY (id_pedido)   REFERENCES pedido(id_pedido),
    FOREIGN KEY (id_producto) REFERENCES producto(id_producto)
);

Fíjate en detalle_pedido. Su clave primaria es compuesta, así que no se declara al lado de una columna sino como restricción aparte: PRIMARY KEY (id_pedido, id_producto). Y tiene dos claves foráneas, una hacia cada tabla que conecta. Es la traducción exacta de la tabla intermedia de la etapa 5.

TipEjercicio 10.1

En pedido, la columna id_cliente lleva NOT NULL además de la clave foránea. Explica qué regla de negocio expresa esa combinación, y qué pasaría si quitaras el NOT NULL.

NotaSolución

FOREIGN KEY garantiza que, si hay un valor, corresponda a un cliente real. NOT NULL garantiza que siempre haya un valor. Juntas expresan que todo pedido pertenece obligatoriamente a un cliente existente. Sin NOT NULL, la base de datos aceptaría pedidos sin cliente, con la columna vacía, y la clave foránea no lo impediría, porque un valor vacío no apunta a nada y por tanto no viola la referencia.

4 Tercera parte. Datos

Etapa 11. Tabla no es lo mismo que datos

Las tablas existen, pero están vacías. La sentencia que agrega una fila es INSERT:

INSERT INTO cliente (id_cliente, nombre, correo, ciudad)
VALUES (1, 'Ana', 'ana@email.com', 'Medellín');

INSERT INTO cliente nombra la tabla destino. Entre el primer par de paréntesis va la lista de columnas que vas a llenar; entre el segundo, después de VALUES, los valores, en el mismo orden y en la misma cantidad. Texto entre comillas simples, números sin comillas. Antes de ejecutarla, predice cómo queda la tabla; después, comprueba:

id_cliente nombre correo ciudad
1 Ana ana@email.com Medellín

Ahora inserta tú a Carlos, con correo carlos@email.com, de Bogotá.

NotaSolución 
INSERT INTO cliente (id_cliente, nombre, correo, ciudad)
VALUES (2, 'Carlos', 'carlos@email.com', 'Bogotá');
id_cliente nombre correo ciudad
1 Ana ana@email.com Medellín
2 Carlos carlos@email.com Bogotá

La lista de columnas puede omitirse si das los valores de todas las columnas en el orden en que fueron creadas, INSERT INTO cliente VALUES (2, 'Carlos', ...). Es más corto y más frágil: si alguien agrega una columna a la tabla, la sentencia deja de funcionar. Escribir la lista de columnas es la forma segura.

Etapa 12. Varias filas de una vez

Diez clientes no necesitan diez sentencias. VALUES admite varias tuplas separadas por coma:

INSERT INTO cliente (id_cliente, nombre, correo, ciudad)
VALUES

    (4, 'Juan',  'juan@email.com',  'Medellín'),

Etapa 13. Hacer que la base de datos falle

Las restricciones se entienden mejor cuando las ves actuar. Intenta insertar un cliente con un identificador que ya existe:

INSERT INTO cliente (id_cliente, nombre, correo, ciudad)
VALUES (1, 'Pedro', 'pedro@email.com', 'Cali');

Clave primaria duplicada

Error

El motor rechaza la sentencia completa. Ya existe una fila con id_cliente = 1, y PRIMARY KEY prohíbe un segundo 1. No se inserta nada: una fila que viola una restricción no entra a medias. PostgreSQL lo reporta como duplicate key value violates unique constraint "cliente_pkey"; cada motor usa su propio mensaje, pero todos nombran la restricción que se violó.

Ahora intenta insertar un producto que apunta a una categoría inexistente:

INSERT INTO producto (id_producto, nombre, precio, stock, id_categoria)
VALUES (10, 'Mouse', 80000, 20, 999);

Violación de clave foránea

Error

No existe ninguna categoría con id_categoria = 999, así que FOREIGN KEY rechaza la fila. El mensaje típico es insert or update on table "producto" violates foreign key constraint. La regla también actúa en sentido contrario: si intentas borrar la categoría 1 mientras existan productos que la referencian, el motor se niega, porque dejaría filas de producto apuntando a nada.

Esto es lo que compras al declarar restricciones: la base de datos protege las reglas que diseñaste, sin que ningún programa tenga que verificarlas por su cuenta. Un identificador duplicado, un pedido sin cliente, un producto de una categoría inexistente, ya no pueden existir.

Etapa 14. La primera consulta

Ya hay datos. La sentencia que los muestra es SELECT, y su forma mínima tiene dos partes:

FROM cliente;

Etapa 16. Filtrar filas

SELECT nombre, ciudad FROM cliente muestra a todos los clientes. Para ver solo los de Medellín le falta una condición, y la condición va en una tercera cláusula, WHERE:

SELECT nombre, ciudad
FROM cliente
WHERE ciudad = 'Medellín';
nombre ciudad
Ana Medellín
Juan Medellín

Las tres cláusulas se leen como una frase: qué (SELECT), de dónde (FROM), bajo qué condición (WHERE). El motor evalúa la condición fila por fila y conserva solo las que la cumplen. Fíjate en que la comparación de texto distingue mayúsculas de minúsculas y tildes en la mayoría de motores: 'medellin' no es igual a 'Medellín'.

Etapa 17. Los operadores de WHERE

Una condición compara una columna con un valor, o combina varias comparaciones. Los operadores que necesitas son estos:

Operador Significado Ejemplo
= igual ciudad = 'Cali'
<> distinto ciudad <> 'Medellín'
> < >= <= mayor, menor, mayor o igual, menor o igual precio > 100000
AND las dos condiciones a la vez precio > 100000 AND stock > 10
OR al menos una de las dos ciudad = 'Medellín' OR ciudad = 'Bogotá'
NOT niega la condición NOT ciudad = 'Cali'
BETWEEN a AND b dentro de un rango, extremos incluidos precio BETWEEN 100000 AND 500000
IN (lista) cualquiera de los valores de la lista ciudad IN ('Medellín', 'Bogotá')
LIKE patrón texto que coincide con un patrón nombre LIKE 'M%'
IS NULL la columna está vacía ciudad IS NULL

Resuelve los cinco retos en orden; cada uno necesita un operador nuevo.

  1. Productos con precio superior a 100.000.
  2. Productos con stock menor a 10.
  3. Clientes que no sean de Medellín.
  4. Productos con precio entre 100.000 y 500.000.
  5. Clientes de Medellín o de Bogotá.
NotaSolución 
SELECT * FROM producto WHERE precio > 100000;

SELECT * FROM producto WHERE stock < 10;

SELECT * FROM cliente  WHERE ciudad <> 'Medellín';

SELECT * FROM producto WHERE precio BETWEEN 100000 AND 500000;

SELECT * FROM cliente  WHERE ciudad IN ('Medellín', 'Bogotá');

La primera devuelve Monitor, Teclado y Cámara. La segunda, Monitor y Cámara. La tercera, Carlos, Laura y Sara. La cuarta, Teclado y Cámara: BETWEEN incluye los extremos, y ninguno de los dos precios cae justo en 100.000 o 500.000, pero si existiera uno, entraría. La quinta, Ana, Carlos, Juan y Sara.

Dos operadores merecen explicación aparte. LIKE compara texto contra un patrón con dos comodines: % reemplaza cualquier cantidad de caracteres, incluida ninguna, y _ reemplaza exactamente uno. nombre LIKE 'M%' encuentra los nombres que empiezan por M, Mouse y Monitor; correo LIKE '%@email.com' encuentra los correos que terminan en ese dominio; nombre LIKE '_ara' encuentra nombres de cuatro letras que terminan en “ara”, como Sara.

NULL representa la ausencia de valor: una celda que no tiene nada, ni cero ni cadena vacía. Como no es un valor, no se compara con =. La consulta WHERE ciudad = NULL no devuelve ninguna fila nunca, ni siquiera para las filas cuya ciudad está vacía, porque la comparación con NULL no es ni verdadera ni falsa. La forma correcta es WHERE ciudad IS NULL, y su contraria, WHERE ciudad IS NOT NULL.

Leer SQL importa tanto como escribirlo. Con la tabla producto a la vista:

predice, sin ejecutar, qué filas devuelve esta consulta:

FROM producto

NotaSolución

Solo Teclado. El Mouse falla en el precio; Monitor y Cámara cumplen el precio pero fallan en el stock. AND exige que las dos condiciones sean verdaderas a la vez para la misma fila.

Y esta otra, que cambia una sola palabra:

SELECT *
FROM producto
WHERE precio > 100000
  OR stock > 10;
NotaSolución

Las cuatro filas. Monitor, Teclado y Cámara entran por el precio; Mouse entra por el stock. Con OR basta que una de las dos condiciones sea verdadera.

Cuando mezclas AND y OR en la misma condición, AND se evalúa primero. a OR b AND c significa a OR (b AND c). Usa paréntesis siempre que combines los dos: son gratis y evitan un resultado que parece correcto y no lo es.

Etapa 19. Ordenar y limitar

El motor devuelve las filas en el orden que le resulte más cómodo, que no tiene por qué ser el orden de inserción. Para ver los productos del más caro al más barato, ORDER BY indica la columna, y DESC la dirección descendente:

SELECT nombre, precio
FROM producto
ORDER BY precio DESC;
nombre precio
Monitor 900000
Cámara 500000
Teclado 150000
Mouse 80000

ASC, ascendente, es el valor por defecto: ORDER BY precio y ORDER BY precio ASC son lo mismo. Puedes ordenar por varias columnas: ORDER BY ciudad, nombre ordena por ciudad, y dentro de cada ciudad por nombre. Si solo quieres los tres más caros, LIMIT corta el resultado:

SELECT nombre, precio
FROM producto
ORDER BY precio DESC
LIMIT 3;

LIMIT sin ORDER BY devuelve tres filas cualesquiera, no las tres más caras: el corte se aplica sobre el orden que tenga el resultado, así que los dos van casi siempre juntos. LIMIT lo entienden PostgreSQL, MySQL y SQLite; el estándar SQL escribe lo mismo como FETCH FIRST 3 ROWS ONLY, y SQL Server usa SELECT TOP 3.

Etapa 20. Modificar datos

El Mouse ahora cuesta 95.000. No hace falta borrarlo e insertarlo de nuevo: la fila ya existe, y lo que cambia es un valor dentro de ella. La sentencia es UPDATE:

UPDATE producto
SET precio = 95000
WHERE id_producto = 1;

UPDATE producto nombra la tabla que cambia; SET precio = 95000 nombra la columna y su valor nuevo; WHERE id_producto = 1 dice a qué filas se aplica el cambio. Puedes cambiar varias columnas en la misma sentencia, SET precio = 95000, stock = 18, y el valor nuevo puede calcularse a partir del viejo, SET precio = precio * 1.1.

Ahora la sentencia sin la última línea:

UPDATE producto
SET precio = 95000;

UPDATE sin WHERE

Riesgo

Todos los productos pasan a costar 95.000. La sentencia es válida, el motor la ejecuta sin preguntar, y no hay forma de deshacerla con un clic. WHERE no es opcional en la práctica: sin él, el cambio se aplica a todas las filas de la tabla. Antes de ejecutar un UPDATE, ejecuta un SELECT con el mismo WHERE y confirma que devuelve exactamente las filas que quieres cambiar.

Etapa 21. Eliminar datos

Sara ya no debe estar en el sistema. DELETE borra filas completas:

WHERE id_cliente = 5;

Se va una fila, la que cumple la condición. Y la versión sin condición:

DELETE FROM cliente;

DELETE sin WHERE

Riesgo

Vacía la tabla completa, sin aviso. La tabla sigue existiendo, con sus columnas y restricciones, pero sin ninguna fila. La misma precaución que con UPDATE: primero el SELECT con ese WHERE, después el DELETE.

Las claves foráneas también intervienen aquí. Si intentaras borrar a Ana, id_cliente = 1, el motor se negaría, porque los pedidos 101 y 103 la referencian y quedarían apuntando a un cliente que ya no existe. Para borrar a Ana tendrías que borrar antes sus pedidos, y antes de eso las líneas de esos pedidos en detalle_pedido. La base de datos obliga a desmontar las relaciones en el orden inverso al que las construiste. Sara sí se pudo borrar porque ningún pedido la referencia.

6 Quinta parte. Recorrer las relaciones

Etapa 22. Volver al modelo

Hasta aquí cada consulta miró una sola tabla. Las preguntas reales cruzan varias. Por ejemplo: el nombre del cliente que hizo cada pedido. El nombre está en cliente; el pedido, en pedido. Antes de escribir nada, responde dos preguntas con el modelo a la vista: qué tablas necesitas, y qué columnas las conectan. Necesitas cliente y pedido, y las conecta id_cliente: clave primaria en la primera, clave foránea en la segunda. Esa columna compartida es la que permite combinar las dos.

Etapa 23. El primer JOIN

Mira las dos tablas fila por fila. Cada fila de pedido trae un id_cliente; ese valor apunta a exactamente una fila de cliente. Combinar las dos tablas es seguir esa flecha para cada fila:

En SQL, esa operación es JOIN:

SELECT pedido.id_pedido,
       cliente.nombre
FROM pedido
JOIN cliente
  ON pedido.id_cliente = cliente.id_cliente;
id_pedido nombre
101 Ana
102 Carlos
103 Ana

Léela por partes. FROM pedido JOIN cliente combina las dos tablas. ON pedido.id_cliente = cliente.id_cliente es la condición de emparejamiento: una fila de pedido se une con la fila de cliente cuyo id_cliente coincide. Como las dos tablas tienen una columna llamada id_cliente, el nombre solo sería ambiguo; por eso se escribe tabla.columna. En SELECT puedes pedir columnas de cualquiera de las dos tablas.

El resultado tiene tres filas, una por cada pedido, porque cada pedido se empareja con exactamente un cliente. Ana aparece dos veces, una por cada uno de sus pedidos: JOIN no elimina repetidos, produce una fila por cada pareja que cumple la condición. Y la idea central: JOIN no inventa conexiones, sigue las relaciones que diseñaste en el modelo. La condición del ON es siempre clave foránea igual a clave primaria.

¿Qué productos compró cada cliente? El nombre del cliente está en cliente; el nombre del producto, en producto. Entre las dos no hay relación directa: el camino pasa por pedido y por detalle_pedido. Antes de escribir SQL, dibuja el camino en el modelo:

SELECT COUNT(*) FROM producto;
count
4

411250

Etapa 27. Agrupar

¿Cuántos clientes hay en cada ciudad? La pregunta pide una cifra, pero no una sola: una por ciudad. Mira los datos: Ana y Juan son de Medellín; Carlos y Sara, de Bogotá; Laura, de Cali. Primero se agrupan las filas por ciudad; después se cuenta dentro de cada grupo. En SQL esa primera operación es GROUP BY:

SELECT ciudad,
       COUNT(*) AS cantidad
FROM cliente
GROUP BY ciudad;
ciudad cantidad
Medellín 2
Bogotá 2
Cali 1

GROUP BY ciudad reúne en un solo grupo todas las filas que comparten ciudad, y a partir de ahí cada función de agregación se calcula por grupo, no sobre la tabla completa. El resultado tiene una fila por grupo. Hay una regla estricta: en el SELECT de una consulta con GROUP BY solo pueden aparecer las columnas por las que agrupas y funciones de agregación. SELECT nombre, ciudad, COUNT(*) ... GROUP BY ciudad es un error, porque dentro del grupo Medellín hay dos nombres y el motor no sabe cuál mostrar.

La palabra que delata al GROUP BY es “por cada”: ventas por producto, clientes por ciudad, pedidos por estado. Cuando la pregunta la contenga, agrupa.

Para filtrar los grupos ya formados existe HAVING. WHERE filtra filas antes de agrupar; HAVING filtra grupos después, y por eso puede usar funciones de agregación:

SELECT ciudad, COUNT(*) AS cantidad
FROM cliente
GROUP BY ciudad
HAVING COUNT(*) > 1;
ciudad cantidad
Medellín 2
Bogotá 2

Etapa 28. La misión final

Gerencia quiere conocer los tres productos que más dinero han vendido. Es la pregunta más elaborada del tema, y se resuelve sin escribir nada todavía, respondiendo cinco preguntas en orden:

  1. ¿Qué tablas hacen falta? El nombre está en producto; lo vendido, en detalle_pedido.
  2. ¿Cuánto produjo cada línea? cantidad * precio_unitario.
  3. ¿Qué columna conecta las dos tablas? id_producto.
  4. ¿Qué significa “por producto”? GROUP BY.
  5. ¿Qué significa “los tres que más”? ORDER BY ... DESC LIMIT 3.

Cada respuesta es una pieza de la consulta:

SELECT p.nombre,
       SUM(d.cantidad * d.precio_unitario) AS ventas
FROM producto p
JOIN detalle_pedido d
  ON p.id_producto = d.id_producto
GROUP BY p.id_producto, p.nombre
ORDER BY ventas DESC
LIMIT 3;
nombre ventas
Monitor 900000
Cámara 500000
Mouse 240000

Verifícalo a mano. El Mouse se vendió dos unidades en el pedido 101 y una en el 103, siempre a 80.000: 240.000. El Teclado, una unidad a 150.000, queda en cuarto lugar y LIMIT 3 lo deja fuera. Observa que el GROUP BY incluye p.id_producto además de p.nombre: agrupar por el identificador garantiza que dos productos distintos con el mismo nombre no se sumen juntos.

Esta consulta usa todo lo del tema: un JOIN que sigue una relación del modelo, una operación aritmética, una función de agregación, un GROUP BY, un alias y un ORDER BY con LIMIT. Cada línea responde a una de las cinco preguntas.

TipEjercicio 28.1

Cuánto ha gastado cada cliente en total, del que más al que menos. Responde primero las cinco preguntas del método.

NotaSolución

Tablas: cliente, pedido y detalle_pedido. Cada línea vale cantidad * precio_unitario. Camino: cliente a pedido por id_cliente, pedido a detalle_pedido por id_pedido. “Por cliente”: GROUP BY. “Del que más al que menos”: ORDER BY ... DESC.

SELECT c.nombre,
       SUM(d.cantidad * d.precio_unitario) AS total
FROM cliente c
JOIN pedido pe        ON c.id_cliente = pe.id_cliente
JOIN detalle_pedido d ON pe.id_pedido = d.id_pedido
GROUP BY c.id_cliente, c.nombre
ORDER BY total DESC;

Ana, 890.000 (160.000 + 150.000 + 500.000 + 80.000); Carlos, 900.000. Carlos queda primero. Laura, Juan y Sara no aparecen, porque un JOIN solo produce filas para los clientes que tienen pedidos.

8 El orden en que el motor lee una consulta

Una consulta se escribe en un orden y se evalúa en otro. Conocer el orden real explica varias reglas que de otro modo parecen caprichos:

Orden de evaluación Cláusula Qué hace
1 FROM y JOIN Reúne las tablas y las combina
2 WHERE Descarta filas
3 GROUP BY Forma los grupos
4 HAVING Descarta grupos
5 SELECT Elige columnas y calcula expresiones
6 ORDER BY Ordena el resultado
7 LIMIT Corta el resultado

De aquí salen tres consecuencias. WHERE no puede usar funciones de agregación, porque se evalúa antes de que existan los grupos; para eso está HAVING. Un alias definido en SELECT no puede usarse en WHERE, porque WHERE corre antes; sí puede usarse en ORDER BY, que corre después, y por eso ORDER BY ventas DESC funcionó en la misión final. Y LIMIT corta al final, sobre las filas ya ordenadas, lo que explica por qué sin ORDER BY devuelve filas arbitrarias.

9 Referencia rápida

-- Estructura
CREATE TABLE tabla (
    columna  TIPO [PRIMARY KEY | NOT NULL | UNIQUE],
    ...,
    PRIMARY KEY (columna, columna),
    FOREIGN KEY (columna) REFERENCES otra_tabla(columna)
);
ALTER TABLE tabla ADD COLUMN columna TIPO;
DROP TABLE tabla;

-- Datos
INSERT INTO tabla (col1, col2) VALUES (v1, v2), (v1, v2);
UPDATE tabla SET col1 = valor WHERE condicion;
DELETE FROM tabla WHERE condicion;

-- Consulta
