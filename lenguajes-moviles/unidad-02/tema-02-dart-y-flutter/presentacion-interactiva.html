void main() {
  var edades = {"Ana": 21, "Luis": 23}; // Map: pares clave y valor

Por qué existen las clases

Si ya puedes guardar datos en variables, ¿para qué haría falta algo más?

El problema

Dos estudiantes, cuatro variables

void main() {
  // Dos estudiantes guardados en variables sueltas
  String nombre1 = "Ana";
  int grupo1 = 601;
  String nombre2 = "Luis";
  int grupo2 = 602;

  print("$nombre1 está en el grupo $grupo1");
  print("$nombre2 está en el grupo $grupo2");
}
Funciona, pero nada dice que nombre1 y grupo1 van juntas. Con 30 estudiantes serían 60 variables sueltas.
Falta una forma de decir: "estos datos forman UNA sola cosa".
Ana está en el grupo 601
Luis está en el grupo 602

El problema

Un Map agrupa, pero no protege

void main() {
  Map<String, Object> ana = {"nombre": "Ana", "grupo": 601};

  print(ana["nombre"]); // Ana
  print(ana["gupo"]);
}
Un Map agrupa pares clave y valor. Ya tenemos todos los datos de Ana en una sola variable.
  1. 1Se crea un Map con nombre y grupo juntos. <String, Object> dice que las claves son texto y los valores pueden ser de cualquier tipo (los tipos entre < > se estudian en la sección 08). Mejoró: ahora hay una sola variable.
  2. 2Leer la clave correcta funciona y da Ana.
  3. 3Pero la clave está mal escrita: "gupo". Dart no avisa; busca esa clave, no la encuentra y devuelve null.

Predice antes de ejecutar

¿Qué da una clave mal escrita?

  print(ana["nombre"]); // Ana
  print(ana["gupo"]);

Con el Map de Ana, ¿qué imprime la segunda línea (ana["gupo"])?

Imprime null. Un Map devuelve null cuando la clave no existe, y el programa sigue como si nada. Un error de escritura queda escondido hasta que un valor null rompa algo más adelante. Queremos que Dart nos avise antes.

La solución

Una clase junta datos y acciones

Una clase agrupa los datos (campos) y las acciones (métodos) de un mismo concepto en un solo lugar.
Es un molde de galletas: define la forma, pero no te puedes comer el molde. Para comer, sacas galletas.
Cada galleta que sale del molde es un objeto. Puedes sacar muchas, y cada una tiene su propio sabor: sus propios datos.

Error común

Los campos final no se reasignan

class Estudiante {
  final String nombre = "Ana";
}

void main() {
  var ana = Estudiante();
  ana.nombre = "Luis";
}

Línea 7: 'nombre' can't be used as a setter because it's final.

Un campo final recibe su valor una sola vez y después ya no cambia. Úsalo para datos que no deben cambiar: un código, una fecha de creación.

Métodos: lo que el objeto sabe hacer

¿Cómo le enseñas a un objeto a trabajar con sus propios datos?

Idea y código

Un método es lo que el objeto sabe hacer

class Estudiante {
  String nombre = "";
  int grupo = 0;

  String presentarse() {
    return "$nombre, grupo $grupo";
  }

  void cambiarGrupo(int nuevoGrupo) {
    grupo = nuevoGrupo;
  }
}
  1. 1Un método se escribe dentro de la clase, igual que una función: tipo de retorno, nombre, paréntesis y cuerpo.
  2. 2Dentro del método puedes usar los campos directamente: nombre y grupo son los del objeto que lo llamó.
  3. 3cambiarGrupo recibe un valor y cambia un campo. Como no devuelve nada, su tipo es void.
Si el objeto es un estudiante, los campos son su ficha y los métodos son lo que sabe hacer: presentarse, cambiar de grupo.

Idea y código

Se llama con el punto y los paréntesis

void main() {
  var ana = Estudiante();
  ana.nombre = "Ana";
  ana.grupo = 601;

  print(ana.presentarse());
  ana.cambiarGrupo(602);
  print(ana.presentarse());
}
  1. 1Se crea el objeto y se le dan datos con los campos, como en la sección anterior.
  2. 2ana.presentarse() llama al método. Devuelve un texto, y print lo muestra.
  3. 3ana.cambiarGrupo(602) también es una llamada, pero no devuelve nada: solo cambia el campo.
  4. 4La misma llamada de antes da otro resultado, porque el objeto ahora tiene otro grupo.

Encapsulamiento: proteger los datos

¿Cómo evitas que cualquiera deje un objeto con datos sin sentido?

El problema

Cualquiera puede romper el objeto

class CuentaBancaria {
  double saldo = 0; // público: cualquiera lo puede cambiar
}

void main() {
  var cuenta = CuentaBancaria();
  cuenta.saldo = 50000;
  cuenta.saldo = -999999; // nada lo impide
  print(cuenta.saldo);
}
  1. 1El campo saldo es público: cualquier parte del programa puede leerlo y cambiarlo directamente.
  2. 2Esta asignación es razonable.
  3. 3Esta es absurda: una cuenta con saldo de -999999. Nada la impide, porque el campo está abierto a todos.
  4. 4La salida confirma que el objeto quedó con un estado sin sentido.
-999999.0

La solución

Esconde el dato, expón operaciones

encapsulamiento: el objeto guarda sus datos en privado y deja que otros los cambien solo con métodos que cuidan las reglas.
Un cajero automático: no metes la mano al dinero. Usas "retirar" o "depositar", y el banco revisa que la operación tenga sentido.
Así el saldo nunca puede quedar negativo por accidente: solo cambia por código de su propio archivo (en la práctica, los métodos de la clase).

Paso 1

El guion bajo vuelve el campo privado

class CuentaBancaria {
  final String titular;
  double _saldo = 0; // privado: el guion bajo lo oculta fuera de este archivo

  CuentaBancaria(this.titular);

  double get saldo => _saldo; // se puede leer, pero no asignar

  void depositar(double monto) {
    if (monto <= 0) {
      print("El monto debe ser positivo");
      return;
    }
    _saldo += monto;
  }
  1. 1El guion bajo al inicio hace al campo privado: solo el código de este mismo archivo puede usar _saldo.
  2. 2Un getter deja leer el saldo desde afuera, sin poder cambiarlo. Se usa como un campo: cuenta.saldo.
  3. 3depositar revisa la regla antes de actuar: si el monto no es positivo, avisa y sale con return.
  4. 4Solo aquí, dentro de la clase, el saldo aumenta.

Un método que devuelve si pudo o no

  bool retirar(double monto) {
    if (monto <= 0 || monto > _saldo) {
      return false;

    _saldo -= monto;
    return true;

}
  1. 1retirar devuelve un bool: true si funcionó, false si no.
  2. 2No permite montos que no sean positivos ni mayores al saldo disponible. En esos casos no toca nada y devuelve false.
  3. 3Si todo está bien, descuenta y avisa que salió bien.
  4. 4Observa lo que NO existe: ningún método permite dejar el saldo negativo.

Herencia y polimorfismo

¿Cómo reutilizas una clase para crear otra más específica?

El problema

Dos clases, la misma mitad de código

class Estudiante {
  final String nombre;
  final int grupo;
  Estudiante(this.nombre, this.grupo);

  String presentarse() => "Soy $nombre"; // repetido
}

class Docente {
  final String nombre;
  final String area;
  Docente(this.nombre, this.area);

  String presentarse() => "Soy $nombre"; // repetido
}
Las dos clases repiten nombre y presentarse(). Si mañana cambia cómo se presenta una persona, hay que editar los dos sitios.
Estudiante y Docente son, en el fondo, personas. Lo que tienen en común debería escribirse una sola vez.
Para eso existe la herencia: una clase toma lo de otra y agrega lo suyo.

La solución

Un Estudiante es una Persona

herencia: class Estudiante extends Persona significa "un Estudiante ES una Persona y además tiene lo suyo".
Como una receta base: la tarta de chocolate hereda la masa de la tarta básica y agrega lo suyo.
Se llama superclase a la clase de la que se hereda (Persona) y subclase a la que hereda (Estudiante).

Paso 1

extends toma casi todo lo de la superclase

class Persona {
  final String nombre;

  Persona(this.nombre);

  String presentarse() => "Soy $nombre";
}

class Estudiante extends Persona {
  final int grupo;

  Estudiante(super.nombre, this.grupo); // super.nombre se lo pasa a Persona
}
  1. 1La superclase Persona: un campo nombre, su constructor y el método presentarse().
  2. 2extends Persona: Estudiante hereda el campo y el método sin escribirlos otra vez.
  3. 3Y agrega lo suyo: el campo grupo.
  4. 4super.nombre recibe el nombre y se lo entrega al constructor de Persona. this.grupo se queda para Estudiante.

Cada subclase agrega lo suyo

class Docente extends Persona {

  2. 2Se crean los dos objetos.
  3. 3presentarse() no está escrito en Estudiante ni en Docente: funciona porque lo heredaron.
  4. 4Cada uno conserva sus campos propios: grupo y area.

Interfaces, mixins y enums

¿Cómo reutilizas comportamiento sin que todo sea una cadena de herencia?

Idea

Prometer métodos, sin heredar código

Una interfaz es un contrato: lista los métodos que una clase promete tener. Se cumple con implements.
El enchufe de la pared: no importa qué aparato conectes, siempre encaja igual.
Quien cumple el contrato debe escribir todo. No recibe código de regalo, a diferencia de extends. Cualquier clase puede usarse como contrato; una clase abstracta es la forma habitual.

Idea y código

Dos clases cumplen el mismo contrato

abstract class Notificable {
  void notificar(String mensaje);
}

class Correo implements Notificable {
  @override
  void notificar(String mensaje) => print("Correo enviado: $mensaje");
}

class Sms implements Notificable {
  @override
  void notificar(String mensaje) => print("SMS enviado: $mensaje");
}
  1. 1El contrato Notificable: cualquier cosa que lo cumpla sabe notificar un mensaje.
  2. 2implements Notificable: Correo promete cumplir el contrato.
  3. 3Y lo cumple escribiendo notificar. @override marca que reemplaza el método del contrato.
  4. 4Sms cumple el mismo contrato, a su manera.

Predice antes de ejecutar

¿Son iguales dos puntos con los mismos valores?

class PuntoA {
  final int x;
  final int y;

  PuntoA(this.x, this.y);
}
print(PuntoA(1, 2) == PuntoA(1, 2));

¿Qué imprime la última línea?

Imprime false. Por defecto, == compara la identidad: si son el mismo objeto. Cada PuntoA(1, 2) crea un objeto nuevo, aunque tengan los mismos valores.

Idea y código

== y hashCode van siempre juntos

class PuntoB {
  final int x;
  final int y;

  PuntoB(this.x, this.y);

  @override
  bool operator ==(Object other) =>
      other is PuntoB && other.x == x && other.y == y;

  @override
  int get hashCode => Object.hash(x, y);
}
  1. 1operator == es cómo se escribe el método que Dart llama cuando haces a == b. Se redefine: dos puntos son iguales si other también es un PuntoB y tiene los mismos x e y. Object es el tipo del que heredan todas las clases, así que other puede ser cualquier objeto.
  2. 2Se redefine hashCode: un número que resume el contenido. Object.hash(x, y) lo calcula a partir de los campos.
  3. 3Regla de oro: dos objetos iguales deben dar el mismo hashCode. Por eso se escriben los dos juntos.

Idea y código

El Set ya reconoce los repetidos

void main() {
  print(PuntoA(1, 2) == PuntoA(1, 2)); // false: son objetos distintos
  print(PuntoB(1, 2) == PuntoB(1, 2)); // true: mismos valores

  var conjunto = {PuntoB(1, 2), PuntoB(1, 2), PuntoB(3, 4)};
  print(conjunto.length); // 2: el Set ya reconoce los repetidos
}
  1. 1Sin la igualdad redefinida (PuntoA): false.
  2. 2Con ella (PuntoB): true, porque los valores coinciden.
  3. 3Llaves con solo valores crean un Set: una colección sin repetidos. Se entregan tres puntos, pero dos son iguales, así que solo quedan 2.

class Estudiante {

}

  2. 2retirar revisa la regla. Si el monto supera el saldo, throw lanza la excepción y el método termina ahí. Si no, sigue y confirma.

Prestar y devolver con reglas

  void prestar(Socio socio, Libro libro) {
    if (libro.prestado) {
      throw BibliotecaException("${libro.titulo} ya está prestado");
    }
    if (socio._enPrestamo.length >= maximoPorSocio) {
      throw BibliotecaException("${socio.nombre} alcanzó el máximo de $maximoPorSocio libros");
    }
    libro._prestado = true;
    socio._enPrestamo.add(libro);
  }

  void devolver(Socio socio, Libro libro) {
    if (!socio._enPrestamo.remove(libro)) {
      throw BibliotecaException("${socio.nombre} no tiene ${libro.titulo}");
    }
    libro._prestado = false;
  }
}
  1. 1Si el libro ya está prestado, se lanza la excepción antes de cambiar nada.
  2. 2Si el socio ya tiene el máximo, otra excepción.
  3. 3Recién ahí se marca el libro y se agrega a la lista del socio.
  4. 4devolver: remove devuelve false si el libro no estaba; entonces lanza. Si estaba, lo libera.
  5. 5Estas clases están en el mismo archivo, por eso Biblioteca puede usar los privados _prestado y _enPrestamo.

Una factura genérica con registro

class Factura<T extends Pagable> with Registro {
  final List<T> _items = [];

  void agregar(T item) {
    _items.add(item);
    anotar("Agregado un item de ${item.total()}");
  }

  double get total {
    double suma = 0;
    for (var item in _items) {
      suma += item.total();
    }
    return suma;
  }
}
  1. 1Factura<T extends Pagable>: acepta cualquier tipo que cumpla el contrato. with Registro le agrega la bitácora.
  2. 2Una lista privada de elementos de tipo T.
  3. 3agregar guarda el elemento y anota el evento usando el método del mixin.
  4. 4El getter total recorre la lista y suma los totales. No le importa si cada elemento es un Producto o un Servicio.

Dos clases: el widget y su estado

class Contador extends StatefulWidget {

  @override
  State<Contador> createState() => _ContadorState();

class _ContadorState extends State<Contador> {

  Widget build(BuildContext context) {
    return TextButton(
